# AIEvaluation Module API Documentation

The `AIEvaluation` module manages AI-model configuration (`ai_models`) and drives automatic AI grading of student assignment submissions through an external "Auto-Evaluation" service (Gemini-backed) — triggering evaluation, receiving async webhook callbacks with scores/feedback, and letting admins bulk-configure or manually override AI results.

**Module-wide auth:** everything in `Modules/AIEvaluation/Routes/api.php` is `auth:sanctum` + `json.response`, prefixed `/api/v1/...`, **except** `POST /v1/ai-assignments/webhook` which sits in its own route group with only `json.response` — no authentication at all (it's the external service's inbound callback; see below).

See [`./_COMMON_CONVENTIONS.md`](./_COMMON_CONVENTIONS.md) for the app-wide response envelope styles, standard error shapes, and pagination conventions. **None of this module's endpoints use the `apiResponse()`/`$this->apiResponse()` helpers** — every response here is a hand-rolled `response()->json([...])` (or, for `sendToAI`, a raw array auto-JSON-encoded by Laravel) with its own ad-hoc shape; do not assume the common envelope applies anywhere in this file.

`AIEvaluationController` (`Modules/AIEvaluation/Http/Controllers/AIEvaluationController.php`) only implements dead `apiResource`-style scaffolding (`index`/`create`/`show`/`edit` return Blade `view()` calls not reachable via any API route in this module; `store`/`update`/`destroy` are empty bodies, also unrouted) plus `use AIEvaluationTrait;`. Real logic for the two routes that target this controller lives in `Modules/AIEvaluation/Http/Traits/AIEvaluationTrait.php`. The rest of the module's routes target three separate `V1\*Controller` classes directly (no traits).

## Legacy `ai-evaluation/*` routes (`AIEvaluationController` + `AIEvaluationTrait`)

### `POST /v1/ai-evaluation/send-to-ai` (`sendToAI`, trait method)
- **Request params:** route-model-bound `Result $result` — **but the parameter is a query/body value, not a URL path segment** (the route is a flat `POST` with no `{result}` placeholder in its URI: `Route::post('ai-evaluation/send-to-ai', ...)`); Laravel resolves the bound `Result` from whatever the request sends under the key `result` (route-model binding falls back to matching a request input key named after the parameter for a non-URI-bound signature — in practice this only works if the caller supplies an appropriately-named `result` field/route substitution; treat as needing verification against a live request rather than assumed to "just work" like a normal `{result}` path binding). No FormRequest.
- **Behavior:** loads `student`, `student_assignment.assignment.topic`, `student_assignment.enrollment`; looks up `AICourseMaterialSyncs` by the enrollment's `course_id` to resolve the auto-eval-side course id (falls back to the local `course_id` cast to string if no sync row exists); builds a payload (`student_id`, `student_email`, `student_name`, `assignment_id`, `topic_id`, `topic`, `course_id`, `channel_id`, `submitted_file_url`, `webhook_url` = `{app.url}/api/v1/ai-evaluation/webhook`) and calls `AutoEvaluationService::triggerEvaluation()`.
- **External call:** `AutoEvaluationService::triggerEvaluation()` does `Http::attach('assignment', file_get_contents($submittedFileUrl), ...)->post("{config('app.auto_evaluation_api_url')}/v1/evaluate", [...])` — downloads the submitted file server-side and re-uploads it as a multipart attachment to the external Auto-Evaluation API, then returns `$response->json()` **verbatim, unwrapped** — the entire response body of `sendToAI` is whatever the external service returns (expected shape per this trait's usage: `{job_id, status}`, but not guaranteed/validated). No try/catch around the HTTP call or `file_get_contents` — a network failure or an inaccessible `submitted_file` URL will surface as an uncaught exception (Laravel's default 500 handler), not a clean app-level error response.
- **Side effects:** updates `Result.ai_evaluation_uuid` (= `$data['job_id']`) and `Result.ai_evaluation_status` (= `$data['status']`) — both **set to `null` silently** if the external response didn't contain those keys, no error raised; creates an `AIEvaluationAuditLogs` row (`event: 'AI_EVALUATION_TRIGGERED'`, `actor_id: auth()->id()`, `actor_type: 'user'`, `metadata` JSON excluding `submitted_file_url`).
- **Notes:** this is a distinct trigger path from `POST /v1/ai-assignments/evaluate` below (different controller, different job-based vs. synchronous-HTTP mechanism) — the two are not interchangeable despite similar intent. Confirm with the team whether this route is still actively used or superseded by the `ai-assignments/*` V1 surface.

### `POST /v1/ai-evaluation/webhook` (route → `AIEvaluationController::evaluationWebhook`)
- **⚠️ Dead/broken route — confirmed by source inspection.** `AIEvaluationController` (shown above) defines no `evaluationWebhook` method, and `AIEvaluationTrait` — the only trait it uses — defines `evaluationWebhookResultUpdate()`, not `evaluationWebhook()`. There is no `__call` magic method on the controller or a parent class that would intercept this. **Calling this route throws an uncaught `Error` (call to undefined method), surfacing as a framework 500**, not a documented JSON error shape. This appears to be leftover from a rename (`evaluationWebhookResultUpdate` was presumably renamed from/to `evaluationWebhook` and the route wasn't updated) — do not write a parity test expecting this route to function; document its actual behavior as "500 on any request" and flag to the team as a likely bug.
- **For reference only (the never-invoked trait method it probably meant to call):** `evaluationWebhookResultUpdate(Request $request)` would look up `Result::where('ai_evaluation_uuid', $data['uuid'])->firstOrFail()` (a missing/mismatched `uuid` → uncaught `ModelNotFoundException`, i.e. an ordinary 404 via the standard `ModelNotFoundException` handler shape — **but only if this method were actually reachable**), parse a `"16/20"`-style `total_score` string into a float, update AI fields on the `Result`, and log an `AIEvaluationAuditLogs` row (`event: 'AI_EVALUATION_COMPLETED'`, `actor_type: 'system'`). None of this executes today given the missing method.

## `ai-models` CRUD (`AIModelController`)

### `GET /v1/ai-models` (`index`)
- **Success response:** bare `AIModelResource::collection(AIModels::orderBy('id','desc')->get())` — Laravel's default resource-collection auto-wrap, i.e. `{"data": [...]}`, **no `meta`/pagination at all** — the whole table is returned unpaginated on every call.
- `AIModelResource` fields: `id`, `name` (= `model_name`), `version` (= `model_version`), `description` (= `model_description`), `gemini_model_id`, `is_default` (cast to bool), `is_active` (cast to bool), `created_at`, `updated_at`.

### `POST /v1/ai-models` (`store`)
- **Request body:** no FormRequest — inline `$request->validate([...])`: `model_name` required string max:255; `model_version` nullable string max:255; `model_description` nullable string; `gemini_model_id` required string max:255.
- **Success response:** `new AIModelResource($model)` → `{"data": {...}}` (default resource auto-wrap), implicit 200 (not 201, despite being a creation endpoint).
- **Side effects:** `is_default` is auto-set to `1` **only if this is the very first row ever created** (`AIModels::count() === 0`) — every subsequent `store` call defaults `is_default` to `0` regardless of request input (the field isn't even accepted from the request body); `is_active` always forced to `1`; `created_by` = `Auth::id()`. Wrapped in `DB::transaction()` (no multi-step writes inside it besides the single insert, so the transaction has no real effect here).

### `PUT /v1/ai-models/{id}` (`update`)
- Raw `$id` param, `AIModels::findOrFail($id)` — standard `ModelNotFoundException` 404 shape (see common conventions) on a bad id.
- **Request body:** inline validate: `model_name` sometimes|required string max:255; `model_version`/`model_description` nullable; `gemini_model_id` sometimes|required string max:255. **`is_default`/`is_active` are not accepted here at all** — only `setDefault`/`destroy` below can change those fields.
- **Success response:** `new AIModelResource($model)`.
- **Side effects:** `updated_by` = `Auth::id()`.

### `PATCH /v1/ai-models/{id}/set-default` (`setDefault`)
- `findOrFail($id)` — standard 404 on miss.
- **Success response:** `new AIModelResource($model)`.
- **Side effects (in `DB::transaction()`):** unsets `is_default` on **every** row currently flagged default (`AIModels::where('is_default',1)->update(['is_default'=>0])` — not scoped to "the previous default", so if data integrity is ever violated and multiple rows are flagged default, all get cleared), then sets `is_default=1` **and** forces `is_active=1` on the target (so setting a soft-deactivated model as default silently reactivates it too), `updated_by` = `Auth::id()`.

### `DELETE /v1/ai-models/{id}` (`destroy`)
- `findOrFail($id)` — standard 404 on miss.
- **Error response:** `response()->json(['message' => 'The default AI model cannot be deactivated.'], 422)` if `$model->is_default` is truthy — the current default model can never be deleted/deactivated via this route (no route to un-default it except `setDefault` on a *different* model first).
- **Success response:** `response()->json(['message' => 'AI model deactivated successfully.'])` — default 200, **no `data` key at all**.
- **Side effects:** sets `is_active=0`, `updated_by=Auth::id()`, **then also calls `$model->delete()`** — the model uses `SoftDeletes`, so this is a soft delete on top of the `is_active=0` flag flip; the row becomes both "inactive" and "trashed" simultaneously via two separate writes (a genuinely redundant double-signal for "this model is gone", worth confirming which flag downstream code actually checks).

## `ai-assignments/*` bulk & evaluation actions (`AIModelBulkAssignmentController`)

### `POST /v1/ai-assignments/bulk-assign` (`bulkAssign`)
- **Request body:** inline validate — `course_ids` nullable array (each `exists:courses,id`); `assignment_ids` nullable array (each `exists:assignments,id`); `student_assignment_ids` nullable array (each `exists:student_assignments,id`); `ai_model_id` nullable `exists:ai_models,id`; `is_ai_enabled` nullable boolean; `assignment_instruction_link`/`assignment_sample_feedback_link` nullable string; `assignment_instruction_file`/`assignment_sample_feedback_file` — validated as `nullable|file|mimes:pdf,doc,docx|max:10240` **only if `$request->hasFile(...)` is true at validation time**, otherwise validated merely as `nullable|string` (so a non-file string value under the same key is accepted without file-type checking); `update_linked_assignments` nullable boolean (defaults to `true` if omitted).
- **⚠️ `course_ids` path is entirely dead code:** the "1. Update Courses" block that would apply `$updateData` to `Course` rows, cascade to `Assignment`/`StudentAssignment`, flip `AICourseMaterialSyncs.sync_status`, and dispatch `SyncCourseMaterialToAutoEvalJob` is **commented out in full** in source. Passing `course_ids` today does nothing except pass validation — it is never read again after that point. Only `assignment_ids` and `student_assignment_ids` actually update anything.
- **Behavior:** for file uploads, uses `Course`/`Assignment`/`StudentAssignment` (first id in whichever array is non-empty, `course_ids` checked first — but since the course branch is dead, an upload with only `course_ids` populated attaches media to a `Course` row that is never otherwise updated) as a Spatie-Media-Library host via `addMediaFromRequest()->toMediaCollection(...)`, replacing (`clearMediaCollection()` first) any existing file in that collection; falls back to accepting a literal string URL under the same field name if no file is present. `assignment_ids` → bulk-updates `Assignment` rows with `$updateData` (`ai_model_id`, `assignment_instruction_link`, `assignment_sample_feedback_link`, `is_ai_enabled`) and, if `update_linked_assignments` is truthy, cascades the subset of those fields to `StudentAssignment` rows via `whereIn('assignment_id', ...)`. `student_assignment_ids` → directly updates those `StudentAssignment` rows with the same field subset.
- **Success response:** `response()->json(['status'=>'success','message'=>'Bulk AI assignment configuration completed successfully.','data'=>['updated_courses'=>0,'updated_assignment_templates'=>N,'updated_student_assignments'=>N]])` — **`updated_courses` is always literally `0`**, never incremented, since that code path is dead.
- **Side effects:** one `activity()` log entry (`event: 'AI Bulk Configuration Updated'`, no `->on()` subject — attaches to no model) recording the ids/fields touched.

### `POST /v1/ai-assignments/bulk-evaluate` (`bulkEvaluate`)
- **Request body:** inline validate — `student_assignment_ids` required array, each `exists:student_assignments,id`.
- **Filtering:** loads only `StudentAssignment` rows where `is_ai_enabled = 1` **and** having a `results` row with `status != Result::EVALUATED`, restricted to the submitted ids — ids that fail either condition (not AI-enabled, or already fully evaluated) are **silently dropped**, not individually reported as errors.
- **Error response:** `response()->json(['status'=>'error','message'=>'No valid student assignments found for evaluation.'], 422)` if the filtered set is empty.
- **Success response:** `response()->json(['status'=>'success','message'=>"Bulk evaluation of {N} assignments initiated through Auto-Evaluation service."])` — **no `data` key**, `N` is the filtered (not requested) count.
- **Side effects:** dispatches `BulkEvaluateStudentAssignmentsJob::dispatch($studentAssignments)` (queued); one summary `activity()` log (`event: 'AI Bulk Evaluation Triggered'`, no subject) plus **one additional per-item** `activity()` log attached to each `StudentAssignment`'s first `results()` row (`event: 'AI Evaluation Triggered'`) — a student assignment with no `results` row at all is silently skipped for this per-item logging (but was already included in the job dispatch and the summary count).

### `POST /v1/ai-assignments/evaluate` (`singleEvaluate`)
- **Request body:** inline validate — `student_assignment_id` required `exists:student_assignments,id`.
- **Behavior:** no existence/state filtering beyond the `exists` rule (unlike `bulkEvaluate`, this does **not** check `is_ai_enabled` or evaluation status before proceeding) — looks up the first `results()` row with `latest = Result::ACTIVE` (may be `null` if none matches; not an error condition here).
- **Success response:** `response()->json(['status'=>'success','message'=>"AI evaluation triggered for student assignment ID: {$id}."])` — matches `API_SPECIFICATIONS.md`'s existing note on this endpoint; confirmed still accurate.
- **Side effects:** dispatches `EvaluateStudentAssignmentJob::dispatch($id)` (queued — **the actual external HTTP call to the Auto-Evaluation service happens inside the job, not synchronously in this request**, unlike the legacy `sendToAI` trait method above which calls out synchronously); `activity()` log (`event: 'AI Evaluation Triggered'`) attached to the resolved `$result` if found, else to the `StudentAssignment` itself.

### `POST /v1/ai-assignments/reevaluate` (closure route → `AIModelBulkAssignmentController::singleReevaluate`)
- **Route definition is a closure**, not a direct controller-method route binding: `Route::post('ai-assignments/reevaluate', function (Request $request) { $request->merge(['is_evaluated' => 1]); return app(...)->singleReevaluate($request); })` — the closure **force-injects `is_evaluated: 1`** into the request before handing off, overwriting any `is_evaluated` value the client sent, every time, unconditionally.
- **Request body:** (as seen by `singleReevaluate`, post-merge) `student_assignment_id` required `exists:student_assignments,id`; `is_evaluated` nullable integer — but effectively **always `1`** due to the closure's merge, regardless of what the client sends for this field.
- **Error response:** `response()->json(['status'=>'error','message'=>'Student Assignment not found'], 404)` if `StudentAssignment::find($id)` misses — a hand-rolled 404, not `findOrFail`.
- **Behavior:** if a `results()` row with `latest = Result::ACTIVE` exists, resets `ai_evaluation_status → 'PENDING'` and `ai_evaluated_at → null`; **because of the closure's forced merge, `$request->input('is_evaluated') == 1` is always true**, so `is_evaluated => 1` is unconditionally added to that update as well — i.e. every reevaluate call marks the result `is_evaluated=1` even before the job has re-run.
- **Success response:** `response()->json(['status'=>'success','message'=>"AI re-evaluation triggered successfully for student assignment ID: {$id}."])`.
- **Side effects:** dispatches `EvaluateStudentAssignmentJob::dispatch($id)` (queued); `activity()` log (`event: 'AI Re-evaluation Triggered'`), message interpolates `{$result?->ai_evaluation_status}` — captured **after** the reset above, so the logged "previous status" text is actually already `PENDING`, not the true pre-reevaluate status (a logging-order bug: the log always reads back the just-written value).

### `POST /v1/ai-assignments/edit-feedback` (`editFeedback`)
- **Request body:** inline validate — `result_id` required `exists:results,id`; `feedback_content` required string (raw HTML from a rich-text editor); `ai_score` nullable numeric 0–100; `reason` nullable string.
- **Error response:** `response()->json(['status'=>'error','message'=>'Result not found'], 404)` — hand-rolled, via `Result::find()` not `findOrFail()` (redundant given the `exists:results,id` rule already guarantees existence at validation time, but present as defensive code).
- **Behavior (in `DB::transaction()`):** renders `feedback_content` into a `resources/views/ai_feedback_template.blade.php` view wrapped in Word-compatible HTML/XML namespaces, uploads it to the `s3` disk at `uploads/ai_evaluations/manual_feedback/{slug(student_name)}_{result_id}_{time()}.docx` (a `.docx` extension on what is actually raw HTML content, not a real binary Word file — Word can often open HTML-as-.docx via the namespace trick, but this is not a genuine OOXML document). If `ai_score` is present, replaces (`delete()` then `create()`) all `resultExerciseScores()` rows with a single synthetic entry (`serial_number: 1`, `full_marks: 10` hardcoded).
- **Success response:** `response()->json(['status'=>'success','message'=>'Feedback updated successfully.','data'=>{result_id, ai_feedback_docx_url, original_feedback_url, ai_score, reason}])`.
- **Side effects:** updates `Result` (`ai_feedback_pdf_url`, `ai_feedback`, `feedback_edit_reason`, `feedback_file`, `feedback_file_original_name`, `updated_by`, optionally `ai_score`); `activity()` log (`event: 'AI Evaluation Feedback Edited'`) capturing before/after feedback URL.

## Public webhook (external inbound, no auth)

### `POST /v1/ai-assignments/webhook` (route name `ai-evaluation.webhook`, `V1\AIEvaluationWebhookController::handle`)
- **Auth:** none — separate `Route::group(['prefix'=>'v1','middleware'=>['json.response']], ...)`, no `auth:sanctum`. This is the real, functioning webhook receiver for the external Auto-Evaluation service (distinct from — and not to be confused with — the dead `POST /v1/ai-evaluation/webhook` above, which is a different, broken route despite the similar name).
- **External call:** this endpoint is itself the receiving end of an external call, not a proxy to one — response shape/timing is entirely under this app's control.
- **Request body:** no FormRequest, raw `$request->input(...)` access throughout. `uuid` (used to look up `Result::where('ai_evaluation_uuid', $uuid)->first()`), `status` (`'COMPLETED'`/`'FAILED'`/anything else), plus status-dependent fields below.
- **Error responses:** `response()->json(['message' => 'UUID missing in payload'], 400)` if `uuid` is absent/falsy; `response()->json(['message' => 'Result record not found for provided UUID'], 404)` if no `Result` matches — both hand-rolled, no `status` field at all (deviates from every other error shape in this module).
- **`status === 'COMPLETED'` branch:** reads `total_score`, `final_verdict`, `pdf_url`, `exercise_scores` (optional array); updates the `Result` row (`ai_evaluation_status`, `ai_score` = raw `total_score` **not parsed from a `"16/20"` string here** — unlike the dead trait method above, this live handler stores `total_score` as-is; `ai_feedback` = `final_verdict`, `ai_feedback_pdf_url`/`feedback_file` = `pdf_url`, `ai_evaluated_at` = `now()`); deletes and rebuilds `resultExerciseScores()` from `exercise_scores` if provided as an array (each entry: `obtain_marks` = `$score['score'] ?? $score`, `full_marks` = `$score['full_marks'] ?? 10`), else — if `total_score` is non-null — creates a single synthetic entry instead. A large block of exercise-count-mismatch validation and staging→prod S3 URL remapping logic is **present but fully commented out** in source; do not expect either behavior live.
- **`status === 'FAILED'` branch:** reads `failed_step`, `failed_at`, `reason`; sets `ai_evaluation_status = 'FAILED'` and a synthesized `ai_feedback` string (`"AI Evaluation Failed. Step: {step} at {at}. Reason: {reason}"`), `ai_evaluated_at = now()`.
- **Any other `status` value:** falls through to an `else` branch that only updates `ai_evaluation_uuid`/`ai_evaluation_status` — no feedback/score fields touched, no activity log written for this branch (activity logging only happens in the `COMPLETED`/`FAILED` branches).
- **Success response:** `response()->json(['status' => 'success', 'message' => 'Result updated successfully.'])` — returned for **every** status branch including the untyped "else" fallthrough, so a 200 here does not imply the payload was actually recognized as `COMPLETED` or `FAILED`.
- **Side effects:** `Log::info`/`Log::warning` calls throughout; on `COMPLETED`/`FAILED`, an `activity()` log entry (`event: 'AI Evaluation Completed'` / `'AI Evaluation Failed'`) attached to the `Result`, attributed via `resolveSubmitter()` — a private helper that looks up the most recent `AI Evaluation Triggered`/`AI Re-evaluation Triggered` activity-log entry for that `Result` and reuses its `causer` as the actor, since the actual caller here is an unauthenticated external service with no user identity of its own. If no prior triggering activity log exists (e.g. the result's evaluation was kicked off some other way), `resolveSubmitter()` returns `null` and the log is written with no causer.

## Summary

**Routes documented:** all 12 routes in `Modules/AIEvaluation/Routes/api.php` (11 live, distinct behaviors + 1 confirmed-broken route).

**Notable bugs/discrepancies found:**
- **`POST /v1/ai-evaluation/webhook` is broken** — routes to `AIEvaluationController::evaluationWebhook`, a method that does not exist on the controller or its trait (`AIEvaluationTrait` only defines `evaluationWebhookResultUpdate`). Any call 500s. This contradicts `API_SPECIFICATIONS.md`'s framing of `ai-evaluation/webhook` as a functioning "inbound receiver from the external AI service" — that description actually applies only to the separate, correctly-wired `POST /v1/ai-assignments/webhook` (`AIEvaluationWebhookController::handle`). The two routes have confusingly similar names/paths (`ai-evaluation` vs `ai-assignments`) but only one works.
- `bulkAssign`'s entire `course_ids` update path (course/cascade-to-assignments/sync-status/job-dispatch) is dead, commented-out code — `updated_courses` in the response is always `0`.
- `reevaluate`'s closure route unconditionally force-sets `is_evaluated=1` on the request regardless of client input, and its activity-log message logs the just-reset `PENDING` status as if it were the "previous" status (order-of-operations bug).
- `destroy` on `ai-models` both flips `is_active=0` **and** soft-deletes the row — two redundant "gone" signals on the same action.
- The live webhook (`AIEvaluationWebhookController::handle`) parses `total_score` as a raw passthrough value, while the dead/unreachable trait method (`evaluationWebhookResultUpdate`) would have parsed a `"16/20"`-style string into a float — these two near-duplicate implementations disagree on `ai_score` semantics, and only the raw-passthrough one is actually live.
- `sendToAI`'s route has no `{result}` URI placeholder despite type-hinting a route-model-bound `Result $result` parameter — verify empirically how/whether Laravel resolves this binding before relying on it in a parity test.
- None of this module's endpoints use the shared `apiResponse()` helper; every response is a bespoke `response()->json()` shape, several without a `status` field at all (the two webhook 400/404 errors).

**Confidence:** High for all `ai-models` and `ai-assignments/*` (V1 controllers) endpoints and the live webhook handler — read in full. High-confidence dead-code call for `POST /v1/ai-evaluation/webhook` (confirmed via direct grep for `evaluationWebhook` across the module — the only occurrence is the route definition itself). Medium confidence on `sendToAI`'s exact route-model-binding resolution behavior (flagged as needing empirical verification, not guessed).
