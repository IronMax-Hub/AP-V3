# AssignmentCSAT Module — API Documentation

The `AssignmentCSAT` module owns the `assignment_csat_form` (+ `assignment_csat_form_reasons` / `assignment_csat_form_reasons_mapping`) tables — a student's satisfaction survey about a specific assignment/enrollment (as distinct from `EvaluatorCSAT`, which surveys the evaluator — see `EvaluatorCSAT.md`). See [`./_COMMON_CONVENTIONS.md`](./_COMMON_CONVENTIONS.md) for app-wide envelope/error/pagination conventions.

**Module-wide auth:** every route in `Modules/AssignmentCSAT/Routes/api.php` is `auth:sanctum` + `json.response`, prefix `v1` — this module's **own** routes are all staff/admin-token routes, including `store()`. Like `NPS`'s and `EvaluatorCSAT`'s `store()` endpoints, `student_id` is taken directly from the request body with no cross-check against an authenticated student identity.

**Class layout:** `AssignmentCSATController` implements `index()`/`store()` directly; `use`s `AssignmentCSATTrait` for `graphIndex()`/`export()`/`checkAvailable()`/`getAssignmentCSATFormReason()`/`getCSATQuestionsAccordingToRating()`/`calculateRangeForCursor()`.

## ⚠️ Critical finding: `assignment_csat_form.assignment_id` has two mutually incompatible meanings depending on which of two entirely different endpoints created the row
`AssignmentCSATForm` (the entity) defines **two relations off the exact same `assignment_id` column**: `assignment(): belongsTo(Assignment::class)` (the real `Assignment` template, module `Assignment`) and `student_assignment(): belongsTo(StudentAssignment::class, 'assignment_id')` (a `StudentAssignment` row — see `StudentAssignment.md`). Which interpretation is *correct* for a given row depends entirely on which endpoint wrote it:
- **This module's own `POST /v1/assignment-csat` (`store()`, documented below)** validates and persists `assignment_id` via `StoreAssignmentCSATRequest`'s rule `'assignment_id' => ['required', 'exists:assignments,id']` — i.e., for rows created here, `assignment_id` genuinely is an `Assignment` template id.
- **A separate, student-facing submission endpoint that this module's own route file does NOT declare** — `POST /student/v1/assignment-csat/{student_assignment}/submit`, registered in `Modules/StudentFrontendEnrollment/Routes/api.php` and handled by `Modules\StudentFrontendEnrollment\Http\Controllers\AssignmentCSATController::submit` (a **different class** from this module's own controller, despite the identical class name — confirm the namespace when tracing, both are imported into that route file, one aliased `ControllersAssignmentCSATController`) — writes `'assignment_id' => $studentAssignment->id`, i.e., for rows created via *this* path, `assignment_id` is a **`StudentAssignment` id**, not an `Assignment` id.
- **`AssignmentCSATFormResources` (this module's own listing resource, used by `index()` below) calls `$this->student_assignment?->assignment?->topic?->only('title')` to populate its `assignment_topic` field** — i.e., it assumes the *second* interpretation (`assignment_id` = a `StudentAssignment` id) is universally correct. **For any row actually created via this module's own `store()` endpoint** (where `assignment_id` is a real `Assignment` id), this lookup resolves `student_assignment` to whatever unrelated `StudentAssignment` row happens to share that numeric id — **`index()`'s displayed `assignment_topic` for `store()`-created rows will show the topic of a coincidentally-numbered, unrelated `StudentAssignment`, not the actual assignment the CSAT was about.** This is a genuine, silent data-display bug affecting every row created through this module's own admin-facing `store()` endpoint. A parity test must seed data through both paths and verify `index()`'s `assignment_topic` output separately for each — do not assume the two write paths produce interchangeable rows.
- The GET half of the student-facing pair, `GET /student/v1/assignment-csat/{student_assignment}` (also in `StudentFrontendEnrollment`'s route file), correctly delegates to **this module's own** `getAssignmentCSATFormReason()` trait method (see below) — that one genuinely is this module's code, just reached via someone else's route declaration.

Full detail on the `StudentFrontendEnrollment`-owned `submit()` action itself (ownership check, duplicate-submission check via `assignmentCsatForm()->count() >= 1`, `SubmitStudentEvaluatorCSATRequest`) belongs in that module's own documentation file, not here — it's flagged here only because it's the second writer of this module's table and the source of the `assignment_id` ambiguity above.

## Core CRUD (`Route::apiResource('assignment-csat', 'AssignmentCSATController')`) — only `index`/`store` are real

### `GET /v1/assignment-csat` — `index()` (controller)
- Query: `rows` (default 15).
- **Success response:** `AssignmentCSATFormResources::collection(...)->additional(['meta' => ['total' => ..., 'range' => ...]])`.
- `AssignmentCSATFormResources` fields: `rating`, `other`, `comment` (note: the raw column is named `other`, distinct from `EvaluatorCSATForm`'s equivalent `other_option` column — the two CSAT modules don't share a schema despite the conceptual overlap), `student` (`{full_name, country_code, phone, email}` — **unguarded** `$this->student->full_name`/`phone`/`email`, `null`-safe only for `countryRelation` — a row with no resolvable student fatal-errors), `course` (`{course_name}`), `batch` (`{batch_date}` or `null`), `package` (`{name}` or `null`), `question` (same hardcoded-reason-id pattern as `EvaluatorCSAT`, see below), `reasons` (same N+1, unguarded-`->first()` pattern as `EvaluatorCSATFormResource::getReason()` — see `EvaluatorCSAT.md` for the identical bug shape), `submitted_date` (from `created_at`), `assignment_topic` (see the critical finding above — **only reliable for rows created via the `StudentFrontendEnrollment`-owned `submit()` path**), `bootcamp` (`{bootcamp_id, bootcamp_name}` via a fresh `Enrollment` re-query, `null` if bootcamp fields are `0`/`null` — same pattern as `EvaluatorCSATFormResource`), `edmingle_batch_name`.
- **`question` resolution:** `app(AssignmentCSATController::class)->getCSATQuestionsAccordingToRating($this->rating)` — same pattern as `EvaluatorCSAT`'s resource (a fresh controller resolved from the container mid-serialization), with its own **independently hardcoded** `AssignmentCSATFormReasons` ids: `14` for `rating >= 4`, `8` for `rating == 3`, `1` for `rating < 3` — **note `rating` on `AssignmentCSATForm` is stored as a string** (see `StoreAssignmentCSATRequest` below), so this comparison (`$rating >= 4`, numeric context) relies on PHP's numeric-string coercion; a non-numeric string in `rating` would make every one of these comparisons evaluate as `false` (a non-numeric string compared numerically is treated as `0` in PHP 8's comparison rules for numeric operators against non-numeric strings, so `'abc' >= 4` is false, `'abc' == 3` is false, `'abc' < 3` is true) — meaning a non-numeric `rating` value falls through to the `< 3` branch (id `1`) by coincidence of PHP's comparison semantics, not by design.

### `POST /v1/assignment-csat` — `store()` (controller)
- **Request body** (`StoreAssignmentCSATRequest`): `student_id` required `exists:students,id`; `assignment_id` required `exists:assignments,id` (see the critical finding above — this really is an `Assignment` id here); `enrollment_id` required **without** `package_id`; `package_id` required **without** `enrollment_id` (exactly one of the two, matching `API_SPECIFICATIONS.md`'s documented mutual exclusivity); `course_id` required `exists:courses,id`; `batch_id` required `exists:course_batches,id`; `rating` required **string** max:255 (confirmed — genuinely a string here, unlike `EvaluatorCSAT`'s integer `rating`, matching `API_SPECIFICATIONS.md`'s note); `selectedOrderIds` required array, each `exists:assignment_csat_form_reasons,id`.
- **Duplicate checks — two separate, near-identical blocks, one per exclusivity branch:** if `enrollment_id` is set, checks `checkIfDuplicate($student_id, $assignment_id, $enrollment_id)`; if `package_id` is set, checks `checkIfDuplicate($student_id, $assignment_id, null, $package_id)` — both `if(isset(...))` guards are effectively always-true in practice given the FormRequest's `required_without` pairing guarantees exactly one of the two is present. Either duplicate match returns `$this->apiResponse([], 'Already Submitted', statusCode: 200)` — `data: []` here (contrast with `EvaluatorCSAT`'s identical-purpose check, which returns `data: null` — the two modules' "already submitted" responses are not byte-identical despite the same semantic meaning), HTTP 200 for a semantic rejection, matching the cross-cutting caution in `_COMMON_CONVENTIONS.md`.
- **Success response:** `$this->apiResponse($csatData, 'Assignment CSAT Submitted Successfully', statusCode: 201)` — `data` is the raw created `AssignmentCSATForm` model, not a Resource — same "less-processed than `index()`'s shape" pattern noted for `EvaluatorCSAT::store()`.
- **Side effects (inside `DB::transaction()`):** creates one `AssignmentCSATForm` row (no `status` column set here at all — unlike `EvaluatorCSATForm`'s forced `STATUS_TYPE_1`, this entity's `store()` path doesn't set any status-like field); creates one `AssignmentCSATFormReasonsMapping` row per id in `selectedOrderIds[]`.

### `GET /v1/assignment-csat/{assignmentCSAT}`, `PUT/PATCH /v1/assignment-csat/{assignmentCSAT}`, `DELETE /v1/assignment-csat/{assignmentCSAT}` — `apiResource`'s `show`/`update`/`destroy` — **confirmed broken, no methods exist**
Neither `AssignmentCSATController` nor `AssignmentCSATTrait` implements `show()`, `update()`, or `destroy()` — confirmed by reading both files in full. All 3 routes trigger a PHP fatal `Error: Call to undefined method` on any call — the same broken-`apiResource` pattern documented repeatedly across this codebase.

## `GET /v1/assignment-csat/graph-index` — `graphIndex()` (trait method)
- Behaviorally **byte-for-byte identical in structure** to `EvaluatorCSAT::graph_index()` (see `EvaluatorCSAT.md` for the full breakdown of the 1–5 rating scale, the combined `"N(XX.XX%)"` percentage-string fields, the fixed rating-to-color mapping, and the `totalEligible`-is-a-misnomer-for-`totalSubmitted` note) — the two methods appear to be copy-pasted from one another, differing only in which repository's `graphSearch()` they call (`assignmentCSATFormRepo` here vs. `EvaluatorCSATFormRepository` there). All the same caveats apply verbatim: unbounded/unpaginated full-scan query, 1–5 (not 0–10) rating scale, no actual eligibility computation despite the `totalEligible` key name.

## `GET /v1/assignment-csat/reasons` — route registered as `getCSATFormReason`, **but no method by that name exists anywhere in this module — confirmed broken, a genuinely different failure mode from `EvaluatorCSAT`'s working same-purpose endpoint**
`Modules/AssignmentCSAT/Routes/api.php` declares `Route::get('/assignment-csat/reasons', [AssignmentCSATController::class, 'getCSATFormReason'])`. **Grepped the full module tree: no method named `getCSATFormReason` exists in `AssignmentCSATController` or `AssignmentCSATTrait`.** The trait *does* define a method that looks like it was meant for a similar purpose — `getAssignmentCSATFormReason(StudentAssignment $studentAssignment)` — but (a) its name doesn't match what this route asks for, and (b) even if it did, its signature requires a `{student_assignment}` route parameter that this specific route (`/assignment-csat/reasons`, no path parameter) doesn't supply. Calling `GET /v1/assignment-csat/reasons` therefore triggers a PHP fatal `Error: Call to undefined method`, an uncaught 500 — **this is a distinct bug from `EvaluatorCSAT`'s own `/evaluator-csat/questions` route, which does successfully resolve to a real (if buggy) method** — don't conflate the two modules' "reasons/questions" endpoints; one is reachable-but-buggy, the other is unreachable entirely.
- **The trait's `getAssignmentCSATFormReason()` method is not dead code, however** — it's genuinely reachable, just via a route this module doesn't itself declare: `GET /student/v1/assignment-csat/{student_assignment}` in `Modules/StudentFrontendEnrollment/Routes/api.php` (`auth:student` guarded, prefix `student/v1`) points directly at it. When called correctly (with a real `{student_assignment}` id): loads `student_assignment.assignment.topic`, and returns a **hand-rolled, non-`apiResponse()` JSON shape**: `{"status": "success", "topic": "<title>", "lowRateOptions": {"question": "What was the issue with the assignment?", "options": [...]}, "midRateOptions": {...}, "highRateOptions": {...}}` — each `options` array is that reason's `children` relation (id/parent_id/`question as name`), looked up by matching on the **literal question text string** (`whereIn('question', [...])` against 3 hardcoded English sentences) rather than by any stable id or type constant — if any of those 3 question strings are ever edited in the `assignment_csat_form_reasons` table, this lookup silently returns no options for that bucket rather than erroring.

## `GET /v1/assignment-csat/export` — `export()` (trait method)
- **Success response:** `apiResponse('', 'Assignment CSAT Csv file exporting started', 'success')`.
- **Side effects:** same `Maatwebsite\Excel` `queue()`-chained-to-a-completion-job pattern as `EvaluatorCSAT::export()` (see `EvaluatorCSAT.md`) — `$this->excel->queue(new AssignmentCSATExport(), "exports/tmp/assignments/{filename}", 's3')->chain([new AssignmentCSATCSVDownload($user, $data)])`. **Note the S3 path**: `exports/tmp/assignments/{filename}` — this is the **same S3 folder** (`exports/tmp/assignments/`) used by the unrelated `Assignment` module's own template-listing CSV export (see `Assignment.md`'s `export()`) and by `StudentAssignment`'s export (`exports/tmp/assignments` too, per `StudentAssignment.md`) — **all three modules' CSV exports land in the identical S3 prefix**; filenames are distinguished only by their own per-module naming convention (`assignment-csat{time}{userId}.csv` here, no separating character between `assignment-csat` and the timestamp, unlike the hyphenated `assignments-{time}...` pattern in the other two) — collisions are unlikely given the distinct prefixes/timestamps, but a test cleaning up "everything under `exports/tmp/assignments/`" would need to account for files from all three modules, not just this one.
- Only a completion mail fires (`AssignmentCSATCSVDownload` → `Mail::to(...)->queue(new AssignmentCSATCSVCompletedMail(...))`, verify directly for exact class if needed) — no in-app notification, matching `EvaluatorCSAT`'s export flow rather than `Assignment`'s/`Evaluator`'s (which both also fire an in-app notification).

## `POST /v1/assignment-csat/check-available` — `checkAvailable()` (trait method)
- **Request body** (`CheckEligibleForCSATRequest`): `student_id` required `exists:students,id`; `assignment_id` required `exists:assignments,id` (again the real `Assignment` template table — this eligibility check's own `assignment_id` semantics match this module's `store()`, not the `StudentFrontendEnrollment` submission path's `StudentAssignment`-id semantics — a third point of confusion if a client tries to reuse an id from one context in the other); `enrollment_id` required `exists:enrollments,id` (**no `package_id` alternative accepted here at all** — unlike `store()`'s mutual-exclusivity pair, this eligibility check has no package-enrollment variant; a package-enrollment CSAT eligibility cannot be pre-checked through this endpoint).
- **Success responses:** `$this->apiResponse([], 'Already Submitted', statusCode: 200)` or `$this->apiResponse([], 'Elligable for Submission', statusCode: 201)` — identical shape, identical misspelling (`'Elligable'`), identical unusual-201-for-a-read-only-check pattern as `EvaluatorCSAT::checkAvailable()` (see `EvaluatorCSAT.md`) — the two methods are structurally identical aside from which repository/table they check against.

## Summary of endpoints documented

**8 route entries** (`graph-index` + `reasons` + `export` + `check-available` + the 5-route `apiResource` = 8 total):
- **5 live/working:** `graphIndex`, `export`, `checkAvailable`, `index`, `store`.
- **3 confirmed broken:** `reasons` (route references a nonexistent method name — a *different* failure signature from the usual "the method genuinely doesn't exist anywhere" pattern, since a same-purpose-but-differently-named-and-differently-signatured method *does* exist, just unreachable from this route), and `apiResource`'s `show`/`update`/`destroy` (undefined methods).

**Notable findings for parity testing (highest-impact first):**
- **`assignment_csat_form.assignment_id` is ambiguous** — it means an `Assignment` template id for rows from this module's own `store()`, but a `StudentAssignment` id for rows from `StudentFrontendEnrollment`'s separate student-facing `submit()` endpoint. `index()`'s `assignment_topic` display field only resolves correctly for the second kind of row, silently showing wrong data for the first.
- **`GET /v1/assignment-csat/reasons` is broken due to a route-to-method name mismatch**, not a missing implementation — the intended-looking method (`getAssignmentCSATFormReason`) exists and works, but only via a completely different route declared in `StudentFrontendEnrollment`'s route file, with a required path parameter this broken route doesn't provide.
- Both this module's `checkAvailable()` and `store()`'s duplicate-check share the "`Already Submitted` at HTTP 200 / `Elligable for Submission` misspelled at HTTP 201" pattern with `EvaluatorCSAT` — confirm which of the two CSAT modules a given integration is really targeting, since the shapes are similar enough to conflate by mistake despite different underlying tables/fields (`other` vs. `other_option`, string vs. integer `rating`).
- `graphIndex()` is a near-verbatim copy of `EvaluatorCSAT::graph_index()` — same 1–5 scale, same misnomer `totalEligible` key, same full-table-scan caution.
- CSV exports for this module, `Assignment`, and `StudentAssignment` all write to the same S3 prefix (`exports/tmp/assignments/`) — relevant for test cleanup/isolation.

**Cross-module coupling confirmed from this side:**
- **`StudentFrontendEnrollment`'s own route file is the actual entry point for the genuine student-facing Assignment-CSAT flow** (`GET`/`POST /student/v1/assignment-csat/{student_assignment}[/submit]`) — the GET half calls into this module's own controller/trait; the POST half is implemented in `StudentFrontendEnrollment`'s own, separately-named `AssignmentCSATController` class and writes the same table with different `assignment_id` semantics (see the critical finding above). Full detail on that POST endpoint's own validation/behavior belongs in `StudentFrontendEnrollment`'s documentation, not here.
- Also distinct from (not a rewrite of) the CSAT-bundled-into-submission flow on `POST /api/student/v1/student-my-courses/submit-assignment/{studentAssignment}` documented in `API_SPECIFICATIONS.md` §4 (a third, `StudentMyCourses`-module code path with its own `selectedOrderIds` comma-separated-string convention, distinct from this module's proper array) — a codebase with (at least) three independent code paths capable of writing to `assignment_csat_form` is a strong candidate for consolidation in AP-V3; a parity suite should enumerate and test all three separately rather than assuming one covers the others.

**Confidence:** High — every endpoint traced to its controller/trait method (or confirmed absent/misrouted) by reading the full controller, trait, both FormRequest classes, the resource, and the entity's dual relations on `assignment_id`; the cross-module routing discovery (`StudentFrontendEnrollment`'s route file) was confirmed by grepping for the orphaned-looking trait method's name across the entire `Modules/` tree rather than assuming it was simply dead.
