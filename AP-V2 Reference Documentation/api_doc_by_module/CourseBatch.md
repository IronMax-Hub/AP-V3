# CourseBatch Module API Documentation

The `CourseBatch` module owns the `course_batches` entity (admin CRUD, search, CSV export, activity log) plus two adjacent surfaces bolted onto the same module: `EdmingleBatch` (a course↔batch↔Edmingle-tutor mapping table) and an inbound **Course Calendar webhook receiver** (`CourseCalendarWebhookController`) that a separate scheduling sub-project calls to create/update/reschedule/cancel batches and read bootcamp/tutor reference data from this app.

See [`./_COMMON_CONVENTIONS.md`](./_COMMON_CONVENTIONS.md) for the app-wide response envelope styles, standard error shapes, and pagination conventions referenced below instead of being repeated per endpoint.

**Module-wide auth — three distinct groups in `Modules/CourseBatch/Routes/api.php`, not one:**
1. All `CourseCalendarWebhookController` routes (the `/v1/course-calendar/*`, `compare-batch-course-calender`, `search/course-batches-course-calender` routes) sit under `middleware(['json.response'])` only — **no Laravel auth guard at all** at the route level. Every action-mutating method on this controller (`handle`, `batchCreated`, `batchUpdated`, `batchCancel`, `getBootcamps`, `getBootcampsWithTitle`, `getEdmingleTutors`, `batchReschedule`) instead does its own **in-method** header check: `$request->header('X-Webhook-Secret') !== config('app.course_calendar_webhook_secret')` → `401`. This is a manual, per-method check, not middleware — **two methods on this same controller skip it entirely**: `compareBatchCourseCalender` and `searchCourseBatchesWithCourseCalender` have no secret check and no auth guard of any kind — genuinely open endpoints. Also note the secret is compared with `!==` (loose type-safe but not timing-safe `hash_equals`).
2. All `CourseBatchController` and `EdmingleBatchController` routes are `auth:sanctum` + `json.response`.
3. Both groups are mounted under prefix `v1` (via `Route::prefix('api')->middleware('api')` in `RouteServiceProvider`, same pattern as every other module).

All controllers extend `App\Http\Controllers\Controller` (so `$this->apiResponse()` is available) **except `EdmingleBatchController`, which extends the bare `Illuminate\Routing\Controller`** — it can only use the global `apiResponse()` helper function or hand-rolled `response()->json()`/plain arrays, never `$this->apiResponse()`. No controller in this module pulls logic in via a trait — all three controllers' methods are their own real bodies (`CourseBatchController` does `use ActivationAndDeactivationProcess;` from `App\Traits`, and `EdmingleBatchController` uses `App\Http\Traits\ActivityLog` — both are shared app-level traits, not module-local ones, invoked only for one helper method each).

## Course batches (`CourseBatchController`)

### `GET /api/v1/course-batches/{courseBatch}/logs` (route name `course-batches.logs`, controller `activityLogs`)
- Path param `courseBatch` — route-model-bound `CourseBatch`; a miss produces the standard `ModelNotFoundException` 404 (see conventions).
- Query: `rows` (optional int, default 15).
- **Success response:** `ActivityLogResource::collection($paginator)->additional(['meta' => ['next_page_url', 'prev_page_url', 'range' => {from,to,total}]])` — cursor-paginated (Laravel's own `cursor` paginator, not this app's custom base64-JSON cursor scheme used elsewhere in the module).

### `Route::apiResource('course-batches', 'CourseBatchController')`
- **`GET /api/v1/course-batches` (`index`)** — Query: `rows` (optional, default 15), `search`/`status` filters consumed by `CourseBatchesRepository::searchQuery()` (via `request('search')`/`request('status')`, read directly off the global request, not typed params). **Success response:** `CourseBatchResource::collection(...)->additional(['meta' => ['total','total_batch','total_active_batch','total_deactive_batch','range']])` — cursor-paginated via the module's own `calculateRangeForCursor()` (this app's standard base64-JSON `cursor` scheme; malformed cursor → `abort(500, 'Cursor value tempered')`, per common conventions). `total_batch` duplicates `total` under a second key.
- **`POST /api/v1/course-batches` (`store`)** — **Request body** (`StoreRequest`): `batch_date` required string, `date_format:M-d-Y`, **`unique:course_batches,batch_date`** (globally unique across the whole table, not scoped per-course — confirms the `API_SPECIFICATIONS.md` claim); `status` optional, one of `CourseBatch::STATUS_ACTIVE`(1)/`STATUS_PENDING`(0) — **note: this validated field is accepted but never actually used** — the controller hardcodes `'status' => CourseBatch::STATUS_ACTIVE` on create regardless of what (if anything) was submitted; `start_date`/`date_of_compilation` optional dates (`Y-m-d`), the latter must be `after:start_date`. Custom message on `batch_date.date_format`: `"The batch date must be in the format: e.g. - Jun-01-2026."`. **Success response:** `$this->apiResponse(['course_batch' => CourseBatchResource::make(...)], 'Course batch created successfully', statusCode: 201)`.
- **`PUT/PATCH /api/v1/course-batches/{id}` (`update`)** — **Request body** (`UpdateRequest`): `batch_id` required int `exists:course_batches,id` (**send both the path `{id}` and this body field** — the body field is what's actually used for the uniqueness-ignore, the path `$id` is used for the lookup); `batch_date` required, unique **ignoring** `batch_id`, `date_format:M-d-Y`, max:255; `start_date`/`date_of_compilation` same as Store. **Not present here at all: `status`** — this endpoint cannot change a batch's active/pending status (see the dedicated `status/change` endpoint below for that). **Error response:** `$this->apiResponse([], 'Course Batch Not Found', 'error', 404)` if `$id` doesn't resolve via the repository (a hand-checked 404, not route-model-binding). **Success response:** same `{course_batch: CourseBatchResource}` shape as store, message `"Course batch updated successfully"`, default 200.
- **`DELETE /api/v1/course-batches/{id}` (`destroy`)** — **Error responses:** `$this->apiResponse([], 'Course Batch Not Found', 'error', 404)`; `$this->apiResponse([], 'Can not delete Batch because it is associated with enrollments', 'error', 422)` if `enrollments()->count() > 0`. **Success:** `$this->apiResponse([], 'Course Batch deleted successfully')`. Repository `delete()` — verify directly whether this is a soft delete (`CourseBatch` uses `SoftDeletes`) or hard delete; not independently re-traced here beyond the controller/FormRequest layer.
- **`GET /api/v1/course-batches/{id}` (`show`) and non-existent `create`/`edit` actions** — `apiResource` wires 7 total routes (`index`,`create`,`store`,`show`,`edit`,`update`,`destroy`); `CourseBatchController` has **no `show`, `create`, or `edit` method at all** — calling `GET /api/v1/course-batches/{id}` or `GET .../create` or `GET .../{id}/edit` hits the "undefined method" fatal-error path (uncaught `Error`, surfaces as a raw 500, not a clean 404/405) — same failure mode documented for NPS's broken `apiResource` actions. Confirmed absent by reading the full controller.

### `POST /api/v1/course-batches/status/change` (route name `course-batches.status.change`, controller `changeStatus`)
- **Request params:** no FormRequest — inline `Validator::make($request->all(), [...])->validate()`: `batch_ids` required array, each `exists:course_batches,id` + `integer`; `comment` required string; `status` required, `in:activate,deactivate`.
- **Success response:** global `apiResponse([], 'course batches deactivated successfully'|'course batches activated successfully', statusCode: 200)` — **note this call uses the global function, not `$this->apiResponse()`, unlike this same controller's other methods** (style varies method-by-method within one controller, per the app-wide pattern).
- **Side effects:** bulk `UPDATE course_batches SET status = ...` for all `batch_ids`; `addActivityLogsAndComments()` (from `App\Traits\ActivationAndDeactivationProcess`) bulk-inserts one `Activity` row **and** one row into a `deactivating_comments`-style table (via `DeactivatingComment`) per batch id, using the submitted `comment` for every row.

### `GET /api/v1/search/course-batches` (route name `course-batches.search`, controller `search`)
- **Success response:** `SearchCourseBatchResource::collection($this->courseBatchesRepo->searchBatches())->additional(['meta' => ['total' => count(...)]])` → `{id, batch_date}` per row. `searchBatches()` reads from a `Cache::rememberForever('all_batches', ...)` cache of **all** batches (id + batch_date only), refreshed on every `CourseBatch` model `saved`/`deleted` event (see the model's `boot()`), then filters in-PHP by an optional `search` query param (substring match on `batch_date`) — **not a DB-level search**, so this endpoint's data is only as fresh as the cache invalidation hook; if that hook is ever bypassed (e.g. a raw `DB::table('course_batches')->update(...)`), results silently go stale.

### `GET /api/v1/search/specific-course-batches` (route name `course-batches.specific.search`, controller `searchBatchesWithArray`)
- Query: `search` (optional array of ids) — `whereIn('id', ...)`, run as a fresh DB query (not the cached path above).
- **Success response:** global `apiResponse($this->courseBatchesRepo->searchBatchesWithArray())` → `{"data": [{id, batch_date}, ...], "message": "Success", "status": "success"}`.

### `GET /api/v1/coursebatch/export` (unnamed route, controller `export`)
- **Request params:** inline `Validator::make($request->all(), ['data' => ['nullable','array']])->validate()`.
- **Success response:** global `apiResponse('', 'Batch Csv file exporting started')` → `data` is an empty **string**.
- **Side effects:** queues `BatchCSVDownload` (`default_medium` queue) with the raw request payload; the job builds a CSV (`Batch Id, Batch Name, Enrolled with this batch, Start Date, Batch Status`) from `CourseBatch::withSearchAndFilters(...)` (a model scope, filtered by whatever `search`/`status` was in the original request), uploads to S3 `exports/tmp/Batch/{filename}`, then **sends `BatchCSVCompletedMail` synchronously from within the job** (`Mail::to(...)->send(...)`, not `->queue(...)`) to the requesting user's email. Fire-and-forget from the endpoint's perspective — a parity test must wait for the email/S3 object, not the HTTP response, to confirm completion.

## Edmingle batches (`EdmingleBatchController`) — extends bare `Illuminate\Routing\Controller`, no `$this->apiResponse()` available

### `GET /api/v1/edmingle-batches/{edmingleBatch}/activity` (route name `edmingleBatch.activity`, controller `activity`)
- Path param `{edmingleBatch}` is a raw `$id` (**not** route-model-bound despite the `{edmingleBatch}` placeholder name — the method signature is `activity($id)`), looked up manually via `EdmingleBatch::withTrashed()->find($id)`.
- **Error response:** global `apiResponse([], 'EdmingleBatch Not Found', 'error', 404)` if not found (**including soft-deleted rows being found and NOT triggering this branch**, since the lookup uses `withTrashed()`).
- **Success response:** delegates to `App\Http\Traits\ActivityLog::logOfEdmingleBatch($id, ['id','description','causer_id','event','created_at'])` — cursor-paginated (Laravel `cursor` paginator) `ActivityResource::collection(...)->additional(['meta' => [next_page_url, prev_page_url, range]])`; filters `Activity` rows by `subject_type = 'Modules\CourseBatch\Entities\EdmingleBatch'` and `subject_id = $id`.

### `Route::apiResource('edmingle-batches', 'EdmingleBatchController')`
- **`GET /api/v1/edmingle-batches` (`index`)** — Query: `rows` (optional, default 15). **Success response:** `EdmingleBatchResource::collection(...)->additional(['meta' => ['total','total_batch','total_active_batch','total_deactive_batch','range']])`, same 4-key meta pattern as `CourseBatchController::index`, `range` from this controller's own (near-identical, copy-pasted) `calculateRangeForCursor()`. `EdmingleBatchResource` fields: `id`, `batch_date` (re-queried fresh from `CourseBatch` by `batch_id` — **1 extra query per row**, not eager-loaded), `course_name` (re-queried fresh from `Course` by `course_id` — likewise N+1), `tutorName`, `edmingleBatchName`, `status`.
- **`POST /api/v1/edmingle-batches` (`store`)** — **No FormRequest — raw `Request $request`, zero validation.** Any of `course_id`/`batch_id`/`edmingle_batch_id`/`tutor_id`/`tutor_name`/`edmingle_batch_name` can be omitted/malformed with no 422; a bad FK likely surfaces as a DB-constraint exception (uncaught, 500) rather than a clean validation error. **Duplicate guard:** if a row already exists with the same `course_id` + `batch_id`, returns `response()->json(['message' => 'Same Course Batch Already Exists, Please Try With Another Batch', 'status' => 'error'], 422)` — hand-rolled, no `data` key at all. **Success response:** global `apiResponse([], 'Edmingle Batch Added Successfully')` — **the created row itself is never returned**, `data` is always `[]`. **Side effects:** direct `Activity::create([...])` (not the `activity()` helper) with `causer_type: null` despite `causer_id` being set to the real auth id — an inconsistent causer pairing.
- **`DELETE /api/v1/edmingle-batches/{id}` (`destroy`)** — looked up via `withTrashed()->find($id)` (raw `$id`, not model-bound). **Error:** global `apiResponse([], 'Edmingle Batch not found', 404)` — **note the 4-arg `apiResponse($data, $message, $status, $statusCode)` signature is called with only 3 positional args here (`[]`, message, `404`)** — `404` lands in the **`$status` slot, not `$statusCode`**, meaning this response actually returns **HTTP 200** with a literal string `"status": 404` in the body, not a real 404 status code. This is a genuine bug worth a dedicated parity test (status-code assertion on this specific error path will fail if a client expects a real 404). **Success:** direct `Activity::create(...)` logged as a "Delete" event, then `$edmingleBatch->update(['status' => EdmingleBatch::DEACTIVE])` **and** `$this->edmingleBatchRepo->delete($id)` (both a status flip and a call to whatever the repository's own delete does — likely a soft delete given the model presumably uses `SoftDeletes`; not independently re-verified beyond this call site) — global `apiResponse([], 'Edmingle Batch deleted successfully')`.
- **`GET /api/v1/edmingle-batches/{id}` (`show`), `GET .../create`, `GET .../{id}/edit`, `PUT/PATCH /api/v1/edmingle-batches/{id}` (`update`)** — **Dead `apiResource` scaffolding, not real APIs:** `create`/`show`/`edit` each `return view('coursebatch::create'|'show'|'edit')` (Blade views, non-functional as JSON endpoints per the common structural traps); `update(Request $request, $id)` has a **fully empty body** (`//` only) — calling it does nothing and returns an empty `200` response (Laravel's default for a controller method with no return value), not an error.

## Course Calendar webhook receiver (`CourseCalendarWebhookController`) — inbound integration surface, `json.response` only, no auth guard

Every mutating method below manually checks `X-Webhook-Secret` against `config('app.course_calendar_webhook_secret')` and returns `$this->apiResponse([], 'Unauthorized', 'error', 401)` on mismatch — this is the *only* authentication for this sub-surface. Treat it as an **External call inbound** boundary: shape/trust here is dictated by whatever the course-calendar sub-project actually sends, not by a FormRequest on this side (all validation is inline `Validator::make()`, not FormRequest classes).

### `POST /api/v1/course-calendar/batch-sync` (route name `course-calendar.batch-sync`, controller `handle`)
- **Request body:** `batch_name` required string `date_format:M-d-Y`; `course_id` required int `exists:courses,id`; `start_date`/`date_of_compilation` optional dates; `status` optional `in:0,1`; `edmingle_batches` optional array of `{course_id (required, exists:courses), edmingle_batch_id, tutor_id, tutor_name, edmingle_batch_name}`.
- **Behavior:** upserts a `CourseBatch` by `batch_date` (update if a row with that `batch_date` exists, else create), always stamping `course_calendar_map = 1`; cascades `course_calendar_map = 1` onto every `Enrollment` with that `batch_id`; for each `edmingle_batches[]` entry, `updateOrCreate`s an `EdmingleBatch` row (keyed on `batch_id`+`course_id`) and dispatches either `CourseCalendarCreateEdmingleBatchJob` (if no `edmingle_batch_id` supplied — creates the batch on Edmingle's side first) or `CourseCalendarAssignStudentsToEdmingleBatchJob` (if one was supplied) on `default_high`; writes `Activity::create()` rows for both the `EdmingleBatch` sync and the batch create/update itself.
- **Success response:** `$this->apiResponse(['course_batch' => $batch->load('edminlgeBatch'), 'edmingle_id' => ...], $message, statusCode: $existing ? 200 : 201)` — note the response embeds the **raw Eloquent model**, not a Resource.
- **Error responses:** `422 {"errors": {...}, ...}` standard-style via `$this->apiResponse(['errors' => $validator->errors()], 'Validation failed', 'error', 422)` (this is a hand-built shape, not Laravel's automatic `ValidationException` rendering — `data.errors` here vs. the app-wide convention's identical-looking but auto-generated shape).

### `POST /api/v1/course-calendar/batch-created` (`batchCreated`) and `POST /api/v1/course-calendar/batch-updated` (`batchUpdated`)
- Similar upsert-by-`batch_name` pattern to `handle` above but **narrower validation** (`batch_name` here is just `required|string`, no `date_format` constraint — inconsistent with `handle`'s stricter rule for what should be the same field) and adds an `is_draft` flag sourced from `edmingle_batches.0.is_draft` (first array element only, not looped). `batchUpdated` **requires** `edmingle_batches` (not optional) and additionally requires `edmingle_batches.0.edmingle_batch_id` to already `exist:edmingle_batches,edmingle_batch_id` — i.e., this endpoint can only "update" a batch that already has at least one real Edmingle mapping; a genuinely new batch must go through `batch-created` or `batch-sync` first. `batchUpdated`'s "no changes detected" branch (`$shouldSyncEdmingle === false`) still returns 200 success (`"No changes detected, nothing synced"`) — a semantic no-op reported as success, worth flagging per the common cross-cutting QA caution.
- **Error (`batchUpdated` only):** `$this->apiResponse([], 'No batch found matching batch_name "..."', 'error', 404)` if no `CourseBatch` row matches `batch_name` — **`batchCreated`/`handle` have no equivalent "not found" path since they always create-if-missing.**
- **Side effects:** same Edmingle sync-job dispatch pattern as `handle`; `batchUpdated`'s actual Edmingle-side sync (`updateEdmingleBatchOnEdmingle` — a synchronous two-call GET-then-POST to the live Edmingle API from inside the request) is a **real external call made in-request**, not queued — a slow/failing Edmingle response here directly slows/fails this webhook call. On Edmingle failure it silently sets `edmingle_sync_status = 0` + `edmingle_failed_step` on the batch and returns/logs — **the HTTP response to the calling webhook can still be a 200 success even though the downstream Edmingle sync failed**, since the calling code path doesn't check this before building its own success response in some branches (verify per exact branch if building a parity test around Edmingle-failure scenarios).

### `POST /api/v1/course-calendar/batch-cancel` (route name `course-calendar.batch-cancel`, controller `batchCancel`)
- **Request body:** `informe_to_student` optional (no type rule at all — `nullable` only); `batch_name` required, must `exists:course_batches,batch_date`; `course_id` required `exists:courses,id`.
- **⚠️ Note: the actual cancellation write is commented out in source** (`// $batch->update(['status' => CourseBatch::STATUS_PENDING]);` and its accompanying `Activity::create()` are both dead, commented-out code) — **the batch's own `status` is never actually flipped to `PENDING` by this endpoint**, despite the endpoint being named/intended for batch cancellation and despite an early check (`if ($batch->status === CourseBatch::STATUS_PENDING) return "Batch is already cancelled"`) implying that flip is supposed to happen. What **does** happen: every active (`status != PENDING`) `Enrollment` for that `batch_id` + `course_id` is individually set to `Enrollment::PENDING` (deactivated) and logged, `EnrollmentDeactivationJob` + (if `informe_to_student` truthy) `CourseCalendarBatchCancelledNotificationJob` + `StudentRemoveJob` are dispatched, and `SyncEnrollmentWithCourseCalendarJob` fires for the first affected enrollment only (`default_medium`). **A parity test asserting the `CourseBatch.status` changes after this call will fail** — only enrollment-level cancellation actually happens; this is a genuine dead-code / naming-vs-behavior mismatch, preserve it exactly.
- **Success response:** `$this->apiResponse(['course_batch' => $batch->fresh(), 'deactivated_enrollments' => count, 'edmingle_id' => ...], 'Batch cancelled and N enrollment(s) deactivated successfully')`.

### `POST /api/v1/course-calendar/batch-reschedule` (route name `course-calendar.batch-reschedule`, controller `batchReschedule`)
- **Request body:** `old_course_id` required `exists:courses,id`; `new_course_id` optional `exists:courses,id` (defaults to `old_course_id` if omitted); `old_batch_name`/`new_batch_name` required strings; `start_date`/`date_of_compilation` optional dates; `edmingle_batches` optional array (same per-item shape as above).
- **Behavior:** looks up the old batch by `batch_date` **scoped to have an `EdmingleBatch` mapping for `old_course_id`** (`whereHas('edminlgeBatch', ...)`) — 404 (`'No batch found matching old_batch_name "..." for old_course_id ...'`) if none. The new batch is then either reused (if a matching `CourseBatch`+`EdmingleBatch`-for-`newCourseId` combo already exists) or `firstOrCreate`d by `batch_date` alone. Dispatches a `Bus::batch()` of one `CourseCalendarBatchRescheduleJob` per actively-enrolled student on the old batch (`allowFailures()`), chained via `->finally()` to `CourseCalendarBulkBatchRescheduleJob`; optionally (`informe_to_student`) also dispatches `CourseCalendarBatchRescheduledNotificationJob`.
- **Notes:** contains **~15 `Log::info('just checking the line ...')` debug statements** left in production source (every few lines) — clearly leftover debugging instrumentation, not intentional structured logging; harmless to behavior but worth knowing the log volume this endpoint generates. A commented-out earlier `CourseBatch::create(...)` block sits directly above the live `firstOrCreate(...)` call — dead code, not a second code path.
- **Success response:** `$this->apiResponse(['course_batch' => ..., 'edmingle_id' => ...], 'Batch reschedule has been queued successfully')` — note the message says "queued" even on the branch where the new batch already existed and no `Bus::batch()` re-dispatch semantics differ; the actual per-student reschedule work is genuinely async either way (`Bus::batch` + queued jobs).

### `GET /api/v1/course-calendar/edmingle-tutors` (`getEdmingleTutors`) — **External call**
- Query: `search` optional, forwarded verbatim to Edmingle's `organization/tutors` endpoint.
- **Behavior:** live synchronous `Http::get()` to `env('EDMINGLE_API_ENDPOINT') . 'organization/tutors'` with `apikey`/`ORGID` headers. Response shape is whatever Edmingle returns under its `tutors` key — **External call**, not this app's contract. `!$response->successful()` → `$this->apiResponse([], 'Failed to fetch tutors from Edmingle', 'error', $response->status())` (passes through Edmingle's own status code). Empty/missing `tutors` key → success with `{"data": []}`, message `"No tutors found"` (2xx, not an error, despite finding nothing).

### `GET /api/v1/course-calendar/bootcamps` (`getBootcamps`) and `GET /api/v1/course-calendar/bootcamps-with-title` (`getBootcampsWithTitle`)
- Query: `search` optional (LIKE on `id`/`name`, and additionally `title` for the `-with-title` variant).
- **Success response:** `$this->apiResponse(['data' => $bootcamps], 'Bootcamps fetched successfully')` — local DB read of `Bootcamp` (not an external call, despite living in this webhook controller), `{id, name}` or (for `-with-title`) `{id, name: "{name} - {title}"}` filtered to `title` non-null/non-empty.

### `GET /api/compare-batch-course-calender` (route name `course-calendar.compare-batch`, controller `compareBatchCourseCalender`) — ⚠️ **no webhook-secret check at all**
- **Request params:** inline `$request->validate(['batch_name' => 'required', 'course_id' => 'required|exists:courses,id|integer'])` — this one DOES use Laravel's automatic `validate()` (so a real `ValidationException`/422 on failure, unlike every sibling method's manual `Validator::make()`), but has **zero authentication of any kind** — this endpoint is reachable by anyone who can reach the app, not even the shared-secret header is checked (confirmed by reading the full method body — no `X-Webhook-Secret` comparison exists here, unlike every other method on this same controller).
- **Success response:** hand-rolled `response()->json(['status' => 1, 'data' => {start_date, date_of_compilation}], 200)` if a matching `EdmingleBatch` mapping exists for that batch+course; `response()->json(['status' => 2, 'data' => {...}], 200)` if the `CourseBatch` exists but no `EdmingleBatch` mapping does; `response()->json(['status' => 3], 200)` if no `CourseBatch` matches at all (**note: no `data` key on this third branch**). All three are HTTP 200 — **the numeric `status` field (1/2/3) is the only way to distinguish these three outcomes**, not the HTTP status code or any `message`/`error` field.

### `GET /api/search/course-batches-course-calender` (route name `course-batches.search`, controller `searchCourseBatchesWithCourseCalender`) — ⚠️ **also no webhook-secret check**
- **Success response:** identical to `CourseBatchController::search()` above — `SearchCourseBatchResource::collection($this->courseBatchesRepo->searchBatches())->additional(['meta' => ['total' => count(...)]])`, same all-batches cache-backed listing. **This is a literal duplicate implementation of the exact same underlying repository call as `GET /api/v1/search/course-batches`** (documented under `CourseBatchController` above), just reachable with no auth guard instead of `auth:sanctum` — an unauthenticated caller can reach this same data via this route even though the "equivalent" route requires a Sanctum token.

## Summary

**19 `Route::` declarations** in `Modules/CourseBatch/Routes/api.php`, resolving to (`apiResource` expands to 7 routes each for `edmingle-batches`/`course-batches`, but several of those are dead — see below):
- **CourseBatchController:** `index`, `store`, `update`, `destroy`, `search`, `searchBatchesWithArray`, `changeStatus`, `activityLogs`, `export` — 9 live endpoints. `show`/`create`/`edit` from its `apiResource` are **fatal-error stubs** (undefined method, 500).
- **EdmingleBatchController:** `index`, `store`, `destroy`, `activity` — 4 live endpoints (one, `store`, with zero input validation). `show`/`create`/`edit` are **dead Blade-view stubs**; `update` is a **fully empty no-op stub**.
- **CourseCalendarWebhookController:** 10 live endpoints, of which 8 do their own manual webhook-secret check and 2 (`compareBatchCourseCalender`, `searchCourseBatchesWithCourseCalender`) have **no authentication of any kind**.

**Notable bugs/discrepancies found:**
1. `EdmingleBatchController::destroy`'s error response passes `404` into the `$status` parameter slot instead of `$statusCode` (`apiResponse($data, $message, $status, $statusCode)` called with only 3 args) — the response is actually **HTTP 200** with `"status": 404` in the body, not a real 404.
2. `CourseBatchController::store` validates and accepts a `status` field that is **silently discarded** — every new batch is hardcoded `STATUS_ACTIVE` regardless of input.
3. `CourseCalendarWebhookController::batchCancel`'s actual `CourseBatch.status` flip to cancelled is **dead, commented-out code** — the endpoint deactivates enrollments but never cancels the batch itself, despite its name and an early-exit check that assumes it does.
4. Two webhook-controller endpoints (`compareBatchCourseCalender`, `searchCourseBatchesWithCourseCalender`) have no auth of any kind, unlike every sibling method on the same controller — likely an oversight, not by design (worth flagging to the team).
5. `compareBatchCourseCalender`'s three-way outcome is distinguishable only by a numeric `status: 1|2|3` field at HTTP 200 in all cases — no status-code-based detection possible.
