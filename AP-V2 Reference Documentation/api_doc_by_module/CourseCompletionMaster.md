# CourseCompletionMaster Module API Documentation

The `CourseCompletionMaster` module is the admin-side surface for computing and reviewing per-enrollment course-completion status: a rich listing endpoint (completion %, exercise-submission ratios, MCQ status), the pass/fail marksheet calculation itself, PDF certificate generation/removal, a manual "send completion email" action, and a CSV export. It reads/writes the `enrollments` table directly (via `Modules\Enrollment\Entities\Enrollment`) rather than owning its own primary entity — there is no `CourseCompletionMaster` Eloquent model backing a dedicated table.

**Module-wide auth:** every route in `Modules/CourseCompletionMaster/Routes/api.php` is `auth:sanctum` + `json.response`, mounted under `/api/v1/...` (standard `prefix('api')->middleware('api')` wrapping). No route deviates from this.

See [`./_COMMON_CONVENTIONS.md`](./_COMMON_CONVENTIONS.md) for the app-wide response envelope styles, standard error shapes, and pagination conventions referenced below instead of being repeated per endpoint.

`CourseCompletionMasterController` (`Modules/CourseCompletionMaster/Http/Controllers/CourseCompletionMasterController.php`) extends the bare `Illuminate\Routing\Controller` (no `$this->apiResponse()` available) and defines only `index()` directly; every other routed method (`export`, `generateCertificate`, `marksheetCalculation`, `sendEmail`, `removeCertificate`) lives in `CourseCompletionMasterTrait` (`Modules/CourseCompletionMaster/Http/Traits/CourseCompletionMasterTrait.php`), pulled in via `use CourseCompletionMasterTrait;`. A second trait, `CourseCompletionMasterHelpers.php`, also exists in this module's `Http/Traits/` directory but is **not used by this controller at all** — grep confirms its only consumers are `StudentFrontendEnrollment`'s `PackageEnrollmentsResource`/`BootcampEnrollmentsResource`, a different module entirely; it has no bearing on any endpoint documented here.

## ⚠️ `apiResource('course-completion-master', ...)` is almost entirely broken — same failure class as NPS

```php
Route::apiResource('course-completion-master', 'CourseCompletionMasterController');
```
This wires up `index`, `store`, `show`, `update`, `destroy`. **Only `index` is implemented** (directly on the controller, described below). `store`, `show`, `update`, and `destroy` exist nowhere in the controller or either trait — confirmed by reading both trait files and the controller in full. Calling any of:
- `POST /api/v1/course-completion-master`
- `GET /api/v1/course-completion-master/{course_completion_master}`
- `PUT`/`PATCH /api/v1/course-completion-master/{course_completion_master}`
- `DELETE /api/v1/course-completion-master/{course_completion_master}`

hits a PHP `Error: Call to undefined method` at dispatch — an uncaught-exception **500**, not a clean 404/405. A parity suite must confirm whether the AP-V3 migration intends to keep this broken or fix it; do not assume either without confirming with the team.

## `GET /api/v1/course-completion-master/export` (route name `course-completion-master.export`, trait `export`)
- **Success response:** global `apiResponse('', 'Course Completion Master Csv file exporting started', 'success')` → `{"data": "", "message": "...", "status": "success"}` — `data` is an empty **string**, not `[]`/`null`.
- **Side effects:** dispatches `CourseCompletionMasterCSVExport::dispatch($request?->user(), $request?->all())` onto the `default_high` queue — **fire-and-forget**, the entire filtered enrollment set (`course_id`, `course_batch_id`, `enrollment_code`, `course_category`, `min_percent`/`max_percent`, `start_date`/`end_date`, `course_expiry_start_date`/`course_expiry_end_date`, `student_id`, `completed_passing_criteria`, `check_lms_mcq`, `search` — all read straight off the whole request body/query with no FormRequest validation) is passed through verbatim into the job's filter logic. On completion: writes a CSV to S3 (`exports/tmp/course-completion-master/{filename}`), sends the requesting user a `CourseCompletionMasterCsvExportingCompletedNotification` and queues `CourseCompletionMasterCSVCompletedMail`. The job wraps its entire `handle()` body in a try/catch that only `Log::error(...)`s on failure — **a failed export never surfaces to the user in any way** (no failure email/notification), it just silently never arrives.

## `GET /api/v1/course-completion-master/generate-certificate/{enrollment}` (route name `course-completion-master.generate-certificate`, trait `generateCertificate`)
- Route-model-bound `{enrollment}` — a `ModelNotFoundException` (standard 404 shape) if it doesn't resolve.
- **Behavior:** computes a letter grade from `enrollment->current_percent` — confirmed exact thresholds from source: **A+** ≥90, **A** 80–89 (`>=80 && <90`), **B+** 70–79, **B** 60–69, **C+** 50–59, **C** 40–49, and **no grade at all below 40** — `$grade` stays its initialized value of the **empty string `''`** (not `null`, not `'F'`) for any `current_percent` under 40. Renders a `certificate` Blade view to PDF via `PDF::loadView(...)` (data: `CN_number` — random `'LS-' . rand(10001, 99999)`, not derived from the enrollment; `enrollment_code`, `full_name`, `course`, `completion_date` (`enrollment->completed_at`, raw — no reformatting), `platform_name: "LawSikho"`, `date_of_issue` (today, `F j, Y`), `grade`), landscape A4, uploads to S3 at `uploads/enrollments/certificates/{student_id}_{time()}.pdf`.
- **Side effects:** direct `Enrollment::query()->where('id', ...)->update([...])` (bypassing the repository layer entirely) setting `certificate_file` (the new S3 URL), `is_certified` → `Enrollment::CERTIFIED`, `certified_by` → `auth()->user()->id`, `certified_datetime` → `now()`. **No domain/webhook event fires** — `triggerEventForGenerateCertificate()` exists in the same trait as a fully-built method (constructs a `WebhookTriggered` event payload) but its call is commented out (`// $this->triggerEventForGenerateCertificate(...)`) — dead code, confirmed by reading the exact line; do not expect any webhook/event side effect from this endpoint despite the helper method's presence.
- **Success response:** a **plain returned array** (not `response()->json()`, not `apiResponse()`): `{"data": {"download_file": "<s3 url>"}, "message": "Certificate Generated Successfully", "status": "success"}` — HTTP 200 always (plain-array return gives no status-code control). Also note a fully dead, commented-out earlier implementation (a `DEMO-` prefixed `CN_number`, a portrait-orientation `PDF::loadView('certificate', $data)` with a different field set including `father_name`/`gender`/`student_image`) sits directly above the live code as comments — not executed, ignore it.

## `GET /api/v1/course-completion-master/marksheet_calculation/{enrollment}` (route name `course-completion-master.marksheet_calculation`, trait `marksheetCalculation`)
- Route-model-bound `{enrollment}`.
- **⚠️ Definitively confirmed response shape (previously flagged as unverified in `API_SPECIFICATIONS.md`):**
  - If `json_decode($enrollment->passing_criteria)` is `null` (no criteria set, or malformed JSON): `apiResponse([], 'No criteria found', 403)`.
    - **This call itself is buggy.** `apiResponse`'s real signature is `apiResponse($data, string $message = 'Success', string $status = 'success', int $statusCode = 200)`. The call here passes `403` as the **third** positional argument, which binds to `$status` (coerced from `int` to the `string` `"403"` — no `strict_types` declared in this file), **not** `$statusCode`. The result: HTTP status stays the default **200**, and the JSON body is literally `{"data": [], "message": "No criteria found", "status": "403"}` — `status` is the string `"403"`, not `"error"`, and the HTTP layer never reports a 403 at all. **A parity test asserting an actual HTTP 403 here will fail against current behavior; the real contract is 200 with `status: "403"` in the body.**
  - Otherwise, the method returns whatever `$this->enrollmentRepo->update($enrollment->id, [...])` returns, and that return value **is the entire HTTP response body** — no wrapping envelope, no `apiResponse()`, no `response()->json()` call at all. `EnrollmentRepository` does not override the generic `update()` it inherits from `BaseRepository`, whose implementation is `return $this->model::query()->find($id)?->update($attributes);` — this is `Illuminate\Database\Eloquent\Model::update()`, which returns a **plain PHP boolean**. **Confirmed: the success response body is the literal JSON boolean `true`** (or in principle `false`/`null`, though `find($id)` cannot fail here since `$enrollment` was already resolved by route-model binding). There is no `current_percent`/`completed`/marksheet object of any kind in this response — a client must re-fetch the enrollment afterward to observe the computed values.
- **Side effects (fields written to the `enrollments` row, via `EnrollmentRepository::update()`, bypassing any Resource/validation layer):**
  - Bootcamp enrollments with a matching `CourseCriteria` row for a `BOOTCAMP_COURSE`-typed course: `current_percent`, `subjective_passing_percent`, `written_passing_percent`, `completed` (0 or 1), `is_passing_condition_added` (always set to `1`) — plus `completed_at` (only set, once, the first time `completed` becomes `1` and `completed_at` was previously `null`; a **separate** `update()` call from the main one, so two DB writes happen on a first-time pass).
  - Bootcamp enrollments **without** a matching `CourseCriteria` row (`$bootcampCriteria` falsy): a narrower fallback branch writes `current_percent`, `subjective_passing_percent`, `written_passing_percent` (hardcoded `0`), `completed`, `is_passing_condition_added` — using only the subjective-score math (no written-assignment component at all in this branch).
  - Non-bootcamp enrollments with a non-null `passing_criteria`: same five fields, using a combined subjective+written scoring path gated on `criteria[0]->totalWrittenAssignment` / `criteria[0]->totalMarks` / `criteria[0]->minTotalPassPercent` / `criteria[0]->wittenPassPercent` (note this **exact misspelling `wittenPassPercent`**, not `writtenPassPercent`, is the literal JSON key this code reads from the `passing_criteria` blob — preserve it if constructing test fixtures).
  - If `passing_criteria` is present but the enrollment falls through all three branches (none of the `if` conditions match, e.g. a non-bootcamp enrollment somehow reaching the final block with `passing_criteria` empty-string rather than null — the final `if ($enrollment->passing_criteria != null || $enrollment->passing_criteria != '')` is **always true** since `!=` against two different values with an `||` can never both be false for any single string — dead/no-op guard, effectively unconditional), the method implicitly returns `null` (no `return` statement reached) — **response body would be the JSON value `null`**, not a boolean, in this unreachable-in-practice edge case.
- **Notes:** All marks/percent math divides by `criteria[0]->subjectiveTotalMark`/`totalMarks`/`writtenTotalMarks` with `!= 0` guards in most but not all branches (the bootcamp-with-criteria branch's `($totalWriScore * 100) / $writtenTotalMarks` and `($totalSubScore * 100) / $criteria[0]->subjectiveTotalMark` divisions have **no zero-guard** — a `DivisionByZeroError`/`INF` risk if `no_writing_assignments`/`writing_assignments_marks`/`subjectiveTotalMark` end up `0`, surfacing as an uncaught 500 or a silently-stored `INF`/`NAN` value depending on PHP's float-division behavior). Worth a boundary test with zero-valued criteria fields.

## `POST /api/v1/course-completion-master/{enrollment}/send/email` (route name `course-completion-master.send-email`, trait `sendEmail`)
- **Request body** (`SendEmailRequest`, `authorize()` always `true`): `mail_body` — required (no type/format constraint beyond presence).
- **Success response:** global `apiResponse([], 'Email sent to student')` → `{"data": [], "message": "Email sent to student", "status": "success"}`, HTTP 200.
- **Side effects:** queues a `CourseCompletionEmail` mailable to `enrollment->student->email`, with `bodyData` (`name`, `course_name`, `batch_name` — null-safe `enrollment?->batch?->batch_date`, `enrollment_code`, `student_name` — duplicate of `name`, both `full_name`) and the caller-supplied `mail_body` as the free-text body content. No null-check on `enrollment->course`/`enrollment->student` themselves (only `batch` is null-safe) — an enrollment somehow missing its course/student relation would 500 here, not error cleanly.

## `GET /api/v1/course-completion-master/remove-certificate/{enrollment}` (route name `course-completion-master.remove-certificate`, trait `removeCertificate`)
- **Behavior:** the inverse of `generateCertificate` — direct `Enrollment::query()->where('id', ...)->update([...])` setting `certificate_file` → `null`, `is_certified` → `Enrollment::NOT_CERTIFIED`, `certified_by` → `null`, `certified_datetime` → `null`. **Does not delete the actual PDF file from S3** — only clears the DB pointer to it; the object remains in the bucket.
- **Success response:** global `apiResponse([], 'Certificate Removed Successfully')`, HTTP 200. **Notable:** this is a `GET` route performing a destructive write — no CSRF/idempotency concern given the `auth:sanctum` API context, but worth flagging as an unusual verb choice for a state-mutating action.
- **Notes:** this route being a plain `GET` means it's also trivially triggerable by a pre-fetch/link-scanner or browser prefetch if ever exposed client-side without care — a genuine (if narrow) accidental-side-effect risk specific to `GET`-verb mutations.

## `GET /api/v1/course-completion-master` (route name resolved via `apiResource`, controller `index`) — the only working `apiResource` action
- Query: `rows` (optional int, default 15) — the only param read directly (`request()?->has('rows')`); all the *filter* params (`course_batch_id`, `course_id`, `course_category`, `enrollment_code`, `min_percent`/`max_percent`, `start_date`/`end_date`, `course_expiry_start_date`/`course_expiry_end_date`, `student_id`, `enrollment_status`, `completed_passing_criteria`, `check_lms_mcq`, `search`) are consumed only by the **export** job's own query builder (`getCourseCompletionMaster()` in `CourseCompletionMasterCSVExport`), not by this listing endpoint's own repository call (`allWithSearch`) — the two surfaces (`index` and `export`) do **not** share one query-building method despite both nominally listing/filtering the same enrollment set; verify independently whether `index()`'s own `allWithSearch()` repository method actually honors the same filter parameters (not traced here — check `CourseCompletionMasterRepository::allWithSearch()` directly before assuming filter parity between the two endpoints).
- **Success response:** `CourseCompletionMasterResource::collection($this->courseCompletionMasterRepo->allWithSearch(['*'], ['student','course','batch','edmingleBatch' => fn(...) => ...], $rows))->additional(['meta' => ['total' => ..., 'range' => $this->calculateRangeForCursor($rows)]])` → resource-collection + cursor-range shape, `{"data":[...], "meta":{"total":N,"range":{"from":N,"to":N,"total":N}}}`. `calculateRangeForCursor()` uses this module's own base64-JSON `cursor` query-param implementation (same family as documented in common conventions) — malformed cursor → `abort(500, 'Cursor value tempered')`.
- **`CourseCompletionMasterResource`** (operates on raw `Enrollment` rows, not a dedicated entity) — key fields: `id`, `current_percent`, `is_certified`, `certificate_file`, `course_expiry_date`, `mcq_completed`, `mcq_score` (raw passthrough); `bootcamp_name` (from `bootcamp_display_name`); `enrollment_status` (from `status`); `enrollment_type` (computed string: `'Package With Batch'` / `'Standard'` / `'Package'` / `'Bootcamp'`, based on `type`/`bootcamp_id`/`package_id`); `created_at` (`Y-m-d H:i:s`); `enrollment_at` (from `enrollment_code_created_at`); `student` (`{id, full_name, email, phone, country_code}`); `course` (`{id, course_name}`); `batch` (`{id, batch_date}` or `null`); `submission_subjective_exercise`/`submission_written_exercies` (note the literal misspelling **"exercies"**, preserve exactly — both formatted strings `"{done}/{outOf}({pct}%)"`, `"0/0(0.00%)"` if the denominator is `<= 0`); `project_id` (cross-module lookup into the deprecated `ProjectManagement` module's `ProjectRepository`); `mcq_valid` (`'Y'` or `null`, from decoded `passing_criteria`); `completed` (a **human-readable status string**, not a boolean — `'Completed'` / `'Student has completed pass criteria,Check LMS MCQ status & Confirm'` / `'Not Completed'`, computed from `completed`+`mcq_completed`+decoded `passing_criteria.lms_mcq`); `class_details` (nested `{total, attended, absent, attendence_persent, absence_persent}` — note the literal misspellings **"attendence_persent"**/no equivalent typo on absence, both preserved exactly — or `null` if `total` is falsy); `edmingle_batch_name`; `more_info` (a long human-readable HTML-fragment string built from multiple criteria comparisons, empty string `''` if neither subjective nor written criteria apply).
- **⚠️ Resource resolves controller instances out of the container mid-serialization**, same pattern flagged in other modules' docs: `app(CourseCompletionMasterController::class)->getSubjectiDoneByStudent(...)` / `getClassDetailsForListing(...)` / (indirectly) `getWrittenDoneByStudent(...)` are called from inside `CourseCompletionMasterResource::toArray()` — a fresh controller instance (with its own constructor-injected repositories) is resolved from the container **per resource item**, not passed in as plain data. This is expensive (repo instantiation per row) and couples the Resource class to the Controller class in a way that would complicate a clean AP-V3 reimplementation — flag as a structural smell, not just a naming quirk.
- **`MarksCalculationResultsResource`** (`Http/Resources/MarksCalculationResultsResource.php`) exists in this module but is **confirmed orphaned** — grep across the entire codebase finds zero references to it outside its own class definition. Not wired to any route or resource call; do not describe it as a live response shape for any endpoint.

## Summary

**Routes documented:** 6 `Route::` declarations (`export`, `generate-certificate/{enrollment}`, `marksheet_calculation/{enrollment}`, `{enrollment}/send/email`, `remove-certificate/{enrollment}`, plus the 5-action `apiResource('course-completion-master', ...)`) = **10 total registered actions**, of which:
- **6 working, fully documented above** (`export`, `generateCertificate`, `marksheetCalculation`, `sendEmail`, `removeCertificate`, `index`).
- **4 confirmed broken** (`apiResource`'s `store`/`show`/`update`/`destroy` — undefined method, fatal 500 on call, same class of bug as `NPS`'s broken `apiResource` actions).

**Notable findings for parity testing:**
- **`marksheetCalculation`'s "No criteria found" branch is a genuine `apiResponse()` misuse bug** — the intended 403 never reaches the HTTP layer; the real response is HTTP 200 with body `{"data": [], "message": "No criteria found", "status": "403"}`. This is a headline, high-confidence finding independently re-derived from `apiResponse()`'s actual signature, not just repeated from the prior spec's flagged-as-uncertain note.
- **`marksheetCalculation`'s success response is a bare JSON boolean** (`true`), not an object — confirmed by tracing `EnrollmentRepository::update()` through to `BaseRepository::update()` and Eloquent's `Model::update()` return type. This resolves the "not confirmed empirically" caveat in `API_SPECIFICATIONS.md` definitively.
- `generateCertificate`'s webhook-event trigger is dead code (call commented out) — no event fires despite the fully-implemented helper method sitting right next to the live code.
- `removeCertificate` is a `GET` route with a destructive side effect (clears certificate DB fields, does not delete the S3 object).
- The `index` listing and the `export` job build their filter query independently — filter-parameter parity between the two is **not verified** here and should be checked directly against `CourseCompletionMasterRepository::allWithSearch()` before assuming they return the same filtered set.
- `MarksCalculationResultsResource` is dead/orphaned code, not wired to anything.
- `CourseCompletionMasterResource` resolves a fresh `CourseCompletionMasterController` instance from the container per row during serialization — a performance and coupling smell worth flagging for the AP-V3 rewrite, separate from pure behavioral parity.

**Confidence:** High for all documented shapes — traced directly from the controller, `CourseCompletionMasterTrait.php` (read in full), `CourseCompletionMasterResource.php` (read in full), `SendEmailRequest.php`, `BaseRepository.php`, and `EnrollmentRepository.php`. The `apiResponse()` positional-argument bug and the boolean-return resolution for `marksheetCalculation` were independently verified against exact source lines and the helper function's real signature, not inferred from naming or prior documentation.
