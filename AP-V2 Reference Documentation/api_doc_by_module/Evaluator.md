# Evaluator Module — API Documentation

The `Evaluator` module is a **read-mostly reporting surface over `App\Models\User` rows that hold the `evaluator` or `admin` Spatie role** — it does not manage its own distinct "evaluator" entity despite having one defined (see the dead-entity finding below), and it performs no evaluator-*assignment* logic itself (that lives entirely in `Result` — see `Result.md`'s `assignEvaluatorSingle`/`assignEvaluatorRoundRobin`, confirming `API_SPECIFICATIONS.md` §4's characterization of this module as "read-mostly master data"). See [`./_COMMON_CONVENTIONS.md`](./_COMMON_CONVENTIONS.md) for app-wide envelope/error/pagination conventions.

**Module-wide auth:** every route in `Modules/Evaluator/Routes/api.php` is `auth:sanctum` + `json.response`, prefix `v1`. No per-route deviation.

**Class layout:** `EvaluatorController` implements only `index()` directly; `use`s `EvaluatorTrait` for `export()`/`evaluatorsResultsDashboardData()`/`calculateRangeForCursor()`.

## ⚠️ `Modules\Evaluator\Entities\Evaluator` is confirmed dead code — this module's own Eloquent entity is never instantiated anywhere
`EvaluatorRepository`'s constructor is type-hinted `App\Models\User $model`, not the module's own `Evaluator` entity — every query in this module (`index()`, `export()`, the dashboard) runs against the `users` table filtered by role, never against whatever table the `Evaluator` model would back. Grepped the full `Modules/` and `app/` trees for any reference to `Modules\Evaluator\Entities\Evaluator` outside its own file — none found. If a parity test needs to enumerate/seed "evaluators," it must create `User` rows with the `evaluator` (or `admin`) role, not rows via this module's own entity class.

## Core CRUD (`Route::apiResource('evaluator', 'EvaluatorController')`) — only `index()` is real; the other 4 actions are confirmed broken

### `GET /v1/evaluator` — `index()` (controller)
- Query params (all optional, applied via the shared `EvaluatorRepository::searchQuery()` used by every method in this module): `rows` (default 15); `evaluator_id` (int or array, `whereIn('id', ...)`); `course_id` (int or array — filters to evaluators who have at least one `Result` whose `student_assignment.enrollment.course.id` matches, a 4-level-deep `whereHas` chain); `current_date_range` (int days — evaluators with at least one `Result` created in the last N days); `date_from`/`date_to` (either or both — `date_from` alone uses `created_at > date_from`, `date_to` alone uses `created_at < date_to+1day`, both together use a `whereBetween`); `status` (raw `User.status` value — no named-constant translation at the query layer); `search` (LIKE against `full_name`/`first_name`/`last_name`).
- Every one of these queries is additionally hard-scoped to `whereHas('roles', fn($q) => $q->where('name','evaluator')->orWhere('name','admin'))` — **admin users are included in every "evaluator" listing/count in this module**, not just users explicitly holding the evaluator role; a parity test seeding only role=`evaluator` users and expecting admins excluded from these endpoints will see extra rows.
- **Success response:** `EvaluatorResource::collection(...)->additional(['meta' => [...]])` — `meta` = `{total_evaluator, total_active_evaluator, total_deactive_evaluator, total_assignments, total_backlog_assignments, total_pending_assignments, range}`. **All of these `meta` counts are recomputed via the same filtered `searchQuery()`**, i.e. they reflect whatever `evaluator_id`/`course_id`/`search`/etc. filters were on the request — these are filtered-set aggregates, not global totals, unlike some other modules' `meta` blocks in this codebase that mix page-level and global-level aggregates inconsistently (see `NPS.md`'s v2 `/nps` note for the contrasting case).
- `total_active_evaluator`/`total_deactive_evaluator` use `User::USER_APPROVED`/`User::USER_DISABLED` respectively — **these two counts are not guaranteed to sum to `total_evaluator`** if any matching user has a third status value (e.g. pending) — verify the full `User` status enum directly if a test asserts `active + deactive == total`.
- `EvaluatorResource` fields: `id`, `full_name`, `status` (raw, only these 3 real columns survive `Arr::only()`), plus 3 computed fields **from the eager-loaded `evaluator_results` relation** (⚠️ requires `index()`'s `['evaluator_results']` relation load — using this resource anywhere without that eager-load would break, though no other route in this module currently does): `total_assignments` (raw count of all `evaluator_results`), `pending_assignments` (count where `is_email_sent == 0` and `submitted_date` within the last 7 days), `backlog_assignments` (count where `is_email_sent == 0` and `submitted_date` more than 7 days ago) — note **pending/backlog here are keyed on `submitted_date`, not `evaluation_due_date`** (contrast with `Result.php`'s own `checkTheStatus()`, which uses `evaluation_due_date` for its own "Backlog" determination — two different backlog definitions coexist across these two modules for what looks like the same concept).

### `GET /v1/evaluator/{evaluator}`, `POST /v1/evaluator`, `PUT/PATCH /v1/evaluator/{evaluator}`, `DELETE /v1/evaluator/{evaluator}` — `apiResource`'s `show`/`store`/`update`/`destroy` — **confirmed broken, no methods exist**
Neither `EvaluatorController` nor `EvaluatorTrait` implements `show()`, `store()`, `update()`, or `destroy()` — confirmed by reading both files in full. All 4 routes trigger a PHP fatal `Error: Call to undefined method` on any call, surfacing as an uncaught **500**, not a clean 404/405 — the same broken-`apiResource` pattern documented repeatedly elsewhere in this codebase (`NPS`, `AssignmentTag`, `AssignmentSendingLog`, `StudentAssignment`, `Result`). This is the most extreme instance of the pattern found so far: **4 of the 5 `apiResource` actions are non-functional**, leaving only `index()` as a real endpoint — there is genuinely no way to create, update, view a single, or delete an "evaluator" through this module's own API; evaluator management, to whatever extent it exists, must happen through the `User`/role-management modules instead.

## `GET /v1/evaluator/export` — `export()` (trait method)
- Registered **before** the `apiResource` block, so this literal path takes precedence over the `{evaluator}` wildcard.
- **Success response:** `apiResponse('', 'Evaluator Csv file exporting started', 'success')` — `data` is an empty string.
- **Side effects:** dispatches `EvaluatorCSVDownloadExport` on queue `default_medium`. The job builds a CSV (`Evaluator Name`, `Total Assignments`, `Pending Assignments`, `Backlog Assignments` — same pending/backlog definitions as `EvaluatorResource` above) from **all** evaluator-role `User` rows (no filter params applied — the job's own `getEvaluators()` query is independent of whatever query params were on the original `export()` request, unlike `Assignment`'s and `StudentAssignment`'s export jobs, which do forward `request()->all()`), uploads to S3 (`exports/tmp/evaluators/{filename}`), then fires **both** `$user->notifyNow(new EvaluatorCSVCompletedNotification(...))` (in-app `database`-channel only) **and** `Mail::to($user->email)->send(new EvaluatorCSVCompletedMail(...))` — no copy-paste text bug here (unlike `Assignment`'s equivalent notification, see `Assignment.md`); this one correctly says "Evaluator CSV exporting completed."
- ⚠️ **Dead export-flow classes:** `Modules/Evaluator/Jobs/EvaluatorCSVDownloadStart.php`, `EvaluatorCsvDownload.php`, `EvaluatorCSVExportStarted.php`, and `Modules/Evaluator/Emails/EvaluatorCSVStartedMail.php` all exist but are **never referenced by the live `export()` route** — grepped the full module tree, they're only self-contained/unreferenced files. No "export started" email is ever sent from this module's live code path, despite these classes existing and implying one should be — only the single completion mail/notification pair above actually fires.

## `GET /v1/evaluator/results/dashboard/list` — `evaluatorsResultsDashboardData()` (trait method)
- **Success response:** `apiResponse(['pie' => [[header], ['Backlog', N], ['Pending', N], ['Evaluated', N]], 'evaluators' => [...]])` — `pie` is a Google-Charts-style array-of-arrays, same pattern as `NPS`'s and `StudentAssignment`'s dashboard endpoints. `pie`'s three counts come from `ResultRepository`'s own status-based counters (`totalResultsWhereStatusIsBacklog/Pending/Evaluated`) — **a third, independent definition of "backlog"/"pending"** from the two already noted above (`EvaluatorResource`'s `submitted_date`-vs-7-days rule, and `Result::checkTheStatus()`'s `evaluation_due_date`-vs-now rule) — verify `ResultRepository`'s exact predicate directly (in `Result`'s own module) if a test needs to reproduce this specific count.
- `evaluators` = `EvaluatorRepository::topEvaluatorsWithMostResultsInBacklog()` — top N (default 6, or `rows` query param) evaluator-role users by a **fourth-again** backlog definition: `Result.status == ACTIVE AND evaluation_due_date < today()` (matches `Result::checkTheStatus()`'s definition this time, not `EvaluatorResource`'s), ordered `orderByDesc('Backlog')`. Each item is a raw `User` row (`id`, `full_name`) with 4 dynamically-named `withCount` aliases merged directly onto it: `Backlog`, `Pending`, `Evaluated`, `Total` — **capitalized, non-snake_case keys**, a naming-convention outlier versus every other count key in this module (`total_evaluator`, `pending_assignments`, etc., all lowercase/snake_case).
- **Caching:** `Cache::remember('dashboard.evaluator_results.data', 60*30, ...)` — same unscoped, 30-minute, single-shared-key caching pattern as `StudentAssignment::studentAssignmentsDashboardData()` (see `StudentAssignment.md`) — stale-data risk for any test run within 30 minutes of another call.

## Summary of endpoints documented

**7 route entries** (`export` + the 5-route `apiResource` + `evaluatorsResultsDashboardData` = 7 total):
- **3 live/working:** `index`, `export`, `evaluatorsResultsDashboardData`.
- **4 confirmed broken:** `apiResource`'s `show`/`store`/`update`/`destroy` — fatal 500, undefined method, for every one of them.

**Notable findings for parity testing:**
- This module has no real CRUD at all — only a listing, an export, and a dashboard. Anyone needing to create/modify/delete an "evaluator" for test setup must do so via `User`+role assignment directly, not through this module's API.
- **The module's own `Evaluator` entity class is entirely dead code** — everything queries `User` filtered by role instead.
- **Three (arguably four, counting `Result`'s own) independent and mutually inconsistent definitions of "backlog"/"pending" coexist across this cluster**: `EvaluatorResource`'s (`submitted_date` + 7 days, ignores `evaluation_due_date`), `ResultRepository`'s dashboard counters (definition not traced here — see `Result.md`), and `topEvaluatorsWithMostResultsInBacklog()`'s (`evaluation_due_date` + `status`, matching `Result::checkTheStatus()`'s own logic). A parity test must pick the specific endpoint's own definition rather than assuming "backlog" means one thing across this codebase.
- `index()`'s "evaluator" scope silently includes `admin`-role users alongside `evaluator`-role ones, everywhere in this module.
- The export flow's "started" mail infrastructure (job + mailable classes) exists but is entirely dead — only a completion signal ever fires.

**Cross-module coupling confirmed from this side:**
- Evaluator *assignment* onto `Result` rows (single or round-robin) is implemented entirely in the `Result` module (see `Result.md`) — this module has no equivalent write endpoint of its own, consistent with `API_SPECIFICATIONS.md`'s characterization.
- `EvaluatorResource`'s `evaluator_results` relation and all count queries here ultimately read `Result` rows (see `Result.md` for that entity's own status/date semantics) — this module is a thin reporting layer on top of `Result` data, not an independent domain.

**Confidence:** High — every route traced to its controller/trait method (or confirmed absent) by reading the full controller, trait, both resource-adjacent repository files, and the entity itself; the dead-entity and dead-export-flow findings were confirmed via full-tree grep, not inferred from naming.
