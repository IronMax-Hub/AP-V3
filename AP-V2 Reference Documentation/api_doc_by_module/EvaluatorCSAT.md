# EvaluatorCSAT Module — API Documentation

The `EvaluatorCSAT` module owns the `evaluator_csat_form` (+ `evaluator_csat_form_reason` / `evaluator_csat_form_reason_maping`) tables — a student's satisfaction survey about the **evaluator** who graded a specific `Result` (as distinct from `AssignmentCSAT`, which surveys the assignment/enrollment itself — see `AssignmentCSAT.md`). See [`./_COMMON_CONVENTIONS.md`](./_COMMON_CONVENTIONS.md) for app-wide envelope/error/pagination conventions.

**Module-wide auth:** every route in `Modules/EvaluatorCSAT/Routes/api.php` is `auth:sanctum` + `json.response`, prefix `v1`. No `auth:student` route exists in this module — like `NPS`'s `store()` (see `NPS.md`), the submission endpoint is only reachable with a staff/admin token, and `student_id` is taken directly from the request body rather than derived from an authenticated student identity — the same authorization-boundary caveat applies here.

**Class layout:** `EvaluatorCSATController` implements `index()`/`store()` directly; `use`s `EvaluatorCSATTrait` for `export()`/`checkAvailable()`/`getCSATFormReason()`/`graph_index()`/`getCSATQuestionsAccordingToRating()`/`calculateRangeForCursor()`.

## Core CRUD (`Route::apiResource('evaluator-csat', 'EvaluatorCSATController')`) — only `index`/`store` are real

### `GET /v1/evaluator-csat` — `index()` (controller)
- Query: `rows` (default 15).
- **Success response:** `EvaluatorCSATFormResource::collection(...)->additional(['meta' => ['total' => ..., 'range' => ...]])` — standard cursor-paginated shape.
- `EvaluatorCSATFormResource` fields: `rating`, `other_option`, `comment`, `status` (raw, `'A'`/`'P'`/`'D'` per `EvaluatorCSATForm::STATUS_TYPE_1/2/3`), plus nested `batch`/`course`/`package` (all via `result.student_assignment.enrollment`, each `null`-safe), `student` (`{full_name, email, country_code, phone}`), `evaluator` (`{id, full_name}`), `assignment_id` (actually `result.assignment_id` — the same `StudentAssignment`-id-named-`assignment_id` FK-naming trap documented in `Result.md`), `submitted_date` (from `created_at`, not from `result.submitted_date`), `bootcamp` (re-queries `Enrollment` by id for `{bootcamp_id, bootcamp_name}`, `null` if the bootcamp fields are `0`/`null`), `edmingle_batch_name`, and two computed keys worth separate call-outs below: `question` and `reasons`.
- **`question` resolution — a resource resolving a fresh controller instance from the container mid-serialization:** `app(EvaluatorCSATController::class)->getCSATQuestionsAccordingToRating($this->rating)` — instantiates an entirely new `EvaluatorCSATController` (with its own injected repositories) just to call one trait method, rather than calling a plain service/repository method. `getCSATQuestionsAccordingToRating($rating)` returns a single fixed reason (`EvaluatorCSATFormReason` id `17` for `rating >= 4`, id `12` for `rating == 3`, id `1` for `rating < 3`) — **these 3 specific reason-row ids are hardcoded**, not looked up by any semantic key; if the underlying seed data for `evaluator_csat_form_reason` ever changes such that ids 1/12/17 no longer hold the intended "why" prompts for negative/neutral/positive ratings, this silently returns the wrong (or a since-repurposed) question with no error.
- **`reasons`:** `getReason($this->evaluatorCSATFormReasonMaping)` — a hand-rolled loop, one `EvaluatorCSATFormReason::where('id', ...)->first()` query per mapping row (N+1 query pattern, not eager-loaded despite `evaluatorCSATFormReasonMaping` itself presumably being loadable as a relation) — **unguarded**: if a mapping's `reason_id` doesn't resolve to an existing reason row (e.g. the reason was later deleted), `$reasons->id` on the next line throws "Attempt to read property on null," an uncaught 500.

### `POST /v1/evaluator-csat` — `store()` (controller)
- **Request body** (`StoreEvaluatorCSATRequest`): `student_id` required `exists:students,id`; `result_id` required `exists:results,id`; `evaluator_id` required `exists:users,id`; `rating` required **integer** (contrast with `AssignmentCSAT`'s `rating`, which is a required **string** — see `AssignmentCSAT.md`); `details` required string; `reason` required array, each `exists:evaluator_csat_form_reason,id`.
- **Duplicate check:** only runs `if (isset($request->result_id))` — since `result_id` is FormRequest-`required`, this condition is effectively always true by the time the method body executes (a request that omitted it would already have 422'd) — functionally always-on, not conditional in practice. If `EvaluatorCSATFormRepository::checkIfDuplicate($student_id, $result_id)` finds an existing submission: `$this->apiResponse(null, 'Already Submitted', statusCode: 200)` — **`data` is literally `null`** (not `[]` or `""`), **HTTP 200 for what is semantically a rejected duplicate** — matches the cross-cutting "2xx success-shaped body on a no-op" caution in `_COMMON_CONVENTIONS.md`; a parity test must check the message text, not the status code, to detect this outcome.
- **Success response:** `$this->apiResponse($csatData, 'Evaluator CSAT Submitted Successfully', statusCode: 201)` — `data` is the raw created `EvaluatorCSATForm` model (not wrapped in a Resource) — a different, less-processed shape than what `index()` returns for the same underlying row (no `question`/`reasons`/nested `batch`/`course`/etc. — a client that creates a CSAT then expects the `store()` response to look like an `index()` row will find far fewer fields).
- **Side effects (inside `DB::transaction()`):** creates one `EvaluatorCSATForm` row (`status` forced to `EvaluatorCSATForm::STATUS_TYPE_1` — `'A'` — regardless of any client input, since the FormRequest doesn't even accept a `status` field); creates one `EvaluatorCSATFormReasonMaping` row per id in `reason[]`.

### `GET /v1/evaluator-csat/{evaluatorCSAT}`, `PUT/PATCH /v1/evaluator-csat/{evaluatorCSAT}`, `DELETE /v1/evaluator-csat/{evaluatorCSAT}` — `apiResource`'s `show`/`update`/`destroy` — **confirmed broken, no methods exist**
Neither `EvaluatorCSATController` nor `EvaluatorCSATTrait` implements `show()`, `update()`, or `destroy()` — confirmed by reading both files in full. All 3 routes trigger a PHP fatal `Error: Call to undefined method` on any call, an uncaught **500** — the same broken-`apiResource` pattern documented repeatedly across this codebase.

## `GET /v1/evaluator-csat/export` — `export()` (trait method)
- Registered before the `apiResource` block, so this literal path is matched first.
- **Success response:** `apiResponse('', 'Evaluator CSAT Csv file exporting started', 'success')` — `data` empty string.
- **Side effects:** `$this->excel->queue(new EvaluatorCSATExport(), "exports/tmp/evaluator-csat/{filename}", 's3')->onQueue('default_high')->chain([new EvaluatorCSATCSVDownload($user, $data)])` — a **Laravel-Excel `queue()` export chained directly to a follow-up job**, a structurally different export mechanism from every other export in this cluster (`Assignment`/`StudentAssignment`/`Evaluator` all dispatch a single custom job that builds the CSV manually with `fputcsv()`; this one delegates CSV generation to `Maatwebsite\Excel`'s own queued export class, only using a custom job for the completion notification). The chained `EvaluatorCSATCSVDownload` job only sends a completion mail (`Mail::to($user->email)->queue(new EvaluatorCSATCSVCompletedMail(...))`) — **no in-app database notification** fires from this export flow, unlike `Assignment`'s and `Evaluator`'s equivalent exports (both of which additionally fire a `notifyNow()` in-app notification) — this is the one export in the cluster with mail-only completion signaling.

## `GET /v1/evaluator-csat/questions` — `getCSATFormReason()` (trait method)
- **Success response:** a **bare PHP array, returned with no `apiResponse()`/envelope at all** — Laravel auto-serializes it to raw JSON with no `data`/`message`/`status` keys, matching the bespoke-shape pattern already seen in `Result::getEvaluatorPendingDetails()` and `AssignmentTag::search()`.
- ⚠️ **Confirmed grouping bug:** the method partitions `EvaluatorCSATFormReasonRepository::questions()` into parent reasons (`parent_id === null`, each seeded with an empty `child: []`) and child reasons (`parent_id !== null`), then does `array_push($res[0]['child'], $arr)` for **every** child, **unconditionally targeting index `0`** of the parent array rather than locating the child's actual parent by matching `parent_id` to the corresponding parent's `id`. **If more than one top-level (parent) reason exists, every child reason from every parent group collapses into the first parent's `child` array** — the response's nested structure does not reflect the real parent/child relationships whenever there is more than one parent reason in the table. Additionally, if the *first* item iterated in `$reasons` happens to be a child row (or if there are zero parent rows at all), `$res[0]` doesn't exist and `array_push($res[0]['child'], ...)` fatally errors (`array_push()` expects its first argument by reference to be an array; `null` triggers a `TypeError`) — an uncaught 500. Preserve this exact grouping behavior (or its failure mode) in parity testing; do not assume a "correctly nested by `parent_id`" tree.

## `GET /v1/evaluator-csat-graph-index` — `graph_index()` (trait method — note the route has **no `/v1` path segment for `evaluator-csat`** in its URL structure, unlike every sibling route in this file; it's registered as a flat `evaluator-csat-graph-index` string rather than `evaluator-csat/graph-index`)
- **Success response:** `apiResponse(['totalEligible', 'totalSubmitted', 'countPro', 'countPassive', 'countDetractor', 'csat', 'allData', 'avgRating', 'responseCode'])`. `countPro`/`countPassive`/`countDetractor` are each a **combined string** `"N(XX.XX%)"` (matching the pattern already documented for `NPS`'s legacy `graph_index1()` — see `NPS.md`), not split count/percentage keys. `allData` is a Google-Charts-style array-of-arrays over ratings 1–5 (not 0–10 like `NPS`), each row `[rating, count, "count" (as annotation string), colorStyle]` — colors are fixed per rating (`1`/`2` → `#ef7a88` red, `3` → `#efd47b` yellow, `4`/`5` → `#78e3a4` green). `promoter`/`passive`/`detractor` buckets: `rating < 3` detractor, `== 3` passive, `> 3` promoter — a 1–5 scale, not NPS's 0–10 scale, so don't reuse NPS's threshold assumptions here.
- Computed by iterating **all** rows from the unbounded, unpaginated `EvaluatorCSATFormRepository::graphSearch()` query — a potential full-table scan, same caution as `NPS`'s equivalent dashboard endpoints.
- `totalEligible` is set to the same value as `totalSubmitted` (`$totalSubmitted ? $totalSubmitted : 0`, i.e. just `$totalSubmitted` since it's already an int) — **there is no actual "eligible" computation here** (contrast with `AssignmentCSAT`'s eligibility-check endpoint, a separate concern) — this key is a misnomer, always equal to `totalSubmitted`.

## `POST /v1/evaluator-csat/check-available` — `checkAvailable()` (trait method)
- **Request body** (`CheckCSATEligibilityRequest`): `student_id` required `exists:students,id`; `result_id` required `exists:results,id`.
- **Success responses:** `$this->apiResponse([], 'Already Submitted', statusCode: 200)` if a CSAT already exists for this student+result; `$this->apiResponse([], 'Elligable for Submission', statusCode: 201)` otherwise — note the literal misspelling **`'Elligable'`** (verbatim from source) and the unusual choice of **HTTP 201 for a read-only eligibility check that creates nothing** — a parity test must not treat 201 here as evidence of a created resource.
- **Notes:** this is the dedicated eligibility pre-check endpoint for `EvaluatorCSAT`, functionally parallel to `AssignmentCSAT`'s own `CheckEligibleForCSATRequest`-backed endpoint (see `AssignmentCSAT.md`) — both ultimately query the same kind of "does a CSAT row already exist for this student+key" duplicate check, but against their own respective tables (`evaluator_csat_form` here vs. `assignment_csat_form` there); the two are not interchangeable and a client must call the correct module's endpoint for the CSAT type it's checking.

## Summary of endpoints documented

**8 route entries** (`export` + `getCSATFormReason` + `graph_index` + `checkAvailable` + the 5-route `apiResource` = 8 total):
- **6 live/working:** `export`, `getCSATFormReason`, `graph_index`, `checkAvailable`, `index`, `store`.
- **2 confirmed broken:** `apiResource`'s `show`/`update`/`destroy` — wait, 3 broken (`show`, `update`, `destroy`), bringing the working count to 5 and broken count to 3 out of 8 total routes.

**Notable findings for parity testing:**
- `getCSATFormReason()`'s parent/child grouping is confirmed broken for any dataset with more than one top-level reason — every child collapses under the first parent, and a dataset with zero/misordered parents fatal-errors.
- `store()`'s duplicate-check success response returns `data: null` (not `[]`) at **HTTP 200** for a semantic rejection — check the message, not the status code.
- `checkAvailable()`'s "eligible" response uses HTTP 201 despite performing no creation — an unusual status-code choice worth flagging so a test doesn't misinterpret it as resource creation.
- `graph_index()`'s `totalEligible` key is a misnomer always equal to `totalSubmitted` — no real eligibility computation happens in this endpoint.
- The `question` field's reason ids (1, 12, 17) are hardcoded magic numbers tied to specific seed rows, not looked up by any stable key — fragile if that seed data changes.
- This module's export flow uniquely delegates CSV generation to `Maatwebsite\Excel`'s own `queue()` mechanism (chained to a completion-only job) rather than the hand-rolled `fputcsv()` pattern used by every sibling module's export in this cluster, and is the only one of them with no in-app notification (mail-only).

**Cross-module coupling confirmed from this side:**
- `store()`/`checkAvailable()` key off `Result` rows (`result_id exists:results,id`) — a CSAT submission is tied to a specific graded `Result`, not directly to a `StudentAssignment` or `Enrollment` (those are reached transitively via `result.student_assignment.enrollment` for display purposes only).
- Functionally parallel to, but structurally independent from, `AssignmentCSAT`'s own eligibility-check/submission pair — see `AssignmentCSAT.md` for that module's own request shape (`rating` as string, `enrollment_id`/`package_id` mutual exclusivity) and confirm which of the two a given client integration actually targets before assuming shared behavior.

**Confidence:** High — every endpoint traced to its controller/trait method (or confirmed absent); the parent/child grouping bug and the hardcoded-reason-id findings were confirmed by reading the exact loop/branching logic, not inferred from the method names.
