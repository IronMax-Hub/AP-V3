# Notification

Admin-facing surface for composing, listing, and managing notifications sent to students (by course/batch/package/tag/channel), plus the admin side of the comment thread on each notification and reference-data lookups (categories, tags) used to build the compose UI. Shares its backing tables (`notification`, `notification_user`, `notification_comments`, etc.) with the student-facing `StudentNotifications` module — see [`./StudentNotifications.md`](./StudentNotifications.md) for that side. See [`./_COMMON_CONVENTIONS.md`](./_COMMON_CONVENTIONS.md) for shared envelope/error/pagination conventions.

**Module-wide auth:** all 16 route registrations are under `Route::middleware(['auth:sanctum', 'json.response'])->prefix('v1')` — `auth:sanctum`, an admin/staff guard, not `auth:student`.

**Class-location note:** `NotificationController` composes `NotificationTrait` (most listing/CRUD-adjacent logic) but defines `show()`, `update()`, and `image_upload()` **directly on the controller itself** — flagged per-endpoint below since it affects which file a parity tester needs to open to verify behavior.

---

## `GET /v1/notification/students` (route name `notification.students`)
- **Trait method:** `students()`.
- **Request params (query):** all optional, read via `request()->all()` inside two `Student` model scopes — `courseBatchAndPackageFilterForNotifications()` and `searchForListing()` (both confirmed-live scopes on `Modules\Student\Entities\Student`; exact filter keys are whatever those scopes read, not re-derived here). `rows` controls page size (default 15, cursor-paginated via `paginate(..., pageName: 'cursor')`).
- **Success:** `StudentNotificationResource::collection($data)->additional(['meta' => ['range' => rangeForPagination($data)]])` — note this uses the **`LengthAwarePaginator`-based** `rangeForPagination()` helper (`{"from","to","total"}` only, no `total` duplicated at the meta root) rather than the cursor-family `calculateRangeForCursor()` used by every other listing endpoint in this module, even though the query itself paginates with `pageName: 'cursor'`. `StudentNotificationResource` (from the **`Student` module**, `Modules\Student\Http\Resources\StudentNotificationResource` — a different class from this module's own unused same-purpose resource, see Summary) returns a large per-student projection: base fields (`full_name`,`status`,`phone`,`email`,`id`,`reg_code`) plus `country_code`, `last_login`, `enrollment_form_filled` (`'Y'`/`'Y'`-or-`'N'` string, not boolean), and four hand-built relationship trees — `courses` (only enrollments with no `bootcamp_id`/`package_id`), `bootcamp` (grouped by `bootcamp_display_name`, each with a nested `courses` array), `packages` (grouped by package `name`, nested `courses`), `batches` (one entry per enrollment, `{id, batch_date}`), plus `tags`, `country_id` (nested), `father_name`, `gender`, `lms_id`, `date_of_birth`, `linked_in_link`.
- **Side effects:** read-only.

## `POST /v1/create-notification-for-specific-range` (route name `notification.create_notification_for_specific_range`)
- **Trait method:** `create_notification_for_specific_range(StoreNotificationRequest $request)`.
- **FormRequest (`StoreNotificationRequest`):** `title` required string max:255; `content` required string; `category_id` required `exists:notification_category,id`; `tag_id` required `exists:notification_tags,id`; `channel_id` required `exists:notification_channel,id`; `radio` required (no further constraint — any non-empty value, e.g. `'now'`/`'later'`/garbage, passes).
- **Behavior:** creates one `Notification` row (`created_by = auth()->user()->id`, `request_data` = the full raw request JSON-encoded as an audit snapshot); `scheduled_time` = `now()` if `radio == 'now'`, else `strtotime($request->scheduled_time)` reformatted (⚠️ **no validation that `scheduled_time` is even present/parseable when `radio != 'now'`** — `strtotime(null)` returns the current timestamp, so an omitted `scheduled_time` silently behaves like "now" rather than erroring). Creates exactly one `NotificationTag` row and one `ChannelNotification` row (both are 1:1 in effect, despite `tags()`/`channel()` being `hasMany` relations on the `Notification` model — this endpoint's writer never creates more than one of each). If `course_id`/`batch_id`/`package_id` arrays are present in the body, loops each and creates one `CourseNotification`/`BatchNotification`/`PackageNotification` row per id — **none of these three are declared in the FormRequest's rules at all**, so they're accepted unvalidated (any value, any type, silently used as a raw FK insert — a non-existent id creates an orphaned mapping row rather than failing validation).
- **Success:** `apiResponse([], 'Notification Created')` → HTTP 200, default `status: "success"`.
- **⚠️ Confirmed structurally identical to `create-notification-for-all` below** — same FormRequest, same field-by-field logic, byte-for-byte. Despite the name implying a distinct "send to a specific filtered range of students" behavior, this endpoint does not itself perform or record any different audience-narrowing beyond whatever `course_id`/`batch_id`/`package_id` happen to be sent — the actual *sending* (matching this `Notification` row against students and creating `NotificationUser`/dispatching mail) is not part of either handler's own code at all (no `NotificationUser` row is created here, no job is dispatched) — presumably that step lives in a separate scheduled command/job not reachable from either of these two endpoints, and out of scope of this trait file. **Do not assume calling this endpoint actually delivers anything to students** — verify independently what process consumes the `notification`/`*_notification` rows created here.

## `POST /v1/create-notification-for-all` (route name `notification.create_notification_for_all`)
- **Trait method:** `create_notification_for_all(StoreNotificationRequest $request)`. Identical `StoreNotificationRequest`, identical body to `create_notification_for_specific_range` above (only difference: an extra `Log::info(...)` call logging the raw request at the top) — see the note above; both endpoints are functionally the same code path.
- **Success:** `apiResponse([], 'Notification Created')`.

## `GET /v1/notification/comments/{notification_id}` (route name `notification.comments.get`)
- **Trait method:** `comments_get($notification_id, $parent_id = null)` — like its `StudentNotifications` counterpart, `$parent_id` is never actually reachable from this route (only `{notification_id}` is captured), so this always returns top-level comments.
- **Behavior:** hand-rolled array (**not `apiResponse()`, not `response()->json()`** — a raw PHP array returned directly from the controller/trait method, which Laravel auto-serializes to a 200 JSON response): if the `Notification` exists, `[{"id","title","content","category_id","scheduled_time","sent_at","new_comments","created_by","updated_by","comments": <CommentResource::collection(...)>}]` (a **single-element array wrapping one object**, not a bare object); if the notification doesn't exist, `$final_result` stays `[]` — an empty array, HTTP 200, no error signaled at all for a bad id.
- **`CommentResource` shape:** raw `notification_comments` columns except `created_at`/`updated_at` (recomputed: `created_at` reformatted `Y-m-d h:i:s` [12-hour, no am/pm marker despite the lowercase `h`], `updated_at` hardcoded `null`), plus `admin_id`/`admin_name` (from the `user` relation, unconditional — **not gated by `user_type` the way `StudentNotifications`'s equivalent resource is**), `student_id` (from the `student` relation, also unconditional), `student_name` (via a private `get_name($user_type)` helper: returns the student's name if `user_type == 'student'`, else the admin's), `sub_comments` (recursively resolved via `app(NotificationController::class)->getSubComments($this->notification_id, $this->id)` — same N+1-per-comment pattern as `StudentNotifications`).

## `POST /v1/notification/comments/{notification_id}` (route name `notification.comments.post`)
- **Trait method:** `comments_post(Request $request, $notification_id)`.
- **Request params (body):** validated inline — `comment` required string; `parent_id` nullable integer.
- **Behavior:** creates a `NotificationComment` (`user_type = NotificationComment::USER_TYPE_1` = `'admin'`, `created_by = auth()->user()->id`, `parent_id` = the sent value or `null` if falsy/omitted — unlike the student-side `store-comment`, this one **does** default missing `parent_id` cleanly via `$request->parent_id ?: null`). Dispatches `CreateNotificationComment::dispatch($notification_id, $data, $parent, auth()->user())` (queued job, presumably emails/notifies the affected student — not traced further, out of this file).
- **Success:** `apiResponse([], 'Comment Created')`.

## `DELETE /v1/delete-comment` (route name `notification-comments.delete`)
- **Trait method:** `delete_comment(Request $request)`. **No FormRequest** — `$request->comment_id` read unvalidated; a missing `comment_id` makes `NotificationComment::findOrFail(null)` throw a `ModelNotFoundException` → standard 404 shape from `_COMMON_CONVENTIONS.md`.
- **Behavior:** writes an `activity()` log entry (event `'Notification Comment Deleted'`, `withProperties` snapshotting the comment's own fields) **before** deleting; then deletes the target comment **and** every comment whose `parent_id` equals it (i.e., direct replies are cascade-deleted, but only one level deep — a reply-to-a-reply, if this UI ever supports nesting beyond one level, would be orphaned rather than cascade-deleted).
- **Success:** `apiResponse([], 'Comment deleted successfully')`.

## `GET /v1/search/category` (route name `notification.search.category`)
- **Trait method:** `search_category()`.
- **Request params (query):** `search` (optional, `LIKE` against `id`/`colour`/`title`); `offset`/`limit` (optional, default `0`/`10`).
- **Success:** `CategoryResource::collection(...)->additional(['meta' => ['total' => <count with the SAME filters but NOT the same offset/limit>]])` — the resource-collection pagination family (`{"data":[...],"meta":{"total":N}}`). `CategoryResource`: `{id, title, colour}` only.

## `GET /v1/search/specific-categories` (route name `notification.specific.search-category`)
- **Trait method:** `searchCategoriesWithArray()`.
- **Request params (query):** `search` (optional array of category ids — `whereIn('id', request('search'))`; if `search` is sent as a non-array scalar, `whereIn` receiving a non-array/non-Arrayable value is likely to misbehave — not independently verified here).
- **Success:** `apiResponse($this->notificationRepo->searchCategoriesWithArray())` — the plain `apiResponse()` envelope (`{"data": [{"id","title","colour"}...], "message": "Success", "status": "success"}`), a **different shape** from `search/category`'s Resource-collection family even though both return the same underlying model.

## `GET /v1/notification/tags` (route name `notification.tags`)
- **Trait method:** `tags()`.
- **Request params (query):** `except` (optional int id to exclude from the result).
- **Behavior:** `notificationRepo->searchTags()` → `NotificationTags::query()->when(search, ...)->limit(10)->get(['id','title'])`. If `except` is present, filters that id out client-side (`$data->reject(...)->values()->all()`).
- **Success:** `apiResponse($data)` (or `apiResponse($rejected->values()->all())` on the `except` branch) — plain `apiResponse()` envelope wrapping a flat `[{"id","title"}, ...]` array (unlike `StudentNotifications`'s `getTags`, which strips down to bare title strings — these are two different tag-listing shapes for two different consumers).

## `PUT /v1/notification-edit/{notification}` (route name `notification.update`) — first of two identically-purposed routes, see apiResource note below
- Routes to the controller's own `update(Request $request, $id)` — see full behavior documented once, under the `apiResource` section below (this route and the apiResource-registered `PUT /v1/notification/{notification}` call the exact same method).

## `apiResource('notification', NotificationController)`

Per Laravel's actual `Route::apiResource()` behavior, this registers exactly 5 routes: `index`, `store`, `show`, `update`, `destroy` (no `create`/`edit`).

### `GET /v1/notification` — `index`
- Defined directly on the controller. **Request params (query):** `rows` (page size, default 15).
- **Success:** `NotificationResource::collection($this->notificationRepo->allWithSearch(...))->additional(['meta' => ['total_notification', 'total_pending_notification', 'total_sent_notification', 'range' => <cursor family>]])` — three distinct named totals in `meta`, not just one `total` key (a genuinely different `meta` shape from most other cursor-paginated listings in this app). The underlying query excludes soft-deleted rows (`whereNull('deleted_at')`) **and** rows with `status = 2` — two independent exclusion mechanisms layered on top of each other (see Summary). Supports rich filtering via `request()`: `search` (matches `title`/`content`/category title/course name/batch date/channel title), `category_id`, `batch_id`/`package_id`/`course_id` (each array, `whereIn`), `min_date`+`max_date` (both required together), `current_date_range` (a day-count lookback, oddly checked twice: `!is_null(x) && !is_null(x)`).
- **`NotificationResource` shape:** `id`,`content`,`title`,`scheduled_time`,`new_comments`,`category_id`,`status` (raw columns), `sent_at` (reformatted `Y-m-d G:i:s` or `null`), `category` (`{title}` only), `tags`/`channel`/`course_notification`/`batch_notification`/`package_notification` each mapped down to their nested reference object only (e.g. `tags` → `[{id,title}, ...]` from each `NotificationTag.notificationTag` relation).

### `POST /v1/notification` — `store` — **broken, not implemented**
No `store()` method exists on the controller or `NotificationTrait` (confirmed via full-file read of both). Calling this route throws an undefined-method `\Error`, surfacing as an uncaught fatal (most likely an unstyled 500), **not** any of this app's standard error envelopes. This is genuinely-broken scaffolding, not a harmless dead stub — flag for a boundary test confirming the 500.

### `GET /v1/notification/{notification}` — `show`
- Defined directly on the controller: `show($id)`.
- **Behavior:** `Notification::find($id)` (no existence check — see below), decodes the row's own `request_data` JSON snapshot (captured at creation time, see `create_notification_for_*` above) and re-attaches **live, current** lookups for `category`/`tags`/`channel` based on the ids found in that snapshot (`NotificationCategory::find(...)`, `NotificationTags::find(...)`, `NotificationChannel::find(...)` — note these overwrite the model's real `category`/`tags` *relation* properties with these ad-hoc singular lookups, which is why the response's `category`/`tags` here are single objects, not the collections `NotificationResource` would show for the same row).
- ⚠️ **No `Notification::find($id)` null-check** — a non-existent `$id` makes `$notification` `null`. Every subsequent line in this method reads/writes a property on that `null` value (`$notification->request_data`, then `$notification->category = ...`, `->tags = ...`, `->channel = ...`, `->radio = ...`) — in PHP 8, reading **or** writing a property on `null` emits a `Warning` ("Attempt to … property … on null") and the operation silently no-ops; it does **not** throw and does **not** auto-vivify `$notification` into an object. Since none of the property-write lines change what `$notification` actually *is* (still `null`), and `json_decode(null)` also just returns `null` (with a passable-null-to-internal-function deprecation notice, not fatal), the method reaches its `return` statement without ever calling a method on `null` — so it does **not** fatal-error. Net effect: a bad id returns **HTTP 200**, `apiResponse(['notification' => null], 'Success', 'success', 200)` — a "successful"-looking envelope whose `data.notification` is bare `null`, not a clean 404 and not a partially-populated object. (Distinguish from `update()` below, which *does* fatally error on a bad id, because it calls `->save()` — a method call, not a property access — on the null `$notification`.)
- **Success:** `apiResponse(['notification' => $notification], 'Success', 'success', 200)` — `$notification` here is the raw Eloquent model (all its native columns) with `category`/`tags`/`channel`/`radio` overwritten as described above, not run through `NotificationResource`.
- **Also reachable via the duplicate, effectively-dead `GET /v1/notification/{id}` route (route name `notification.show`)** registered later in this same file — since it shares an identical URI *shape* with this apiResource-registered route and was added to the route collection afterward, Laravel's router matches this apiResource entry first; the later `notification.show`-named route is unreachable in practice. Harmless here specifically because both ultimately point at the same `show()` method — but worth knowing if grepping route *names* for this action, since two names (`notification.show` is unreachable; the apiResource one is unnamed by default) exist for one truly-reachable path.

### `PUT/PATCH /v1/notification/{notification}` — `update`
- Defined directly on the controller: `update(Request $request, $id)`. **No FormRequest** — inline `$request->validate([...])`: `title`/`content`/`category_id`/`radio` required; `scheduled_time` `required_if:radio,later`.
- ⚠️ Same missing-null-check pattern as `show()`: `Notification::find($id)` with no existence check. Unlike `show()`, though, this method **does** eventually fatal-error on a bad id — not at the early property-assignment lines (`$notification->title = ...` etc. are property *writes* on `null`, which — same as in `show()` — only emit PHP 8 `Warning`s and silently no-op, they don't throw), but at `$notification->save();` further down: calling a **method** on `null` (as opposed to reading/writing a property) is always a fatal `Error` in PHP ("Call to a member function save() on null"). So a non-existent `$id` reaches that line and 500s — not a clean 404 — but only once code execution gets there; a handful of harmless warnings are logged first.
- **Behavior:** overwrites `title`/`content`/`category_id`/`created_by` (⚠️ **sets `created_by` to the current caller on every update**, not `updated_by` — there is no `updated_by` column touched here at all, so the original creator attribution is destroyed on any edit); re-merges `student_id`/`course_id`/`batch_id`/`package_id` from the row's **existing** `request_data` snapshot into the current request before re-encoding `request_data` (so those four keys persist across edits even if the edit form doesn't resubmit them — but only those four; any other original field not in the current request body is lost from the new snapshot); recomputes `scheduled_time` the same `now()`-vs-`strtotime()` way as create. Then **deletes and recreates** the tag and channel mapping rows (`NotificationTag::where('notification_id', $id)->delete()` + insert one fresh row; same for `ChannelNotification`) — course/batch/package mapping rows (`CourseNotification`/`BatchNotification`/`PackageNotification`) are **not** touched at all by update, unlike create, meaning those associations can never actually be changed after initial creation via this endpoint.
- **Success:** `apiResponse([], 'Notification Updated')`.
- **Also reachable via `PUT /v1/notification-edit/{notification}` (registered earlier in the route file, route name `notification.update`) and the duplicate, effectively-dead `PUT /v1/notification/{id}` (registered later, also named `notification.update` — the second registration of this exact route name; `route('notification.update')` will resolve to whichever the router's name list retains, not independently confirmed which wins).** All three URIs funnel into the identical `update()` method — `notification-edit/{id}` is a genuinely distinct, reachable alternate path (different URI shape from the apiResource route), while the later `notification/{id}` registration is shadowed/unreachable for the same reason `show`'s duplicate is.

### `DELETE /v1/notification/{notification}` — `destroy` — **broken, not implemented**
No `destroy()` method exists on the controller or `NotificationTrait`. Same broken-scaffolding situation as `store` above — an undefined-method fatal error, not a graceful no-op.

## `POST /v1/text_editor/image_upload` (route name `text_editor.image_upload`)
- Defined directly on the controller: `image_upload(Request $request)`.
- **Request params (body, multipart):** inline `$request->validate(['file' => ['required','mimes:png,jpg,jpeg','max:10240']])`.
- **Behavior:** uploads to S3 under `uploads/text_editor/{time()}{uniqid()}-{ext}`.
- **Success:** `apiResponse(['image_path' => $imageLink], 'Success', 'success', 200)`.
- **Error (any exception, e.g. S3 failure):** `apiResponse([], 'Please try after sometime. We are faceing problem', 'error', 422)` — note the literal typo `"faceing"`, preserved verbatim; also reports Sentry if bound.

## `PUT /v1/notification-status/{notification_id}` (route name `notification.change.status`)
- **Trait method:** `changeNotificationStatus($id)`.
- ⚠️ **Misleadingly named — hard-deletes the row unconditionally**, does not toggle any status field: `Notification::find($id)->delete()`. No existence check — a non-existent `$id` makes `find()` return `null`, and calling `->delete()` on `null` is a fatal `Error` (method call on null), so a bad id here almost certainly 500s rather than 404s.
- **Success:** `apiResponse([], 'Notification Deleted')` — message text at least honestly describes the real (delete) behavior, even though the route/method name suggests a status toggle.

## `GET /v1/notification/{id}` (route name `notification.show`) — **unreachable, shadowed by the apiResource `show` route above**
Registered after `Route::apiResource('notification', ...)` with an identical URI shape (`notification/{param}`, param name doesn't affect route matching) and the same HTTP verb — Laravel's router matches the first-registered route with a matching pattern, so this route is dead weight in the route table, never actually invoked by any request. Harmless in effect since it points at the identical `show()` method the apiResource route already reaches, but worth knowing the URL-generation helper `route('notification.show')` still works even though the underlying route entry is never the one that actually handles a request.

## `PUT /v1/notification/{id}` (route name `notification.update`) — **unreachable, shadowed the same way**
Same shadowing situation as directly above, for `update()`. Also notable: this duplicates the route *name* `notification.update` already used by `PUT /v1/notification-edit/{notification}` earlier in the file — Laravel does not error on a duplicate route name, but which registration `route('notification.update')` resolves to was not independently confirmed here.

## Summary

- **Endpoint count:** 16 route registrations in the file — 10 explicit named routes before the `apiResource` line, 1 `apiResource` line contributing 5 REST routes (3 live: `index`/`show`/`update`; 2 broken: `store`/`destroy`), then 5 more explicit routes after it (`image_upload`, `changeNotificationStatus`, plus 2 that are unreachable duplicates of the apiResource's `show`/`update`). **Net distinct, reachable behaviors: 12** (`students`, `create_notification_for_specific_range`, `create_notification_for_all`, `comments_get`, `comments_post`, `delete_comment`, `search_category`, `searchCategoriesWithArray`, `tags`, `index`, `show`/`update` [reachable via 3 different URIs total], `image_upload`, `changeNotificationStatus`) plus 2 confirmed-broken (`store`, `destroy`) plus 2 confirmed-unreachable-but-harmless duplicate route registrations.
- **Structural surprises / bugs worth flagging for parity testing:**
  1. `create-notification-for-all` and `create-notification-for-specific-range` are **byte-for-byte identical logic** (bar one `Log::info` call) — the "for all" vs "for a specific range" distinction implied by the names is not implemented as any code difference between these two endpoints.
  2. Neither create endpoint actually creates a `NotificationUser` row or dispatches any visible send/delivery job — the real "who receives this and when" mechanism is not reachable from this controller/trait at all.
  3. `show()` and `update()` (both defined directly on the controller) have **no null-check** after `Notification::find($id)` — a bad id is very likely to either emit warnings-with-degraded-output (`show`) or fatally 500 (`update`, `changeNotificationStatus`), not cleanly 404.
  4. `update()` overwrites `created_by` (not `updated_by`) on every edit, destroying the original creator's attribution.
  5. `PUT /v1/notification/{id}` and `GET /v1/notification/{id}` (both registered after the `apiResource` line) are dead/unreachable — shadowed by the identically-shaped apiResource routes registered earlier — though harmless since both sets resolve to the same controller methods.
  6. `store`/`destroy` (from the `apiResource` registration) are genuinely broken — no such methods exist anywhere in this module.
  7. `NotificationTagsResource` (`Modules/Notification/Http/Resources/NotificationTagsResource.php`) and `UserResource` (`Modules/Notification/Http/Resources/UserResource.php`) are both confirmed dead — never instantiated anywhere in the codebase (grepped) — do not treat their shapes as live contracts.
  8. `Notification`'s own `Modules\Notification\Http\Resources\StudentNotificationResource` (note: not what `students()` actually uses — that pulls the *Student module's* same-named class instead) — grepped and confirmed **zero references anywhere**, fully dead.
- **Confidence:** High for all endpoints defined directly on the controller and in `NotificationTrait` (both read in full) and `NotificationRepository` (read in full). The route-shadowing analysis was independently verified against Laravel's actual route-matching/registration order, not assumed.
