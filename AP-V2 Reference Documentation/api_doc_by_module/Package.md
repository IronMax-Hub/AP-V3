# Package

Admin-facing CRUD + search/reference-lookup surface for the `packages` entity (a bundle of courses sold/enrolled as one unit) and its `package_course_mappings` pivot, plus an async CSV export and an activity log. Updating a package's course list triggers a queued job that retroactively enrolls the package's existing active students into any newly-added course. See [`./_COMMON_CONVENTIONS.md`](./_COMMON_CONVENTIONS.md) for shared envelope/error/pagination conventions.

**Module-wide auth:** all 6 routes are under `Route::middleware(['auth:sanctum', 'json.response'])->prefix('v1')`.

**Class-location note:** `PackageController` composes `PackageTrait` (`calculateRangeForCursor()`, `activity()`) and the app-wide `App\Http\Traits\ActivityLog` (`activity()`'s delegate). All CRUD (`index`/`show`/`store`/`update`/`destroy`) and search (`search`/`searchPackagesWithArray`/`searchPackagesWithCourses`) methods, plus `export()`, are defined **directly on the controller itself** — `PackageTrait` only contributes the two methods named above.

⚠️ **Structural gotcha, confirmed by reading both files:** `PackageTrait` declares its own `__construct(Excel $excel)`. Since `PackageController` **also** declares its own `__construct(PackageRepositoryInterface, PackageCourseMappingRepositoryInterface, EnrollmentRepositoryInterface)`, and a class's own method always wins over a same-named trait method, **`PackageTrait::__construct()` never actually runs** — `$this->excel` is never populated on any `PackageController` instance. Confirmed harmless in current usage (neither `activity()` nor `calculateRangeForCursor()` reference `$this->excel`), but worth knowing if a future change to this trait assumes that constructor executes — it does not.

## `apiResource('packages', PackageController)`

Per Laravel's actual `Route::apiResource()` behavior, this registers exactly 5 routes: `index`, `store`, `show`, `update`, `destroy` (no `create`/`edit`) — and unlike `Notification`/`StudentNotifications`, **all 5 are genuinely implemented** on this controller.

### `GET /v1/packages` — `index`
- **Request params (query):** `rows` (page size, default 15); `cursor` (standard cursor family; tampered cursor → `abort(500, 'Cursor value tempered')`); `search` (optional — matches `id` exactly **or** `name` `LIKE '%%<search>%'`, note the literal doubled `'%' . '%' . request('search') . '%'` concatenation in source, which produces the same string as a single `%`-wrap — a redundant but harmless quirk, not a functional bug).
- **Success:** `PackageResource::collection($this->packageRepo->allWithSearch(...))->additional(['meta' => ['total' => <int>, 'total_package' => <int, identical value, duplicated under two different keys>, 'range' => <cursor family>]])`.
- **`PackageResource` shape:** `id`,`name`,`duration_days` (raw columns only), plus `courses` (`PackageCourseMappingResource::collection($this->courses)` — each mapping row minus its own id/course_id/package_id/timestamps, replaced with a nested `course: {id, course_name}`), `courses_count` (from the controller's `withCount(['courses'])` eager-load), `enrollments_count` (`$this->enrollments->count()` — a full collection count on an eager-loaded, `groupBy('student_id')`-collapsed relation, i.e. this actually counts **distinct enrolled students**, not raw enrollment rows, because the `index()` call site's own eager-load closure groups by `student_id` before this resource ever sees the collection).

### `GET /v1/packages/{package}` — `show($id)`
- **Not-found:** `$this->apiResponse([], 'Package Not Found', 'error', 404)` — correct argument order, genuinely returns HTTP 404.
- **Success:** `$this->apiResponse(['package' => PackageShowResource::make($package)])` — default `message: 'Success'`, `status: 'success'`, 200.
- **`PackageShowResource` shape:** all raw columns except `created_at`,`updated_at`,`deleted_at`,`created_by`,`updated_by`, plus `course_categories` (`CourseCategoryTreeResource::customCollection(...)` — every `CourseCategory` that has at least one course, annotated against this package's own mapped course ids; that resource's own tree-building logic belongs to the `CourseCategory` module, not re-derived here), `creator` (`{id,first_name,last_name}`, **no null-safe operator** — if `created_by` ever points at a deleted/missing user, this line throws rather than degrading to `null`), `updater` (same shape, **with** a null-safe `?->`, so a package that's never been updated returns `updater: null` cleanly).

### `POST /v1/packages` — `store(Store $request)`
- **FormRequest (`Store`):** `name` required string max:255; `duration_days` required integer; `courses` nullable array; `courses.*` integer `exists:courses,id` (custom message on failure: `"Course id does not exist in the database"`).
- ⚠️ **Likely bug, not independently executed to confirm the exact runtime error:** the controller resolves course names for the activity-log description **unconditionally and before** the `if ($request->has('courses'))` check inside the transaction: `Course::whereIn('id', $request->courses)->get('course_name')`. Since `courses` is `nullable` per the FormRequest, a fully valid request that simply omits `courses` makes `$request->courses` resolve to `null`, and Laravel's query builder `whereIn()` internally expects an array/Arrayable — passing `null` is very likely to throw a `TypeError` (PHP 8 no longer silently coerces `null` to an empty array in this context). **Worth a dedicated boundary test: `POST /v1/packages` with `name`+`duration_days` only, no `courses` key at all.**
- **Behavior** (inside `DB::transaction`): creates the `Package` row (`name`,`duration_days`,`created_by`), then if `courses` was sent, creates one `PackageCourseMapping` row per course id (no dedupe check — duplicate ids in the array create duplicate mapping rows). Writes one `Activity::create()` row directly (`log_name: 'Package Added successfully'`, description includes the package name/duration/comma-joined course names as raw HTML with literal `<br>` tags embedded in the stored string, `causer_type: null` — bypasses the `activity()` helper the same way `Bootcamp`'s equivalent calls do).
- **Success:** `$this->apiResponse(['package' => PackageResource::make($package)], 'Package is created successfully', statusCode: 201)`.
- **Cache side effect:** the `Package` model's `static::saved()` boot hook (`Modules/Package/Entities/Package.php`) forgets and eagerly re-populates a process-wide `Cache::rememberForever('all_packages', ...)` key on every save — this is what backs `searchPackages()` below, so a create here is immediately visible to `search`/`get-packages` without a stale-cache window.

### `PUT/PATCH /v1/packages/{package}` — `update(Update $request, $id)`
- **FormRequest (`Update`):** identical rule set to `Store` — `name`/`duration_days` required (not relaxed to `sometimes`/`nullable` on update), `courses` nullable array of `exists:courses,id` ints.
- **Not-found:** same `apiResponse([], 'Package Not Found', 'error', 404)` shape as `show`.
- ⚠️ **Same latent `courses`-omission risk as `store`:** `$currentCourse = $request->courses; $requestedCourse = Course::whereIn('id', $currentCourse)->get(...)` runs unconditionally (outside any `has('courses')` guard) purely to compute an activity-log diff — an update request that validly omits `courses` passes `null` into `whereIn()` here too.
- **Behavior:** fetches the package's **previous** state (`$package = $this->packageRepo->findById($id)`, read *before* any writes — used later purely for the "previous" values in the activity-log description) and its previous course-id list; inside `DB::transaction`, updates `name`/`duration_days`/`updated_by`, and if `courses` was sent, **deletes all existing `PackageCourseMapping` rows for this package and recreates them from the request** (`deleteAllRecordsWithId($id)` then one `create()` per id) — a full replace, same pattern as `Bootcamp`'s book-mapping update, not a merge/diff at the DB level (the added/removed diff is computed **separately**, only for the activity-log text, via `array_diff` against course *names*).
- **Side effect — queued job:** `PackageUpdateStudent::dispatch($request->all(), $id, $this->enrollmentRepo, $this->packageCourseMappingRepo, $userEmail)` (queue unspecified, defaults to the standard queue). For every **active** (`Enrollment::ACTIVE`) student currently enrolled in this package (grouped by `student_id`, chunked 50 at a time), and for every course id in the **submitted** `courses` array not already matched by an existing `type=2` (package) enrollment for that student+course+package, creates a brand-new package-type `Enrollment` (with computed `passing_criteria`). **This is purely additive** — a course *removed* from the package's mapping is never used to deactivate/remove any student's existing enrollment in that course; students keep access to courses dropped from the package definition. Any exception inside the job's `handle()` is caught and only `Log::error()`'d — the job reports as completed to the queue regardless, and the completion event below is simply never fired in that case (silent partial failure, no retry, no visible error to the admin who triggered the update).
- **Side effect — event/email:** on successful completion of the loop, fires `PackageUpdateStudentCompleted($userEmail)`, handled synchronously-within-the-listener by `SendPackageUpdateEmailNotification` → `Mail::to($userEmail)->send(new CourseAndAssignmentsToStudentForPackageUpdate())` (a **`send()`, not `queue()`**, inside an otherwise-queued listener) — sent to the **acting admin's own email** (`auth()->user()->email`, captured before dispatch), not to the affected students, despite the mailable's name suggesting a student-facing notice.
- **Activity log:** `Activity::create()` (`log_name: 'Package Updated Successfully'`, description embeds previous name/duration plus comma-joined added/removed course names computed via `array_diff`, same `causer_type: null` / bypass-the-helper pattern as `store`).
- **Success:** `$this->apiResponse(['package' => PackageResource::make($this->packageRepo->findById($id))], 'Package updated successfully, Now the students of this package will be enrolled with these new courses are in queue.you will get a mail when this is completed')` — note the literal grammar/spacing in the message string, preserved verbatim. **The response returns before the queued job runs** — per `_COMMON_CONVENTIONS.md`'s cross-cutting caution, a 2xx here only confirms the package row/mapping itself was updated, not that any student enrollments have been created yet; poll/wait or check for the completion email before asserting on student-side effects.

### `DELETE /v1/packages/{package}` — `destroy($id)`
- **Not-found:** same `apiResponse([], 'Package Not Found', 'error', 404)` shape.
- **Behavior:** inside `DB::transaction`, deletes all `PackageCourseMapping` rows for this package, then deletes the `Package` itself (`SoftDeletes` — a soft delete, not a hard row removal, since the `Package` entity uses the `SoftDeletes` trait).
- ⚠️ **No activity log is written on delete** — unlike `store`/`update`, which both write an explicit `Activity::create()` row, `destroy()` has no equivalent; a deletion leaves no audit trail via this mechanism, only whatever Spatie's own model-event auto-logging (if configured elsewhere) might separately capture.
- **Cache side effect:** the model's `static::deleted()` boot hook refreshes the `all_packages` cache key the same way `saved()` does.
- **Success:** `$this->apiResponse([], 'Package deleted successfully')`.

## `GET /v1/search/packages` (route name `packages.search`)
- **Controller method:** `search()`.
- **Behavior:** `$this->packageRepo->searchPackages()` — reads from a **cache-backed** all-packages list (`Cache::rememberForever('all_packages', ...)`, `select(['id','name'])`), then filters **in-memory** (not via a DB query) if `search` is present: `stripos($package->id, $search) !== false || stripos($package->name, $search) !== false`. The cache is kept fresh by the `Package` model's `saved`/`deleted` boot hooks (see `store`/`update`/`destroy` above), so this does **not** exhibit a stale-data bug under normal use — but note `searchPackages()` is called **twice** at this call site (once for the collection, once again just to `count()` it for `meta.total`) — a redundant duplicate cache-read/in-memory-filter, not a correctness bug, just wasted work.
- **Success:** `SearchPackageResource::collection(...)->additional(['meta' => ['total' => <int>]])` — resource-collection pagination family. `SearchPackageResource` shape: `{id, name}` only.
- **Cross-module cross-check (per task instruction):** `StudentDashboardManagement.md` documents `GET /v1/get-packages` (registered in *that* module's own route file) as delegating to this exact method. **Confirmed accurate** — `PackageController::search()` as read here matches that description exactly, including the "called twice" redundancy and the identical `{"data":[...],"meta":{"total":N}}` shape. No discrepancy found.

## `GET /v1/search/packages-with-courses` (route name `packages.with-courses.search`)
- **Controller method:** `searchPackagesWithCourses()`.
- **Behavior:** `$this->packageRepo->searchPackagesWithCourses()` — a **live DB query** (not the cached list), filtered by `search` (`LIKE` on `id`/`name`, same doubled-`%` quirk as `index`), restricted to `whereHas('courses')` (only packages with at least one mapped course), `limit(10)` (hardcoded, no offset/pagination param at all).
- **Success:** `$this->apiResponse($data)` — plain `apiResponse()` envelope wrapping a flat `[{"id","name"}, ...]` array (raw model attributes, not a Resource) — a **different shape** from `search/packages` above despite similar naming/purpose.

## `GET /v1/search/specific-packages` (route name `packages.specific.search`)
- **Controller method:** `searchPackagesWithArray()`.
- **Request params (query):** `search` — expected array of package ids; guarded by `request('search') && request('search') !== ''` (an odd double-check: a non-empty array is always truthy, so the `!== ''` half only matters if `search` were sent as the literal empty string, which an array parameter normally wouldn't be) before `whereIn('id', request('search'))`.
- **Success:** `$this->apiResponse($this->packageRepo->searchPackagesWithArray())` — plain `apiResponse()` envelope, flat `[{"id","name"}, ...]` raw-attribute array.

## `GET /v1/export/package`
- **Controller method:** `export(Request $request)`.
- **Request params:** `Validator::make($request->all(), ['data' => ['nullable','array']])` — only `data` validated; everything else passed through unvalidated.
- **Behavior:** fire-and-forget — dispatches `PackageCSVDownload::dispatch($request?->user(), $request?->all(), $data['data'] ?? [])->onQueue('default_medium')`.
- **Success:** `apiResponse('', 'Package Csv file exporting started')` — note this call uses the **global** `apiResponse()` helper function, not `$this->apiResponse()` — the only endpoint in this controller that does so (every other endpoint in this file uses the instance method); both produce an identical shape per `_COMMON_CONVENTIONS.md`, so no behavioral difference, just a call-site inconsistency worth knowing about.
- **Side effects (traced from `PackageCSVDownload::handle()`):** builds a CSV (`Package Name`, `No of Enrollments`, `No of Course`, `Duration` columns — `No of Enrollments` counts **distinct students**, since the job's own `getPackage()` query eager-loads `enrollments` with the same `groupBy('student_id')` collapse as `index()`) directly against `storage_path('tmp/')`, uploads it to S3 under `exports/tmp/package/`, deletes the local temp file, then **synchronously** (`Mail::send`, not `queue`) emails `PackageCSVCompletedMail` (with the S3 download URL) to the requesting admin's own email. A test must poll for this email / the S3 object rather than expecting a synchronous file in the HTTP response itself.

## `GET /v1/packages/{package_id}/activity` (route name `packages.activity`)
- **Trait method (`PackageTrait`):** `activity($id)`.
- **Not-found:** `apiResponse([], 'Package Not Found', 'error', 404)` — correct argument order, genuine HTTP 404 (same pattern confirmed for `Bootcamp`'s equivalent — no apiResponse argument-order bug in this module).
- **Found:** delegates to `App\Http\Traits\ActivityLog::logOfPackage($id, ['id','description','causer_id','event','created_at'])` — cursor-paginated `Activity` listing filtered to `subject_type = Modules\Package\Entities\Package::class`, `subject_id = $id`. Same shape as `Bootcamp`'s activity endpoint: `ActivityResource::collection($paginator)->additional(['meta' => ['next_page_url','prev_page_url','range']])`.

## Summary

- **Endpoint count:** 6 route registrations — 1 `apiResource` line (5 REST routes, all genuinely implemented, unlike `Notification`) + 5 explicit named routes. **11 total reachable endpoints**, all live/functioning.
- **Structural surprises / bugs worth flagging for parity testing:**
  1. `PackageTrait::__construct(Excel $excel)` never actually runs — shadowed by `PackageController`'s own constructor; `$this->excel` is always unset. Currently harmless (nothing reads it) but a landmine for future changes to this trait.
  2. Both `store()` and `update()` unconditionally run `Course::whereIn('id', $request->courses)` **before** checking whether `courses` was actually sent, even though the FormRequest marks `courses` as `nullable` — a fully valid "no courses" request is likely to throw a `TypeError` on the `whereIn()` call. Not independently executed to confirm the exact exception, but the type mismatch is real; flagged as a high-value boundary test (`POST`/`PUT` with `name`+`duration_days` only).
  3. `update()`'s course-mapping change is a **full delete-and-recreate**, not a merge, and separately triggers `PackageUpdateStudent` which is **additive-only** for existing students (never removes access to a course dropped from the package) — two different "replace vs. merge" semantics coexisting in one endpoint, worth distinguishing carefully in any test asserting on post-update student enrollments.
  4. `PackageUpdateStudentCompleted`'s listener emails the **acting admin**, not affected students, despite the mailable class name (`CourseAndAssignmentsToStudentForPackageUpdate`) suggesting otherwise.
  5. `destroy()` writes no activity-log entry, unlike `store`/`update` in the same controller.
  6. `search/packages`, `search/packages-with-courses`, and `search/specific-packages` return **three different response shapes** for superficially similar "give me a short package list" needs — resource-collection-with-meta, plain-apiResponse-flat-array, and plain-apiResponse-flat-array respectively (the latter two share a shape with each other, but not with the first).
  7. Cross-module cross-check against `StudentDashboardManagement.md`'s `GET /v1/get-packages` claim: **confirmed accurate**, no discrepancy.
- **Confidence:** High — `PackageController` (all methods), `PackageTrait`, `PackageRepository`, `PackageCourseMappingRepository` (existence/signature of `deleteAllRecordsWithId` confirmed), the `Package` entity's cache-invalidating boot hooks, `Store`/`Update` FormRequests, and all four Resources (`PackageResource`, `PackageShowResource`, `SearchPackageResource`, `PackageCourseMappingResource`) were read in full. `PackageUpdateStudent`'s job body and its listener were read for the side-effect summary (not transcribed line-by-line beyond what's needed to characterize the additive-only/admin-email behavior).
