# Permission Module API Documentation

The `Permission` module is a **read-only** surface over `spatie/laravel-permission`-backed `Permission` records (`Modules/Permission/Entities/Permission`) — a flat/full listing, a parent-only listing shaped for the role-creation UI, and a per-user effective-permissions lookup (with two synthesized pseudo-permission entries layered on top). No create/update/destroy actions exist anywhere in this module — permissions are static/seeded data (see `Modules/Permission/Database/Seeders/PermissionDatabaseSeeder.php`).

**Module-wide auth:** all 3 routes are `auth:sanctum` + `json.response`, prefixed `/api/v1/...`.

See [`./_COMMON_CONVENTIONS.md`](./_COMMON_CONVENTIONS.md) for the app-wide response envelope styles, standard error shapes, and pagination conventions. `PermissionsController` (`Modules/Permission/Http/Controllers/PermissionsController.php`) implements all 3 routed methods directly — no traits.

---

### `GET /v1/permissions` (route name `permissions.index`, `index`)
- **Success response:** bare `PermissionResource::collection($this->permissionRepository->all())` — Laravel's default resource-collection auto-wrap (`{"data": [...]}`), **no `meta`/pagination** — `all()` (inherited from `BaseRepository`) returns every `Permission` row unpaginated in one call.
- `PermissionResource`: raw-merged columns excluding `created_at`/`updated_at`/`pivot`/`created_by`/`updated_by`/`guard_name`, plus `creator`/`updater` (each `{id, first_name, last_name}` or null). **Does not include `children`/`child`** (unlike the other two response shapes in this module) — this is the flat/undifferentiated listing, parent and child permissions returned side-by-side with no nesting.

### `GET /v1/permissions-for-role-creation` (route name `permissions.list-for-role-creation`, `listForRoleCreation`)
- **Success response:** bare `PermissionForRoleCreationResource::collection($this->permissionRepository->allPermissionsWhichAreOnlyParent())` — `{"data": [...]}`, no `meta`. Only permissions with `parent_id IS NULL` are top-level entries here.
- `PermissionForRoleCreationResource`: raw-merged columns (same exclusion list as `PermissionResource`, but note **`creator`/`updater` are NOT included** here — a genuine field-set difference from `PermissionResource` despite both extending the same base pattern), plus `child` (`self::collection($this->children)` — nested nullable-parent's children, recursively resource-wrapped) and **`checked` hardcoded to `false`** for every entry regardless of any actual role/user context — this resource is meant to seed a fresh "create role" form's checkbox tree (nothing pre-checked), unlike `Role.md`'s `PermissionsForRoleResource` (used inside `Role`'s own `store`/`update`/`show`/`index` responses), which computes a real `checked` value against a specific role's assigned permissions. **Do not confuse the two resource classes** — `PermissionForRoleCreationResource` (this module) always reports `checked: false`; `PermissionsForRoleResource` (`Permission` module too, but consumed by `Role`'s endpoints) reports a real boolean.

### `GET /v1/permissions/users/{user?}` (route name `permissions.user.index`, `userPermissions`)
- **Request params:** `{user}` is an **optional** path segment (`{user?}`) — a raw id, not route-model-bound (`findById($id)` called manually). If omitted entirely, defaults to `auth()->user()->id` (i.e. "my own permissions").
- **Error response:** `$this->apiResponse([], 'User Not Found', 'error', 404)` if the id (when provided) doesn't resolve to a `User` via the repository.
- **⚠️ Not the standard envelope at all** — success response: `apiResponse(['permissions' => {...}, 'redirect_url' => '...'])` → full shape `{"data":{"permissions":{"<parent_name>":["<child_name>", ...], ...},"redirect_url":"..."},"message":"Success","status":"success"}`. `permissions` is a **map keyed by parent-permission name** (not a list) whose values are arrays of the target user's assigned **child**-permission names under that parent — a parent with zero assigned children for this user is **omitted from the map entirely** (not present with an empty array). `redirect_url` = `$permissions->first()->display_endpoint ?? ''` — the `display_endpoint` of **whichever permission happens to be first** in the target user's full `getAllPermissions()` collection (order not guaranteed/filtered to be meaningful — e.g. not necessarily the first *parent* or any particular priority permission), falling back to an empty string if the user has zero permissions at all.
- **Synthesized pseudo-entries, not backed by real `Permission` rows:**
  - `permissions.lms` → present (as `{"lms": ["lms"]}`) **iff `auth()->user()->edmingle_id` is non-null** — note this check is against the **authenticated caller's** `edmingle_id`, not the target `{user}` being looked up. **When an admin looks up a different user's permissions (`{user}` provided and differs from the caller), this `lms` entry reflects the caller's own LMS-linkage status, not the target user's** — a genuine cross-user data-leak/bug worth a dedicated parity test (call as admin A looking up user B, where A has `edmingle_id` set but B does not, and confirm `lms` appears anyway).
  - `Schedule_My_Meeting_Managment` → **removed** from the map (`unset()`) unless **the caller's own** `meeting_id` is non-null **and** `meeting_status === 'Completed'` — same caller-vs-target bug as above: this check also reads `auth()->user()->meeting_id`/`meeting_status`, never the target `$user`'s. If the underlying `Permission` table happens to have a real row named `Schedule_My_Meeting_Managment` that the target user was actually assigned, this code can still strip it from the response based purely on the *caller's* meeting status.
- **Notes:** confirms and sharpens `documentation/API_SPECIFICATIONS.md`'s existing note on this endpoint — that doc flagged the two synthesized entries but did not identify that **both of their gating conditions read `auth()->user()` instead of the resolved `$user`**, a bug that only manifests when `{user}` is explicitly provided and differs from the caller. When `{user}` is omitted (caller checking their own permissions), the bug is unobservable since caller and target are the same row.

## Summary

**Routes documented:** all 3 routes in `Modules/Permission/Routes/api.php`. No create/update/destroy exist — confirmed read-only, matching `documentation/API_SPECIFICATIONS.md`'s existing framing.

**Notable bugs/discrepancies found:**
- `userPermissions`'s two synthesized pseudo-permission entries (`lms`, `Schedule_My_Meeting_Managment`) both gate on `auth()->user()`'s own `edmingle_id`/`meeting_id`/`meeting_status` rather than the resolved target `$user`'s — when an admin looks up another user's permission set via `{user}`, these two entries reflect the **caller's** LMS/meeting-scheduling state, not the target's. This is a sharper, previously-unstated finding beyond what `API_SPECIFICATIONS.md` already flagged (it noted the synthesis but not the wrong-actor bug).
- `PermissionResource` (flat `index` listing) and `PermissionForRoleCreationResource` (parent-only listing) have divergent field sets despite superficial similarity — the former includes `creator`/`updater`, the latter includes `child`/`checked` instead; neither is a superset of the other.
- `PermissionForRoleCreationResource.checked` is unconditionally `false` — a client must not read this field as reflecting any real role/user state; it exists purely as a fresh-form-default placeholder, contrasted with `Role` module's `PermissionsForRoleResource.checked`, which is a real computed boolean against a specific role.
- `redirect_url` in `userPermissions`'s response depends on collection-ordering of `getAllPermissions()`, which is not documented/guaranteed to be stable or meaningful — treat as effectively arbitrary unless the underlying query is confirmed to have a deterministic order.

**Confidence:** High — every endpoint read directly from `PermissionsController.php` (full file, all 3 methods), `PermissionResource.php`, `PermissionForRoleCreationResource.php`, and the relevant `PermissionRepository`/`BaseRepository` methods. The caller-vs-target bug in `userPermissions` was independently verified by re-reading the exact `auth()->user()` calls line-by-line against the resolved `$user` variable — it is not inferred from behavior, but confirmed from the literal source.
