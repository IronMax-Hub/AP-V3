# Result Module — API Documentation

The `Result` module owns the `results` table — one row per submission-and-grading cycle of a `StudentAssignment` (see `StudentAssignment.md`), including scores (`ResultExerciseScore` children), evaluator assignment, plagiarism data, and the "featured assignment" showcase mechanism. It is the terminal stage of the grading workflow: `StudentAssignment::submit()` creates a `Result` row, this module scores/finalizes it, and finalization writes back `StudentAssignment.status`. See [`./_COMMON_CONVENTIONS.md`](./_COMMON_CONVENTIONS.md) for app-wide envelope/error/pagination conventions — this file only calls out deviations.

**Module-wide auth:** all routes are `auth:sanctum` + `json.response`, prefix `v1` — **except one**: `GET /v1/results/file/download/{result}` is registered in its **own route group with no middleware at all** (not even `json.response`) — confirmed by reading `Modules/Result/Routes/api.php` directly: the `downloadFile` route sits in a bare `Route::prefix('v1')->group(...)` block, entirely separate from the `auth:sanctum` group every other route in this file belongs to. **This means any unauthenticated caller who can guess/enumerate a `{result}` id can download that student's submitted assignment file** — a genuine authorization gap worth a dedicated security-boundary test, not just a functional one.

**Class layout:** `ResultController` implements `index`/`store`/`update` directly; it `use`s `ResultTrait` (`Modules/Result/Http/Traits/ResultTrait.php`) for every other routed method (`export`/`downloadFile`/`download`/`getAllEvaluatorDetails`/`getEvaluatorPendingDetails`/`assignEvaluatorSingle`/`assignEvaluatorRoundRobin`/`addToFeatureList`/`removeFromFeatureList`/`sendMail`/`activity`), and `App\Http\Traits\ActivityLog` for `logOfResult()`.

## `GET /v1/results/file/download/{result}` — `downloadFile()` (trait method — **unauthenticated, see module-wide note above**)
- Route-model-bound `Result`; a binding miss produces the standard 404 `ModelNotFoundException` shape.
- Derives the S3 object key by stripping a hardcoded `https://{AWS_BUCKET}.s3.{AWS_DEFAULT_REGION}.amazonaws.com/` prefix off `result.submitted_file` — if the stored URL doesn't start with exactly that prefix (e.g. a CDN-fronted or differently-formatted URL), the "stripped" path is actually the whole original URL, and the subsequent `Storage::disk('s3')->getMetadata()` call will simply fail to find it.
- **Error responses:** `response()->json(['message' => 'File not found.'], 404)` if the S3 object doesn't exist; `response()->json(['message' => 'Failed to retrieve metadata for the file.'], 404)` if metadata retrieval otherwise fails — both **bespoke shapes with only a `message` key**, no `data`/`status` at all, distinct from every convention in `_COMMON_CONVENTIONS.md`.
- **Success response:** raw binary file stream (`Response::make($fileContents, 200, $headers)`) — **not JSON at all** — with `Content-Type` from S3 metadata and `Content-Disposition: attachment; filename="{student_full_name}_{result.assignment_id}_{original_filename}.{ext}"`.

## Core CRUD (`Route::apiResource('results', 'ResultController')`)

### `GET /v1/results` — `index()` (controller)
- Query: `rows` (default 15). Same "simple vs. filtered" branching pattern as `StudentAssignment::index()` (see `StudentAssignment.md`): no params (beyond `rows`/`cursor`) → a fixed narrow column list; any other query param present → `['*']` (all columns) — but **unlike `StudentAssignment`, both branches use the same `ResultResource` class** (no "Old" vs. "new" resource split here).
- **Success response:** `ResultResource::collection($data)->additional(['meta' => [...]])` where `meta` = `{submitted, evaluated, backlog, next_page_url, prev_page_url, range: {from,to,total}, evaluator: <bool>}`. **`submitted`/`evaluated`/`backlog` are computed via separate unfiltered repository calls** (`allWithSearchSubmittedCount()` etc.) — verify whether these respect the same search/filter params as the main listing or are always global totals; the naming pattern elsewhere in this codebase (e.g. `NPS`'s page-vs-global aggregate distinction, see `NPS.md`) suggests this is worth an explicit check rather than an assumption. `evaluator` is a boolean — `true` if the **calling user's** first Spatie role name is literally `"Evaluator"` — a per-request, per-caller flag embedded in a listing response's `meta`, not a property of the data itself.
- `ResultResource` fields include (not exhaustive — see source for full list): `status` (`'Backlog'`/`'Evaluated'`/`'Submitted'`, derived from `status` + whether `now() > evaluation_due_date`), `marks_deduction` (0.5/day capped at 3, computed from days between `submitted_date` and the student assignment's `submission_last_date`), `evaluator` (`{first_name, last_name, pending_count}` — **`pending_count` requires the `evaluator_results as pending_assignments`/`backlog_assignments` counts to have been eager-loaded** by the specific relation closure `index()` sets up; calling this resource from a context that doesn't load those counts would throw), and a typo'd key **`defult_evaluator`** (missing the "a" — literal, verbatim from source, alongside the correctly-spelled `default_written_evaluator` next to it) holding the course's default subjective evaluator.

### `POST /v1/results` — `store()` (controller) — direct `Result` creation, distinct from `StudentAssignment::submit()`'s implicit `Result` creation
- **Request body** (`StoreResultRequest`): `student_id` required `exists:students,id`; `assignment_id` required `exists:student_assignments,id` (confirms the FK-naming trap: this column really references `StudentAssignment`, not `Assignment`, at both the DB and validation layer — see `API_SPECIFICATIONS.md` §4's original note); `plagiarism_result` optional int 1–100; `plagiarism_result_file` required only if `plagiarism_result` present, URL; `submitted_file` required URL.
- **Behavior (`createResult()`, trait):** re-validates the same 5 fields via an inline `Validator::make()` inside the trait method — **redundant with `StoreResultRequest`'s own automatic validation**, which has already run by the time the controller method body executes; both use identical rules, so this second pass is dead weight rather than a source of divergent behavior, but it does mean any custom messages/order from `StoreResultRequest` never actually surface (the trait's plain `Validator::make(...)->validate()` throws its own generic-shaped `ValidationException` first — actually **`StoreResultRequest`'s own type-hinted validation runs first**, before the controller method body — so in practice the trait's inline validator can only ever re-confirm already-valid data; it's unreachable as a source of a *different* validation error).
- ⚠️ **Cross-module inconsistency in evaluator defaulting — confirmed by comparing this method against `StudentAssignment::submit()`:** `createResult()` branches on `assignment_type` — subjective → `course.default_evaluator_id`, written → `course.default_written_evaluator_id`. **`StudentAssignment::submit()`'s own inline `Result` creation (see `StudentAssignment.md`) always uses `course.default_evaluator_id`, regardless of assignment type** — there is no branch there for written assignments. This means a `Result` row created via this endpoint (`POST /v1/results`) can get a different default evaluator than one created via the student-submission flow, for the same course and a written-type assignment. A parity test comparing "evaluator defaulting logic" must treat these as two independently-implemented rules, not one shared one.
- **Success response:** `apiResponse(['result' => ResultResource::make($result->fresh())], 'Result created successfully', statusCode: 201)`.
- **Side effects:** `submitted_date`/`evaluation_due_date` (`+7 days`, `23:59:59`) computed server-side, ignoring any client-supplied value (not even accepted by the FormRequest); one `ResultExerciseScore` per exercise (`full_marks` = `request['total_marks']` if `> 0`, else 10 — note `total_marks` is **not validated by `StoreResultRequest` at all**, so a client can send an arbitrary unvalidated value here, or omit it for the default); if `plagiarism_result > 40`, immediately sets `Result.status → RESUBMIT` and `StudentAssignment.status → STATUS_RESUBMITTED` inline (no email queued from this path, unlike the resubmission flow in `StudentAssignment::re_submit()`); writes a raw `Activity::create()` (`log_name: 'Result  creation'` — **note the double space in `'Result  creation'`, literal from source**, subject = `Result`, `causer_type: null` alongside a real `causer_id` — the same causer-type-null inconsistency documented in `Enrollment.md`).

### `PUT/PATCH /v1/results/{result}` — `update()` (controller) — scoring/feedback, step 1 of grading finalization
- **Request body** (`UpdateResultRequest`, multipart): `_method` required literal `PUT`/`PATCH`; `scores` optional array of `{serial_number: required int 1–10, obtain_marks: required numeric}`; `feedback_file` optional file (no mime/size restriction in the FormRequest itself); `waive_marks` optional boolean; `feedback_edit_reason` optional string.
- **Guards:** 403 `"Cannot update result. Student is inactive."` if `result.student.status != 1`; 403 `"Cannot update result. Enrollment is inactive."` if `result.student_assignment.enrollment.status != 1` — both correctly return the intended status code (4-argument `apiResponse()` calls, not subject to the positional-arg bug).
- **Behavior:** `feedback_file`, if uploaded, is renamed server-side to `{slugified_student_name}_{admin_user_id}_{time}.{ext}` — **the client's original filename is discarded for the storage key**, though `feedback_file_original_name` is set to this *same* server-generated name (not the client's actual original filename — the variable is misleadingly named; verify directly if a parity test needs the true original filename preserved anywhere, since it appears not to be). `waive_marks` is stored as the literal integer `3` if truthy, else `null` (not a plain boolean) — same non-boolean-storage convention noted for other modules in this codebase.
- **Resubmission gate** (only if `scores` present and `scores[0]` is not null — accessing `scores[0]` directly means an explicitly-empty `scores: []` array triggers a PHP "undefined array key" warning, not a clean skip, though the `!is_null(...)` check on the resulting `null` still correctly skips the block): only evaluated for **subjective** assignments (`assignment_type == TYPE_SUBJECTIVE`) — checks if *any* score's `obtain_marks < 4`; if so, `Result.status → RESUBMIT` + `reason → REASON_NEW_4` ("Based on Evaluator Feedback"), `StudentAssignment.status → STATUS_ACTIVE` + `submit_counter += 1`, queues `ResultFeedbackFileMail` to the student, and returns early: `apiResponse([], 'Resubmit Functionality activated!', 'success')` — grading stops here, matching `API_SPECIFICATIONS.md`'s documented behavior. **Skipped entirely for written assignments**, exactly as previously documented.
- **Score writes (non-resubmit path):** per score entry, `obtain_marks == 101` is a sentinel that clears the score to `null` (confirmed exact behavior); any other value writes it as-is, with **no bounds/range check against the exercise's `full_marks`** at this layer — a client can submit `obtain_marks` far exceeding `full_marks` and it will persist unmodified.
- **Normal success response:** `apiResponse(['result' => ResultResource::make($result->fresh())], 'Result updated successfully')` — `StudentAssignment.status` is **not** touched on this path, matching `API_SPECIFICATIONS.md`'s note that finalization is a separate step.
- **Side effects (always, regardless of scores branch outcome):** writes an `Activity::create()` (`log_name: 'Result  updation'` — again a literal double space — `properties: {feedback_edit_reason}`, `causer_type: null`).

### `GET /v1/results/{result}` and `DELETE /v1/results/{result}` — `apiResource`'s `show`/`destroy` — **confirmed broken, no method exists**
Neither `ResultController` nor `ResultTrait` implements `show()` or `destroy()` — confirmed by grepping both files in full. Calling either route triggers a PHP fatal `Error: Call to undefined method`, surfacing as an uncaught **500** — the same broken-`apiResource` pattern documented repeatedly elsewhere in this codebase (`NPS`, `AssignmentTag`, `AssignmentSendingLog`, `StudentAssignment`).

- **Side effects:** dispatches `ResultCSVExport` on queue `default_high` — verify the job's own started/completed mail pattern directly if precise email-timing assertions are needed; not traced further here as out of this file's primary scope (job internals live under `Modules/Result/Jobs/`).

- **Success response:** `apiResponse([], 'Zipping started')`.
- **Side effects:** dispatches `ResultZipDownloadJob` on queue `default_medium`, passing the raw `resultRepo` instance and all query params — fire-and-forget; separate `ResultZipStarted`/`ResultZipCompleted` notification classes exist in `Modules/Result/Notifications/`, implying a started+completed dual-signal pattern similar to other export flows in this codebase — verify the job body directly for exact trigger conditions if needed.

## `GET /v1/results/get-evaluator-pending-details/{evaluator_id}` — `getEvaluatorPendingDetails()` (trait method)
- Path param `evaluator_id` — plain value, not route-model-bound; no existence check before use — a nonexistent id yields `'evaluator' => null` from `EvaluatorDetailsResource::make(null)` plus zeroed/empty counts from the repository calls, not a 404.
- **Success response:** a **bare PHP array, returned directly from the controller with no `apiResponse()`/`response()->json()` wrapper at all**: `{"evaluator": {...}, "pending_assignment": N, "backlog_assignment": N, "total_assignment": N}` — Laravel auto-serializes this to JSON with **no `data`/`message`/`status` envelope whatsoever**, matching the bespoke-shape pattern seen in `AssignmentTag`'s `search()` (see `AssignmentTag.md`).

## `GET /v1/results/get-all-evaluator-details/{course}` — `getAllEvaluatorDetails()` (trait method)
- Route-model-bound `Course`; standard 404 on a binding miss.
- **Success response:** `apiResponse($evaluators, 'Successful')` — `$evaluators` is a plain array of `{pending_assignment, backlog_assignment, total_assignment, evaluator: <EvaluatorDetailsResource>}`, one per user id in the union of `course.evaluators` (a pivot relation) plus `course.default_evaluator_id`/`default_written_evaluator_id` — **evaluators appear here even if they only hold one of those three roles for this specific course**, not just the pivot-mapped ones.

## `POST /v1/results/assign-evaluator-single/{result_id}` — `assignEvaluatorSingle()` (trait method)
- Path param `result_id` — plain value, not route-model-bound; `Result::find($result_id)` with **no null-check before dereferencing `$results->student`** — a nonexistent `result_id` causes an unguarded "attempt to read property on null" fatal error (uncaught 500), not a clean 404, despite the guards below appearing to defensively check student/enrollment status.
- **Request body:** inline `Validator::make()`: `evaluator_id` required `exists:users,id`; `change_all` — read directly off the request with no validation rule at all (truthy/falsy check only).
- **Guards:** same two 403s (`"Cannot update result. Student is inactive."` / `"...Enrollment is inactive."`) as `update()`/`sendMail()`.
- **Behavior, `change_all` truthy branch:** reassigns **every** `Result` currently on the *same evaluator* as the target result where `is_review_done == 0` — i.e. every pending review for that evaluator, not scoped to this result's course/topic/anything else — to the new evaluator. ⚠️ **Latent undefined-variable bug:** if `$result->evaluator_id` is falsy (e.g. `null` — an unassigned result), the inner `if ($result !== null && $result->evaluator_id)` block is skipped entirely, so `$affectedResultIds` and `$update` are **never initialized** — the subsequent `if ($update)` check then references an undefined variable, which in PHP 8 raises a `Warning: Undefined variable $update` (not fatal) and evaluates the falsy branch, silently falling through to the single-result reassignment below instead of erroring — a genuinely confusing but non-fatal path, not a clean rejection.
- **Success response (`change_all` branch):** `apiResponse([$update], 'All pending Assignments assigned to new Evaluator successfully', 'success')` — `data` is an array **containing the raw row-count integer** from the bulk update (`[$update]`, not `$update` itself) — an array-wrapped scalar, not a list of affected ids (those are only in the activity log's `properties`, not the response body).
- **Success response (single-result branch):** `apiResponse([$update], 'Assignment assigned to new Evaluator successfully', 'success')` — same array-wrapped-scalar shape.
- **Error response:** `apiResponse([], 'Something went Wrong', 500)` — ⚠️ **3-positional-arg `apiResponse()` bug**: `500` lands in `$status` (coerced to string `"500"`), `$statusCode` stays at its default **200** — a genuine update failure is reported as **HTTP 200** with `status: "500"` in the body, matching the same bug class already documented in `StudentAssignment.md`.
- **Side effects:** writes one `Activity::create()` per affected result in the `change_all` branch (`event: 'evaluator_bulk_assigned'`, `properties: {new_evaluator_id, previous_evaluator_id}`), or one for the single-result branch (`event: 'evaluator_assigned'`).

## `POST /v1/results/assign-evaluator-round-robin` — `assignEvaluatorRoundRobin()` (trait method)
- **Request body:** inline `Validator::make()`: `evaluator_id` required array, `exists:users,id` (validated as a whole-array `exists` check — Laravel's `exists` rule against an array value checks each element); `result_id` required **without** `current_cond`, array, `exists:results,id`; `current_cond` required **without** `result_id` (any truthy value, no format constraint — its literal content is never used, only its presence/truthiness and the accompanying `course_id` query param matter).
- **Guard:** if `current_cond` is set but no `course_id` query param is present: ⚠️ **another instance of the 3-positional-arg bug** — `apiResponse([], 'Please add filter / search conditions', 403)` — `$status` becomes the string `"403"`, but **`$statusCode` stays at the default 200**. This directly contradicts `API_SPECIFICATIONS.md` §4's claim of a "403" response for this exact condition: **the real, current behavior is HTTP 200** with `status: "403"` embedded in the body — a parity test asserting on the HTTP status code alone will incorrectly treat this rejection as a success.
- **Distribution logic:** two near-identical branches (`current_cond` truthy → apply to **every** result id currently returned by `resultRepo->allResultIds()`, an unfiltered/unpaginated full list, despite the guard's own message implying filters are being respected — verify `allResultIds()`'s own query directly if this scoping matters for a test; else → apply only to the explicit `result_id` array) — both assign `evaluator_id[i % totalEvaluators]` to each result in id order, batched per-evaluator via a single `Result::whereIn('id', $ids)->update(...)` call per evaluator (not per-result).
- **Success response (both branches):** `apiResponse([$response], 'Successfully Added evaluators to assignments', 'success')` — `$response` is itself an array of `{evaluator_id, updated_count, result_ids}` per evaluator, but it's **wrapped in an outer array** (`[$response]`), producing an extra level of array nesting (`data: [[{evaluator_id:...}, ...]]`) beyond what the per-evaluator breakdown alone would suggest — confirm this double-nesting directly rather than assuming `data` is a flat list of evaluator-assignment summaries.
- **Side effects:** one `Activity::create()` per evaluator-group update (`event: 'evaluator_round_robin_assigned'`), **not** one per individual result reassigned.

## `GET /v1/results/add-featured-assignment/{result}` — `addToFeatureList()` (trait method)
Route-model-bound `Result`; standard 404 on binding miss.
- ⚠️ **Confirmed broken comparison logic — this endpoint fatal-errors on the code path its own structure implies should be the "normal" one.** `CourseFeaturedAssignmentMappingRepository::getDuplicatFeatureResultId()` returns an **Eloquent Collection** (`->get()`), and the method compares it with `$fetchFeaturedResult != '[]'` — a loose comparison between an **object** and a **string**. Per PHP's comparison rules, an object is never loosely equal to a string regardless of content, so **`$fetchFeaturedResult != '[]'` evaluates to `true` unconditionally**, whether or not any duplicate featured-assignment mapping actually exists. This means:
  - The "duplicate exists, swap the feature flag" branch is **always** taken, never the "no duplicate, create fresh" branch below it (which is therefore **dead code** — unreachable under any input).
  - When a duplicate genuinely **does not** exist (the common case for a topic/course/batch combination being featured for the first time), `$fetchFeaturedResult` is an **empty** Collection, and `$fetchFeaturedResult[0]` (Collection's `ArrayAccess::offsetGet` on a missing key) evaluates to `null` (with a PHP warning), and the subsequent `$fetchFeaturedResult[0]->result_id` access **fatally errors** — "Attempt to read property 'result_id' on null" — an uncaught 500.
  - The endpoint only actually succeeds when a duplicate mapping for that exact topic/course/batch combination already exists in `course_featured_assignment_mapping` — i.e., **the very first time a given topic/course/batch is featured, this endpoint 500s**; only re-featuring an already-featured combination works. This is the opposite of what the code's own branching structure suggests it should do.
- **Success response** (only reachable on the "duplicate exists" path): `apiResponse($updateFeature, 'Successfully Added', 'success')` — `data` is the raw boolean/row-count return of the repository `update()` call.
- **Side effects (on the reachable path):** unsets `feature_assignment` on the previously-featured `Result`, sets it on the current one, and updates the `CourseFeaturedAssignmentMapping` row to point at the new result/assignment.

## `GET /v1/results/remove-featured-assignment/{result}` — `removeFromFeatureList()` (trait method)
- Same `!= '[]'` object-vs-string comparison bug as `addToFeatureList()` above — the "not found" branch (`apiResponse([], 'Error Occured')`, note the literal misspelling "Occured") is **unreachable dead code**; the method always takes the "found" branch, which either succeeds (`apiResponse($updateFeature, 'Successfully Removed', 'success')`) if a mapping genuinely exists, or **fatal-errors** (`$fetchFeaturedResult[0]->id` on an empty Collection) if it does not.

## `GET /v1/results/send-email/{result}` — `sendMail()` (trait method) — finalize grading, step 2 (GET, not POST)
- Same student/enrollment-inactive guards as `update()`/`assignEvaluatorSingle()`.
- **Success response:** `apiResponse('', 'Mail Send Successfully')` — `data` is an empty string; note the grammatically odd "Mail Send" (not "Sent"), verbatim from source.
- **Side effects:** queues `ResultSendMail` to the student (subject data includes all `ResultExerciseScore` rows' `serial_number`/`obtain_marks`); notifies **both** the student (`$result->student->notify(...)`) and the acting admin (`auth()->user()?->notify(...)`) with the same `ResultEvaluated` notification class/payload; sets `Result`: `is_email_sent = EMAIL_SENT`, `is_review_done = REVIEW_DONE`, `status = EVALUATED`, `evaluation_date = now()`; sets **`StudentAssignment.status → STATUS_EVALUATED`** — confirmed, per `API_SPECIFICATIONS.md`, this is genuinely the only place in the codebase this specific transition happens (cross-checked against `StudentAssignment.md`'s full trace of that module — no other write to `StudentAssignment.status = STATUS_EVALUATED` was found anywhere); synchronously invokes `CourseCompletionMasterController::marksheetCalculation($enrollment)`.
- **Dead code:** the `triggerResultEvaluationEvent()` webhook-dispatch call is commented out (`// $this->triggerResultEvaluationEvent($result, 'Result Evaluated');`) — no `WebhookTriggered` event fires on grading finalization today, consistent with every other webhook-trigger call site found dead across the `Assignment`/`StudentAssignment`/`Result` cluster in this codebase.

## `GET /v1/results/{result}/activity` — `activity()` (trait method)
- **Error response:** `apiResponse([], 'Result Not Found', 'error', 404)` if the id doesn't resolve via `ResultRepository::findById()`.
- **Success response:** delegates to `App\Http\Traits\ActivityLog::logOfResult($id, [...])`, which filters `Activity::where('subject_id', $id)->where('subject_type', 'Modules\Result\Entities\Result')` — **unlike `StudentAssignment`'s equivalent `activity()` endpoint (documented as broken in `StudentAssignment.md`), this one is correctly wired**: every `Result`-related activity log in this module (`store()`, `update()`, `assignEvaluatorSingle()`, `assignEvaluatorRoundRobin()`) is written with `subject_type: Result::class` and `subject_id: $result->id`, matching exactly what this endpoint queries — worth calling out as the contrasting *correct* case in the same audit pattern.

## Summary of endpoints documented

**14 route entries** in `Modules/Result/Routes/api.php` (1 unguarded `downloadFile` + the 5-route `apiResource` + 8 further named routes = 14 total):
- **12 live/working**, of which **2 contain confirmed fatal-error bugs on their primary/first-use code path** (`addToFeatureList`, `removeFromFeatureList` — see above) and **1 is unauthenticated by omission** (`downloadFile`).
- **2 confirmed broken** (`apiResource`'s `show`/`destroy` — undefined method, fatal 500).

**Notable findings for parity testing (highest-impact first):**
- **`GET /v1/results/file/download/{result}` has no auth middleware at all** — any caller, authenticated or not, can download a result's submitted file by id.
- **`addToFeatureList()`/`removeFromFeatureList()` both compare an Eloquent Collection to the string `'[]'` with `!=`**, which is always `true` regardless of the collection's actual contents (PHP object-vs-string comparison) — the "no existing record" branch in each method is dead code, and the "record exists" branch fatal-errors when no record actually exists. **The first time any given topic/course/batch combination is featured, `addToFeatureList()` 500s**; only re-featuring an already-featured one succeeds. `removeFromFeatureList()`'s "not found" message (`'Error Occured'`) can never actually be returned.
- **`assignEvaluatorRoundRobin()`'s `current_cond`-without-`course_id` guard, and `assignEvaluatorSingle()`'s generic failure branch, both return HTTP 200 instead of their intended 403/500** due to the same 3-positional-argument `apiResponse()` coercion bug documented throughout this codebase (see `Enrollment.md`, `StudentAssignment.md`) — this directly contradicts `API_SPECIFICATIONS.md` §4's claim of a real 403 for the round-robin guard.
- **Evaluator-defaulting logic differs between `Result::store()` and `StudentAssignment::submit()`'s inline `Result` creation** — the former branches on assignment type (subjective vs. written evaluator), the latter always uses the subjective default regardless of type. Treat these as two independent implementations, not one shared rule.
- **`GET .../activity` is correctly wired here** (contrast with the same-shaped but broken endpoint in `StudentAssignment.md`) — useful as a confirmed-good reference case.
- Two literal typos preserved verbatim in live responses: **`defult_evaluator`** (in `ResultResource`) and the double-spaced **`'Result  creation'`/`'Result  updation'`** activity-log names.
- `getEvaluatorPendingDetails()` returns a bare unwrapped array (no `data`/`message`/`status` envelope) — one more instance of the "no consistent envelope" caution from `_COMMON_CONVENTIONS.md`.

**Cross-module coupling confirmed from this side:**
- `sendMail()`'s `StudentAssignment.status → STATUS_EVALUATED` write is confirmed the sole such transition point in the codebase (cross-checked against the full `StudentAssignment` trace in `StudentAssignment.md`).
- `update()`'s resubmission gate and `StudentAssignment::re_submit()` are two **separate** resubmission-triggering code paths writing to overlapping fields (`Result.status`, `StudentAssignment.status`/`submit_counter`) — a client could in principle race these two independent flows; not evaluated further here as it's a concurrency scenario rather than a single-endpoint contract question.
- `assignEvaluatorSingle`/`assignEvaluatorRoundRobin` are the actual evaluator-(re)assignment logic for the whole grading domain, confirming `API_SPECIFICATIONS.md`'s note that `Evaluator`'s own module (see `Evaluator.md`) is read-mostly master data with no assignment logic of its own.

**Confidence:** High — every endpoint traced to its controller/trait method; the two feature-list fatal-error findings and both `apiResponse()` HTTP-status-coercion bugs were independently verified by reading the exact comparison/call-site code, not inferred from behavior descriptions.
