# RevenueAPI Module — API Documentation

The `RevenueAPI` module is a small, purpose-built integration surface for the external LawSikho revenue/marketing system — distinct from (and much smaller than) the `LawSikho` module's own ingestion gateway. It exposes exactly two endpoints: a student-details lookup (read) and a shared-secret-gated installment-payment webhook receiver (write, queues async reactivation work). No local tables of its own — both endpoints operate on `Student`/`Enrollment` entities owned by other modules. See [`./_COMMON_CONVENTIONS.md`](./_COMMON_CONVENTIONS.md) for the app-wide envelope/error/pagination conventions — this file only calls out where a specific endpoint deviates.

## Module-wide notes

- **Both routes** sit in one group: `Route::middleware(['json.response'])->prefix('v1')`. Neither carries a Laravel auth guard — `handleInstallmentPayment` instead does its own manual shared-secret check inside the controller method (see below); `get_student_details` has no authentication of any kind.
- **Response helper style:** both endpoints use `$this->apiResponse(...)` (the base-`Controller` instance method), consistently — this is one of the few modules in this codebase where the response helper style is uniform across all its routes.
- **This is genuinely a webhook-*receiver*** (the other direction from the outbound webhooks documented in `Webhook.md`) — `handleInstallmentPayment` is called *by* the external revenue system when an installment payment posts, not the other way around.

## `GET /v1/get-student-details`
- **Controller:** `RevenueAPIController::get_student_details`.
- **Auth:** none — genuinely open, no header/token check of any kind. This is a real, verifiable finding worth flagging explicitly for a security-focused parity test (any caller can probe whether an email exists in this system and get back the associated name/phone).
- **Request params:** `email` — query string, read via `$request->has('email')`/`$request->email`; **no format validation at all** (not even a basic email-shape check) before the DB lookup.
- **Behavior:** `Student::where('email', $request->email)->first()`.
- **Success:** `200 $this->apiResponse(['name' => ..., 'phone' => ...], 'success')` → `{"data": {"name": <full_name>, "phone": ...}, "message": "success", "status": "success"}`.
- **Error responses — inconsistent status/message pairing, preserve exactly:**
  - `email` present but no matching student: `$this->apiResponse('Email doesn\'t exist in assignment portal', 'success', statusCode: 422)` → `422 {"data": "Email doesn't exist in assignment portal", "message": "success", "status": "success"}` — ⚠️ **`data` is a bare string here (not an object), and both `message` and `status` read `"success"` despite this being a 422 "not found" response.** A status-code-only *or* a message-only check would both misread this as different things — only the combination of HTTP 422 + `data` being the literal not-found string identifies this branch.
  - `email` missing/empty entirely: `$this->apiResponse('Please enter the email address', 'error', 'error', statusCode: 422)` → `422 {"data": "Please enter the email address", "message": "error", "status": "error"}` — this branch correctly uses `"error"` for both `message` and `status`, unlike the sibling branch above.
- **Notes:** the two 422 branches use the same status code and the same "bare string in `data`" shape but opposite `status`/`message` semantics — a parity test needs to distinguish them by the `data` string's exact content, not by `status`/`message` alone.

## `POST /v1/installment-payment`
- **Controller:** `RevenueAPIController::handleInstallmentPayment`.
- **Auth:** shared-secret header, checked manually in the controller (not middleware) — `hash_equals(config('revenueapi.webhook_secret'), $request->header('X-Revenue-Secret', ''))`. This **is** timing-safe (`hash_equals`, unlike the `===` comparison used for the equivalent LawSikho-module token check). `config('revenueapi.webhook_secret')` resolves from `env('REVENUE_API_TOKEN', <a hardcoded fallback hash checked into Modules/RevenueAPI/Config/config.php>)` — ⚠️ **if `REVENUE_API_TOKEN` is unset in the environment, the secret silently falls back to a hardcoded literal value committed in the repository** (`ba1e0fe419305bc48ccc42002c77d4f9d0229fef4b457f77ac3d1d9142ce3ed6%` at the time of writing) — worth flagging as a secret-management smell even though the code path itself (`empty($secret) || !hash_equals(...)`) does correctly reject when `$secret` is empty.
- **Request params — inline `Validator::make()`, not a FormRequest class:**
  - `student_email` — string, required, `email` format.
  - `enrollment_type` — string, required, `in:course,bootcamp,package`.
  - `course_id` — integer, `required_if:enrollment_type,course`, else nullable, `min:1`.
  - `bootcamp_id` — integer, `required_if:enrollment_type,bootcamp`, else nullable, `min:1`.
  - `package_id` — integer, `required_if:enrollment_type,package`, else nullable, `min:1`.
- **Error responses:**
  - Missing/wrong/empty secret header → `401 $this->apiResponse([], 'Unauthorized', 'error', statusCode: 401)` → `{"data": [], "message": "Unauthorized", "status": "error"}` — checked out logs the attempted secret/incoming value at `Log::error` level (⚠️ logs the **configured secret value itself**, not just the incoming header — a plaintext-secret-in-logs concern, distinct from the hardcoded-fallback concern above).
  - Validation failure → `422 $this->apiResponse([], $validator->errors()->first(), 'error', statusCode: 422)` → `{"data": [], "message": "<first validation error only>", "status": "error"}` — ⚠️ **differs from the app-wide standard 422 shape** (conventions doc): here `message` carries only the *first* error string and `data` is an empty array, with **no `data.errors` object** at all — a client relying on the standard per-field `errors` structure will find nothing there for this specific endpoint.
- **Success:** `200 $this->apiResponse([], 'Payment received. Access reactivation is in progress.')` → `{"data": [], "message": "Payment received. Access reactivation is in progress.", "status": "success"}` — returned **immediately, before any reactivation actually happens**; the real work is queued.
- **Side effects — fully async, `ProcessInstallmentPaymentJob::dispatch($validator->validated())->onQueue('default_high')`:**
  1. Looks up `Student::where('email', $payload['student_email'])->first()`. If not found, calls `$this->fail(new \RuntimeException(...))` — a **permanent job failure, no retry** — and logs an error; the HTTP caller already got a 200, so this failure is only visible via the queue's failed-jobs table/logs, never back to the original caller.
  2. If found and `status !== Student::ACTIVE`, reactivates the student (`status = ACTIVE`) and writes an `Activity::create()` row (`log_name: 'Student Activated'`, `event: 'Student Activated'`, `causer_id: null` — **no causer attribution at all**, unlike most other admin-driven activity logs in this codebase which at least attribute to a hardcoded system user id).
  3. Resolves "pending" enrollments to reactivate via `fetchPendingEnrollments()`: filters `Enrollment` by `student_id`, `status = PENDING`, `deactivation_status = NORMAL_DEACTIVATION`, the `type` matching the payload's `enrollment_type` (`course` → `NORMAL_ENROLLMENT`; `bootcamp` → `BOOTCAMP_ENROLLMENT`; `package` → `PACKAGE_ENROLLMENT` or `PACKAGE_BATCH_ENROLLMENT`), and the relevant id column (`course_id`/`bootcamp_id`/`package_id`) matching the payload's value. **If no student is found, or no pending enrollments match, the job silently ends** (logged, no error) — the HTTP response was already an unconditional 200 "in progress" regardless of whether anything downstream actually matched. This is exactly the "2xx + success body ≠ proof of effect" caution from `_COMMON_CONVENTIONS.md` — a parity test must poll the student/enrollment state afterward, never trust the initial response alone.
  4. For each matching enrollment: sets `status = ACTIVE`, writes an `Activity::create()` row (`log_name: 'Enrollment Activated'`, again `causer_id: null`), and — **only if** the enrollment is not batch-migrated (`is_batch_migrated == BATCH_NOT_MIGRATED`) and has a `batch_id` — calls `assignMissedAssignments()`, which back-fills any assignments the student's active batchmates received while this student was deactivated (found by looking up the most recent `Activity` row logged against the `Student` with `event = 'student deactivated'`, then diffing batchmates' `StudentAssignment` rows created after that timestamp). This entire back-fill step is wrapped in its own `try/catch` — a failure here is logged and swallowed, does not fail the outer job or the enrollment reactivation itself.
  5. Regardless of whether any assignment back-fill ran, dispatches `Modules\Enrollment\Jobs\StudentAddJob::dispatch($enrollments, $payload, [], [], 'Activation', null, ['techteam@lawsikho.in', 'mayukh.b@lawsikho.in'])->onQueue('default_high')` — this is the same job used by the admin-driven student activate/deactivate flow (`API_SPECIFICATIONS.md` §2's `students/activate|deactivate`); it performs a **live Edmingle batch-assignment API call per reactivated enrollment** (via `EdmingleBatchTrait`) and, per its own signature, would send admin-notification emails to the two hardcoded addresses above if any Edmingle assignment failures occur (`$edmingleFailures`) — this job's own `adminEmails` parameter is explicitly empty here, so **no student-facing email is sent from this flow**; only the two hardcoded internal addresses could receive an Edmingle-failure notice, and only via whatever `StudentAddJob` itself does with a non-empty `$edmingleFailures` array (not re-verified line-by-line here — see the `Enrollment` module's own doc/`StudentAddJob` source for that job's exact email-trigger conditions).
- **Retry behavior:** `tries = 3`, `backoff = 60` (seconds) — a transient failure (e.g. a DB blip) retries up to twice more before landing in the failed-jobs table; the explicit `$this->fail()` call for "student not found" bypasses retries entirely (permanent failure).
- **Notes:** Every call (success or failure, before the secret check even runs) is logged via `Log::info('RevenueAPIController::handleInstallmentPayment', ['request' => $request->all()])` — the **entire raw request body**, before any validation, is written to the application log. Combined with the plaintext-secret-on-failure logging noted above, this endpoint's logs are relatively sensitive; a parity/security test should confirm what actually lands in `storage/logs` isn't unexpectedly exposed.

## Endpoint count and confidence

- **2 routes** in `Modules/RevenueAPI/Routes/api.php`, both documented above in full, including their full async side-effect chain (`ProcessInstallmentPaymentJob`).

The one piece not re-verified byte-for-byte in this pass is `StudentAddJob`'s own exact Edmingle-failure-email trigger condition (only its constructor signature was confirmed here) — cross-reference the `Enrollment` module's documentation if a parity test needs that exact behavior.
