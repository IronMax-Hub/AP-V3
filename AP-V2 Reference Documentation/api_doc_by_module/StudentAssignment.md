# StudentAssignment Module — API Documentation

The `StudentAssignment` module owns the `student_assignments` table — the **per-enrollment instance** of an `Assignment` template (see `Assignment.md`), tracking submission status, submit-counter, AI-evaluation config, and the link to `Result` rows created on submission. It is the busiest module in the grading-workflow cluster: individual and bulk assignment creation, student self-service and staff-mediated submission/resubmission, CSV import/export, and dashboard aggregates. See [`./_COMMON_CONVENTIONS.md`](./_COMMON_CONVENTIONS.md) for app-wide envelope/error/pagination conventions — this file only calls out deviations.

**Module-wide auth:** every route except one is `auth:sanctum` + `json.response`, prefix `v1`. **One route deviates:** `POST /student/v1/student-assignments/{student_assignment}/send-link-email` is registered in a *separate* route group at the bottom of the file with `auth:student` + `json.response`, prefix `student/v1` — this is the only student-facing (not staff-facing) route in this module's own file.

**Class layout:** `StudentAssignmentController` is large and implements `index`/`getMetaData`/`store`/`update`/`destroy`/`sendLinkEmail`/`bypass_large_csv_set`/`assignByFilters`/`validateEnrollments`/`updateMultiple`/`bulkEvaluateEdit` directly. It also `use`s `StudentAssignmentTrait` (`Modules/StudentAssignment/Http/Traits/StudentAssignmentTrait.php`, ~1,500 lines) for `import`/`export`/`destroyMultiple`/`submit`/`re_submit`/`getStudentAssignmentResubmissionList`/`studentAssignmentsDashboardData`/`activity`/`createAssignment`/`createStudentAssignment`, and `App\Http\Traits\ActivityLog` for generic activity-log listing helpers.

## ⚠️ Module-wide landmine: the controller's own `updateMultiple()` silently shadows the trait's `updateMultiple()` — two completely different implementations exist for the same method name, and the trait's version never runs
`StudentAssignmentTrait` defines a full `public function updateMultiple(UpdateMultipleRequest $request)` (trait lines 330–469, via a private `workingForUpdatingMultiple()` helper) that resolves/creates a `Topic` from `assignment_topic`, updates it, syncs tags, and mails `StudentAssignmentUpdated` per student assignment. **`StudentAssignmentController` also declares its own `public function updateMultiple(UpdateMultipleRequest $request)` directly on the class body** (controller lines 937–1025) — in PHP, a class's own method definition always wins over a `use`d trait method of the same name, with no error or warning. **The trait's version is 100% dead code; it never executes for the live route.** The two implementations are materially different: the live (controller) version never touches the `Topic` at all and never syncs tags, despite `UpdateMultipleRequest` still validating `assignment_topic` (required) and `tags` — **a client is required to send a topic value that has zero effect, and any `tags` sent are silently ignored** (not synced, not attached, not validated against existing tags beyond the FormRequest's own shape rules). Confirmed by reading both methods in full — this is not a hypothetical, it's the actual live behavior of `PUT /v1/student-assignments/update-multiple`.

## `POST /v1/student-assignments/{student_assignment}/submit` — `submit()` (trait method — **staff-mediated submission**; see `StudentMyCourses`/`API_SPECIFICATIONS.md` §4 for the separate student self-service submission endpoint, `POST /api/student/v1/student-my-courses/submit-assignment/{studentAssignment}`, which is a different module/controller entirely)
- **Request body** (`SubmitStudentAssignmentRequest`, multipart): `file` — required, max 10240KB, plus a custom `SimpleAllowedFileTypeRule($studentAssignment)` — validates the uploaded extension against `assignment.allowed_file_types`, but **fails open** (`return true`) in every edge case: no student assignment, no linked assignment, empty `allowed_file_types`, or any thrown exception during the check all pass validation rather than reject.
- **Error responses:** 403 `"Can not submit an already submitted assignment"` if `status == STATUS_SUBMITTED` **and** the latest `Result.plagiarism_result < 40` (note: this guard is bypassed — i.e., re-submission is allowed — if `plagiarism_result` is `null`, since `null < 40` is `true` in PHP, so this condition is actually **always true** whenever a result exists at all, making the "already submitted" block effectively dependent only on `status`); 403 `"Submission counter full. Assignment expired"` if `submit_counter <= 0`.
- **Success response:** `apiResponse([], 'Assignment submitted successfully', 200)` — ⚠️ **3-positional-argument `apiResponse()` bug** (same systemic pattern documented in `Enrollment.md`): `apiResponse()`'s real signature is `($data, $message, string $status = 'success', $statusCode = 200)` — passing `200` as the 3rd argument lands in `$status` (typed `string`, so PHP coerces the int to the string `"200"`), not `$statusCode`. The actual response body is `{"data":[],"message":"Assignment submitted successfully","status":"200"}` at HTTP 200 — `status` is the **string `"200"`**, not `"success"`. Not a functional break here (the code path down `$statusCode`'s default of 200 happens to be correct anyway), but the `status` field shape is wrong and must be asserted exactly, not assumed to be `"success"`.
- **Error (file-branch failure):** `apiResponse([], $response['msg'], 'error', 403)` if the plagiarism sub-branch (see below) reports a non-1 status.
- **Side effects (inside `DB::transaction()`):** uploads file to S3 (`uploads/assignments/submitted/{userId}_{time}.{ext}`); deactivates any prior `Result` for this student+assignment (`latest = DEACTIVE`); creates a new `Result` row with `evaluator_id` = **`enrollment.course.default_evaluator_id`** (the cross-module default from `Course`, not from `Evaluator`'s own assignment logic — see `Evaluator.md`/`Result.md`), `bootcamp_id` from the enrollment, `is_email_sent = EMAIL_NOT_SENT`, `status = ACTIVE`; creates one `ResultExerciseScore` per exercise, with `full_marks` from the enrollment's `passing_criteria` JSON (`perSubMarks`/`perWriMarks` depending on `assignment_type`, defaulting to 10 if the criteria value is falsy) or a flat 10 if `passing_criteria` is entirely absent; sets `StudentAssignment.status → STATUS_SUBMITTED`, `submit_counter -= 1`; writes a raw `Spatie\Activitylog\Models\Activity::create()` row (`log_name: 'Student Assignment Submission'`, subject = the `Enrollment`, **not** the `StudentAssignment**) directly (bypassing the `activity()` fluent helper used elsewhere in this module).
- **⚠️ Dead plagiarism-check branch, confirmed unreachable:** the method still contains a full "Unicheck" plagiarism-checking branch (`if ($plagiarism) { ... app(StudentMyCoursesController::class)->checkPlagiarism(...) ... }`), but `$plagiarism` is hardcoded `false` immediately above it with the comment `// added because unicheck has been removed` — **this branch can never execute under any input**; only the `else` branch (no plagiarism check, `Result.status` always `ACTIVE`) ever runs. This directly contradicts `API_SPECIFICATIONS.md` §4's older note that "plagiarism check is conditionally still live here if `assignment.plagiarism == 1`" for the *other* (student self-service) submission endpoint — that claim is about a different controller entirely and doesn't apply to this one regardless; for *this* endpoint specifically, plagiarism checking is unconditionally dead.
- **Notes:** the request has no `hasFile('file')`-false branch handled explicitly in the visible code path beyond the FormRequest's own `required` rule on `file` — a request without a file never reaches the method body's file-branch logic; the method implicitly returns `null` (no response) in that case, which Laravel would still turn into a response, but it isn't one of the two documented paths — this is effectively unreachable given `file` is FormRequest-required and would already have failed with the standard 422 shape before the controller method runs.

## `GET /v1/student-assignments/validate-enrollments` — `validateEnrollments()` (controller)
- **Query params** (`ValidateEnrollmentsRequest`; `prepareForValidation()` auto-splits comma-separated `batch_id`/`enrollment_status` strings into arrays, same convenience as `assign-by-filters` below): `course_id` required int `exists:courses,id`; `batch_id` required array min 1, each `exists:course_batches,id`; `enrollment_status` optional array of ints; `topic_id` optional int `exists:topics,id`.
- **Success response:** `apiResponse(['total_enrollments' => N, 'eligible_count' => N, 'ineligible_count' => N, 'ineligible_enrollments' => [...]], 'Enrollments validation completed successfully')`. ⚠️ **Discrepancy with `API_SPECIFICATIONS.md` §4**, which describes this endpoint's response as `{total_enrollments, eligible_enrollments:[...], ineligible_enrollments:[...]}` — **the current live code does not return an `eligible_enrollments` array at all**, only `eligible_count` (an integer). A parity test built against the older spec's claimed shape will fail; only the full `ineligible_enrollments` list (each `{enrollment_id, student_name, enrollment_code, type, reason}`) is returned in detail.
- Ineligibility `reason` strings (joined with `; ` if more than one applies), confirmed verbatim from source: `"Batch not assigned"`, `"Enrollment is deactive"`, `"Package enrollment"`, `"Same topic already exists for this enrollment"` — matches `API_SPECIFICATIONS.md`'s claimed strings.
- `type` in each entry is a human label from `getEnrollmentTypeName()`: `"Normal Enrollment"`/`"Package Enrollment"`/`"Bootcamp Enrollment"`/`"Package Batch Enrollment"`/`"Unknown"` — not the raw `Enrollment::type` int.

## `POST /v1/student-assignments/{student_assignment}/re-submit` — `re_submit()` (trait method)
- **Request body:** no FormRequest — inline `Validator::make()`: `result_id` required `exists:results,id`; `reason` required int `between:1,6` (mapped via a fixed array to `Result::REASON_NEW_1`...`REASON_NEW_6` constants); `feedback` optional string.
- **Guards:** 403 `"Cannot update result. Student is inactive."` if `results.student.status != 1`; 403 `"Cannot update result. Enrollment is inactive."` if `results.student_assignment.enrollment.status != 1` — **but both these guard responses use the same 3-positional-arg `apiResponse()` call shape** (`apiResponse([], '...', 'error', 403)`, 4 args here, correctly ordered — these two are fine).
- **Eligibility:** only allowed if `studentAssignment.status == STATUS_SUBMITTED`, **or** (`status == STATUS_RESUBMITTED` **and** `assignment.plagiarism == 1`) — otherwise falls through to the final guard below.
- ⚠️ **Two more 3-positional-arg `apiResponse()` bugs, this time with real HTTP-status consequences:**
  - Success: `apiResponse($resubmitData, 'Assignment status changed to re-submit successfully', 200)` — `$resubmitData` here is **the raw boolean return value of `$studentAssignment->update($updateArr)`** (i.e., literally `true` on success), not a resource/model — `data` in the response body is the JSON boolean `true`, not an object. `status` becomes the string `"200"` (same coercion bug as `submit()` above); `statusCode` defaults to 200 so this one is functionally harmless beyond the wrong `status` field.
  - Failure (should-be-500) branch: `apiResponse([], 'Some Error Occurred', 500)` — `$status` becomes `"500"`, but **`$statusCode` stays at its default of 200** — a genuine failure (the `update()` call returned falsy) is reported as **HTTP 200** with `status: "500"` in the body. A parity test checking HTTP status alone will see this as a success.
  - Ineligible-for-resubmit branch: `apiResponse([], 'Can not re-submit a non submitted assignment', 403)` — same bug: `$status` becomes `"403"` as a string, but **`$statusCode` stays 200** — this guard, semantically a 403, is actually returned as **HTTP 200**. This is the most consequential instance of the bug in this module: a client checking `response.status === 403` (numeric) will never see it; only inspecting the body's `status` string (or `message`) reveals the rejection.
- **Side effects (inside `DB::transaction()`):** updates the named `Result` (`status → RESUBMIT`, `reason`, `resubmission_feedback`); `StudentAssignment.status → STATUS_ACTIVE`; `submit_counter += 1` **only if it was `<= 3`** (i.e., capped — cannot exceed 4, the original starting value); queues `AssignmentResubmit` mail to the student; writes a raw `Activity::create()` row (`log_name: 'Student Assignment Resubmission'`, subject = the `Enrollment`).
- **Dead code inside this method:** the `triggerAssignmentResubmitEvent()` webhook-dispatch calls that would fire on this path are commented out (both the with-feedback and without-feedback variants) — no `WebhookTriggered` event fires from resubmission today, regardless of what any webhook-consumer documentation elsewhere might imply.

## `GET /v1/student-assignments/get-resubmit-data/{student_assignment_id}/{student_id}` — `getStudentAssignmentResubmissionList()` (trait method)
- Both path params are plain values, not route-model-bound; `$student_id` is accepted in the URL but not actually cross-checked against the resolved records inside the method beyond being passed through to the repository query — verify repository-level filtering directly (`ResultRepository::getStudentAssignmentResubmissionList()`) if precise scoping matters for a test.
- **Success response:** `apiResponse($resubmitData, 'Successful', 200)` — same 3-positional-arg coercion bug (`status` becomes string `"200"`), harmless here since `statusCode` still defaults to 200. `$resubmitData` is `StudentAssignmentResubmissionResource::collection(...)` — each item is a `Result` row with `created_at`/`updated_at`/`evaluator_id`/`assignment_id`/`status`/`is_email_sent`/`student_id`/`plagiarism_result`/`plagiarism_result_file`/`submitted_date`/`submitted_file`/`feedback_file_original_name`/`feedback_link`/`evaluation_date`/`evaluation_due_date`/`feedback_to_student`/`is_review_done`/`waive_marks`/`feature_assignment`/`bootcamp_id` excluded (i.e. only the remaining raw columns plus a nested `student_assignment: {id, submit_counter}` survive) — note the literal excluded-key `'feedback_file  '` (two trailing spaces) in the source's `Arr::except()` call **does not match** the real column `feedback_file` (no trailing spaces) — this means **`feedback_file` is NOT actually excluded** despite the author's apparent intent, and will leak through in the response. Preserve this bug in parity assertions — the response includes `feedback_file`, not just `feedback_file_original_name`.
- **Error branch** (`apiResponse([], 'Some Error Occurred', 500)`) is dead code in practice — `StudentAssignmentResubmissionResource::collection()` always returns a (possibly empty) collection object, which is always truthy, so the ternary's false branch can never actually trigger.

## `POST /v1/student-assignments/import` — `import()` (trait method)
- **Request body** (`Modules\Enrollment\Http\Requests\EnrollmentCsvImportRequest` — **cross-module FormRequest**, `file` required CSV): header row must exactly match one of the 14 literal column names `Enrollment Code,Topic,Plagiarism,Last Date,Word Count,Download,Type,Tags,Exercises,Allowed File Types,Is AI Enabled,AI Model ID,Instruction File,Feedback File` (validated via `in:` rule against the header array — any unexpected column name anywhere in the header fails the whole import before any row is read).
- Per-row validation (inline `Validator`, not a FormRequest): `Enrollment Code` required, `exists:enrollments,enrollment_code`; `Topic` required string; `Plagiarism` required `in:0,1`; `Word Count` required integer; `Download` required **only if** `Type == Assignment::TYPE_SUBJECTIVE` (0), else nullable URL; `Type` required, one of `0`/`1`; `Last Date` required (no format check at the per-row validator level); `Exercises` required numeric 1–10; `Tags` required (any non-empty value, format unconstrained here); `Is AI Enabled` optional `in:0,1`; `AI Model ID` optional `exists:ai_models,id`; `Instruction File`/`Feedback File` optional URL.
- **Error response (bad header):** hand-rolled `response()->json(['status'=>'error','message'=>'Validation failed','data'=>['errors'=>$e->failures()]], 422)` — note this uses `Maatwebsite\Excel\Validators\ValidationException`'s `->failures()`, a **different exception class and error shape** from Laravel's own `ValidationException` documented in `_COMMON_CONVENTIONS.md` (no `errors` keyed by field name in the usual way — `failures()` returns a flat list of failure objects).
- **Error response (bad row data):** hand-rolled `response()->json(['status'=>'error','message'=> "Validation failed on row {N} : {enrollment_code} : {first field error for each of 9 checked fields, concatenated}"], 422)` — **stops at the first invalid row**, not a full per-row error report; `data` key is entirely absent from this error shape (unlike the header-validation error above, which does include `data.errors`).
- **Success response:** `apiResponse('', 'Assignments created by import file')` — `data` is an empty **string**.
- **Side effects:** uploads the raw CSV to S3 (`imports/assignments/{firstName}_{uniqid}_{time}.{ext}`); writes an `activity()`-helper log (`event: 'Student Assignment Import Initiated'`); dispatches `StudentAssignmentCsvImport::dispatch(...)` on queue `default_high` — **actual row-by-row assignment/student-assignment creation happens asynchronously in the job**, not in this request/response cycle; a parity test must poll rather than assert immediate creation.
- **Notes:** `Allowed File Types` column values are validated separately (`StudentAssignmentCsvImport::parseAllowedFileTypes()`) in a loop **after** the main per-row validation loop already completed for all rows — if this later loop throws, it's a real Laravel `ValidationException` (not caught/converted here), so it surfaces as the standard 422 shape from `_COMMON_CONVENTIONS.md`, a third distinct error shape for this one endpoint depending on which validation stage fails.

## `POST /v1/student-assignments/assign-by-filters` — `assignByFilters()` (controller)
- **Request body** (`AssignByFiltersRequest`; `prepareForValidation()` auto-splits a comma-separated `batch_id` string into an array): `course_id` required int `exists:courses,id`; `batch_id` required array min 1, each `exists:course_batches,id`; `submission_last_date` required, format `Y-m-d`; `number_of_exercises` required numeric 1–10; `assignment_download_file` required only if `assignment_type == TYPE_SUBJECTIVE`; `assignment_topic` required max:255; `assignment_type` required, `in:0,1`; `plagiarism` required boolean (inert, per the dead plagiarism-branch findings elsewhere in this module); `word_count` required integer; `tags` optional array `{key,value}`; `allowed_file_types` required array min 1; `ai_model`/`is_ai_enabled`/`assignment_instruction_link`/`assignment_sample_feedback_link`/`assignment_instruction_file`/`assignment_sample_feedback_file` optional AI-config fields (file variants branch on `hasFile()`).
- **Success response:** `apiResponse([], 'Assignment added successfully', statusCode: 202)` — **HTTP 202 Accepted** (named argument, so this one is NOT subject to the positional-arg bug) — correctly signals async processing, unlike several other endpoints in this module that return 200 for similarly-deferred work.
- **Side effects:** if `is_ai_enabled` and instruction/feedback files were uploaded, they're attached to the **`Course`** model's media library (not `Assignment`'s) at this stage, and the resulting URL is put into the job payload — file objects themselves are stripped from the payload before dispatch (can't serialize an `UploadedFile` onto a queue). Writes an `activity()`-helper log (`event: 'Bulk Assignment Started'`) synchronously. Dispatches `AssignAssignmentsByFiltersJob` on queue `default_high`, which (per-enrollment, chunked 100 at a time, each wrapped in `retry(3, ..., 100)` + its own `DB::transaction()`): creates one `Assignment` + one `StudentAssignment` row per matching, active, non-duplicate-topic enrollment; queues a `StudentAssignmentCreated` mail per student (no admin CC — see note below); on completion, queues one `BulkAssignmentReportMail` to the initiating admin.
- ⚠️ **Discrepancy with `API_SPECIFICATIONS.md` §4:** that doc claims this flow fires a `WebhookTriggered` event as a side effect. **The actual call, `$this->triggerWebhook($studentAssignment->assignment, $enrollment)`, is commented out** in `AssignAssignmentsByFiltersJob::handle()` — no webhook fires from this endpoint's job today. Likewise, the doc doesn't mention (and it's worth calling out) that the job's admin-CC logic for `BulkAssignmentReportMail` is also dead: `resolveAdminEmails()` builds a two-address string (`{initiating admin's email},schedulingteam@lawsikho.in`), but the `->cc($adminEmails)` call that would actually attach the second address is commented out — **the bulk-assignment report mail only ever reaches the single admin who triggered the job**, `schedulingteam@lawsikho.in` is computed but never used.
- **Notes:** the in-app `NotificationEntity`/`NotificationUser` "New Assignment Assigned" system notification is created **only on the branch where the student has no email on file** (i.e., as a fallback when the mail can't be queued) — a student with a valid email gets the email but not the in-app notification from this flow; this is asymmetric with the individual `store()`/`createStudentAssignment()` path (see `Assignment.md`/this file's `store()`-adjacent logic), which sends both unconditionally.

## `DELETE /v1/student-assignments/delete-multiple` — `destroyMultiple()` (trait method)
- **Request body** (`DestroyMultipleRequest`): `ids` required array, each `exists:student_assignments,id`.
- **Success response:** `apiResponse([], 'Student Assignments deleted successfully')` — always 200, **even if some/all of the requested ids were silently skipped** (see below) — the response doesn't distinguish "all deleted" from "none deleted because all were submitted/evaluated."
- **Behavior:** `StudentAssignmentRepository::deleteMultipleWhereStatusIsNotSubmitted($ids)` — despite the method name mentioning only "not submitted," the actual repository query (verify directly if building a precise test) is expected to also exclude `STATUS_EVALUATED` rows, matching the `deletedStudentAssignments` re-query in this same method which explicitly filters `status != SUBMITTED AND status != EVALUATED` — i.e. submitted **and** evaluated assignments are both silently immune to this bulk delete, unlike the single-record `destroy()` (apiResource action, see below) which only blocks `SUBMITTED` explicitly and would 404-style-reject an evaluated one only incidentally.
- **Side effects:** cascading `deleteCorespondingResults($ids)` (note the literal method-name typo **`deleteCorespondingResults`**, missing an "r" — real method name, not a doc typo) — deletes every `Result` row whose `assignment_id` is in the given id list (soft-delete, per the `Result` entity — see `Result.md`); `multipleDeleteFirstAssignmentLog()` — for each deleted student assignment, finds a `FirstAssignmentSendLog` row matching `enrollment_id`+`assignment_id` and either re-points it at another subjective `StudentAssignment` for the same enrollment (if one exists) or deletes the log row entirely (if not) — a "first assignment" bookkeeping table consumed by the NPS-scheduling logic (see `NPS.md`'s `getSurveyData` endpoint, which reads `StudentAssignment` timing, not this table directly — the two are related but not identical mechanisms). A single `activity()`-helper log entry summarizes all deletions in one call (not one per assignment).

## `PUT /v1/student-assignments/update-multiple` — `updateMultiple()` (controller — see the module-wide shadowing warning above; the trait's same-named method never runs)
- **Request body** (`UpdateMultipleRequest`): `ids` required array, each `exists:student_assignments,id`; `submission_last_date` required `Y-m-d`; `number_of_exercises` required numeric 1–10; `assignment_download_file` optional URL; `assignment_topic` required max:255 (**validated but functionally inert — see module-wide warning**); `assignment_type` required `in:0,1`; `plagiarism` required boolean; `word_count` required integer; `tags` optional array (**also functionally inert** — validated but never synced); `ai_model_id`/`is_ai_enabled`/AI link and file fields optional.
- **Success response:** `apiResponse([], 'Student Assignments updated successfully')` (200).
- **Error response:** `apiResponse([], 'No assignments found', 'error', 404)` if none of the given `ids` resolve to existing `StudentAssignment` rows (note: since `UpdateMultipleRequest` already validates each id with `exists:student_assignments,id`, this branch is effectively unreachable in practice — it would require every id to have been deleted between validation and the query, a narrow race condition, not a normal-path outcome).
- **Side effects (inside `DB::transaction()`, `set_time_limit(180)`):** if `is_ai_enabled` and a file was uploaded, attaches it once to the **first** student assignment in the batch's underlying `assignment` model's media library (not per-student — every row in the batch shares the one uploaded file's resulting URL); for each id: updates the `StudentAssignment` row (`submission_last_date`, `number_of_exercises`, `is_ai_enabled`, and AI fields — nulled out if `is_ai_enabled` is false, matching the "don't inherit course defaults" convention used elsewhere in this module) and the **parent `Assignment` template** (`assignment_type`, `word_count`, `plagiarism`, `number_of_exercises`, `allowed_file_types`, `assignment_download_file`, plus the same AI fields) — meaning every `StudentAssignment` sharing the same underlying `Assignment` template id gets that template row overwritten repeatedly (once per id in the loop) with identical values, a redundant-but-harmless repeat write; logs one `activity()`-helper entry per student assignment (`event: 'Student Assignment Bulk Updated'`).

## `GET /v1/student-assignments/export/csv` — `export()` (trait method)
- **Success response:** `apiResponse('', 'Assignment Csv file exporting started')` — `data` is an empty string.
- **Side effects:** dispatches `AssignmentCSVDownload::dispatch(auth()->user(), request()->all())` on queue `default_medium` — the job builds a CSV from `StudentAssignment` rows (filtered by whatever query params were on the original request, passed through wholesale), uploads to S3 (`exports/tmp/assignments/{filename}`), then emails `StudentAssignmentCSVCompletedMail` and fires `StudentAssignmentCsvCompletedNotification` — a started+completed dual-signal pattern matching `NPS`'s export flow, unlike `Assignment`'s single-completion-only export (see `Assignment.md`).

## `GET /v1/student-assignments/dashboard/list` — `studentAssignmentsDashboardData()` (trait method)
- **Success response:** `apiResponse(['total', 'pending', 'submitted', 'reviewed', 'bar' => [[...header], [7-day row], [30-day row], [90-day row]]])` — `bar` is a Google-Charts-style array-of-arrays (header row + 3 data rows), matching the pattern seen in `NPS.md`'s dashboard endpoints.
- **Caching:** wrapped in `Cache::remember('dashboard.student_assignments.data', 60*30, ...)` — a **shared cache key with no scoping by user, course, or any filter** — the entire response is memoized for 30 minutes regardless of which authenticated user calls it; a parity test run shortly after another test/user hit this endpoint will see stale cached data, not a fresh computation, for up to half an hour.

## `PUT /v1/student-assignments/update-multiple-ai-data` — `bulkEvaluateEdit()` (controller)
- **Request body** (`UpdateMultipleAIEvaluationDataRequest`): `ids` required array, each `exists:student_assignments,id`; `ai_model_id`/`is_ai_enabled`/`assignment_instruction_link`/`assignment_sample_feedback_link`/file variants — all optional, no other fields accepted (no `submission_last_date`/`assignment_type`/etc. — a narrower request than `updateMultiple` above).
- **Success/error responses:** identical shapes to `updateMultiple()` above (`'Student Assignments AI Evaluation Data updated successfully'` / the same practically-unreachable `'No assignments found'` 404).
- **Behavior:** near-duplicate of `updateMultiple()`'s update loop, but only touches AI-related fields on both `StudentAssignment` and the parent `Assignment` template (no `submission_last_date`/`word_count`/`plagiarism`/etc.) — `activity()` event name differs: `'Student Assignment AI Evaluation Data Bulk Updated'`.

## `POST /v1/request-large-csv-set` — `bypass_large_csv_set()` (controller, route name `bypass.large.csv.set`)
- **Request body** (`BypassLargeDataSetRequest`): `component` required (no type/format constraint beyond presence); `comment` required.
- **Success response:** a **hand-rolled plain PHP array**, not `apiResponse()`: `{"data": "CSV Export Request Send to the Admin", "message": "CSV Export Request Send to the Admin", "status": "success"}` — note `data` and `message` are identical strings, and the grammar "Send" (not "Sent") is verbatim from source.
- **Side effects:** synchronously (`Mail::to(...)->send()`, not `->queue()`) emails `BypassLargeData` to a **hardcoded list of 4 addresses** in source: `dipanajan@lawsikho.in`, `mayukh.b@lawsikho.in`, `chhandak@lawsikho.in`, `techteam@lawsikho.in` — note the misspelling `dipanajan` (verbatim from source, likely meant "dipanjan") — a parity test's mail assertions must match this exact literal list, not a config-driven admin list.

## `GET /v1/student-assignment/meta-data` — `getMetaData()` (controller — note singular `student-assignment` in the path, unlike every other route in this module which uses the plural `student-assignments`)
- **Success response:** `apiResponse(['data' => ['total' => N, 'submitted_assignment' => N]])` — note the **double-nested `data`**: the outer `apiResponse()` envelope's own `data` key contains an inner object that itself has a `data` key, so the full body is `{"data": {"data": {"total": N, "submitted_assignment": N}}, "message": "Success", "status": "success"}` — this is because the controller passes `['data' => [...]]` as the *first* argument to `apiResponse()`, which itself already wraps everything in `data`. Preserve this double-nesting exactly; do not "flatten" it when writing a parity assertion.

## `GET /v1/student-assignments/{student_assignment_id}/activity` — `activity()` (trait method, route name `student_assignment.activity`)
- **Error response:** `apiResponse([], 'StudentAssignment Not Found', 'error', 404)` if the id doesn't resolve via `StudentAssignmentRepository::findById()`.
- ⚠️ **Confirmed functional bug — this endpoint queries the wrong subject type/id pairing and will effectively always return an empty (or wrong) result set.** On success it delegates to `App\Http\Traits\ActivityLog::logOfAssignment($id, [...])`, which runs `Activity::query()->where('subject_id', $id)->where('subject_type', 'Modules\Assignment\Entities\Assignment')`. But `$id` here is a **`StudentAssignment` id** (validated via `studentAssignmentRepo->findById($id)` just above), and every actual activity log this module writes for a student assignment (`'Student Assignment Created'`, `'Student Assignment Deleted'`, the AI-config-update event, etc.) is logged via `activity()->on($studentAssignment)`, which sets `subject_type = 'Modules\StudentAssignment\Entities\StudentAssignment'` — a **different subject type entirely**, and a numerically unrelated id space from `Assignment`'s own ids. This endpoint will only ever surface real data by numeric coincidence (if an unrelated `Assignment` row happens to share the same id and has its own logged activity) — for the overwhelming majority of calls it will return an empty `data` array despite the target `StudentAssignment` genuinely having activity history. A parity test expecting this endpoint to surface a student assignment's own audit trail will fail; if AP-V3 is expected to actually fix this (query `StudentAssignment`'s own activity), confirm the intended behavior with the team rather than assuming either the bug or the fix is "correct."

## Core CRUD (`Route::apiResource('student-assignments', 'StudentAssignmentController')`)

### `GET /v1/student-assignments` — `index()` (controller)
- Query: `rows` (default 15). **Two entirely different query/resource paths, chosen by `isSimpleQuery()`:** a request with *no* filter params (or only `rows`, or only `rows`+`cursor`/`page`) is treated as "simple" — uses a plain `StudentAssignment::query()` with explicit column selects and full relation eager-loading, rendered via **`StudentAssignmentOldResource`** (despite the "Old" name, this is the resource used for the *unfiltered/simple* case, not a deprecated path — a counter-intuitive naming choice worth noting for anyone reading the code cold). Any other query param present at all switches to "filtered" mode: queries `student_assignments_view.*` (a **database VIEW**, not the base table — implies denormalized columns like `full_name`/`email`/`bootcamp_display_name`/`enrollment_code` are read directly off the view rather than via relations) and renders via **`StudentAssignmentResource`** (the "new"/plain-named one), which pulls those same fields as flat magic-property accesses (`$this->full_name`, `$this->email`, etc.) rather than through `$this->enrollment->student->...`.
- **Success response:** `{resourceClass}::collection(...)->additional(['meta' => ['range' => calculateRangeForCursor($rows)]])` — note **no `total` key in `meta` at all** for this endpoint (unlike almost every other cursor-paginated listing in this codebase, which nests `total` inside `range` at minimum) — `range` itself does include `total` (`{from, to, total}`), so the data exists, just not duplicated at the top `meta` level the way `NPS`/`Enrollment` do.
- Both resource classes share nearly identical logic (duplicated code, not shared via inheritance/trait) for `checkTheStatus()` (derives a human `"Expired"/"Submitted"/"Evaluated"/"Pending"` string from `status`+`submit_counter`+`submission_last_date`), plagiarism/resubmission history lookups against `results`, and nested `enrollment`/`assignment` sub-objects — see source for the full field list; both include `plagreq` (`'Y'`/`'N'` from `assignment.plagiarism`), `rating_id` (a `Result.reason` value, oddly named), and AI-model info via `getEffectiveAIModel()` (course-level fallback per `Assignment.md`'s note on the same method).

### `POST /v1/student-assignments` — `store()` (controller) — individual/small-batch creation, topic-driven
- **Request body** (`StoreRequest`): `enrollment_ids` required array, each `exists:enrollments,id`; `submission_last_date` required `Y-m-d`; `number_of_exercises` required numeric 1–10; `assignment_download_file` required only if `assignment_type == TYPE_SUBJECTIVE`; `assignment_topic` required max:255; `assignment_type` required `in:0,1`; `plagiarism` required boolean (inert); `word_count` required integer; `tags` optional array; `allowed_file_types` required array; AI fields optional.
- **Behavior — topic-reuse branching:** if a `Topic` with the given title already exists, a **separate code path** runs (with a `try/catch` around the whole per-enrollment loop) that additionally checks, per enrollment, whether that enrollment already has a `StudentAssignment` for this exact topic — if so, the **entire request aborts** via a thrown `\Exception` caught at the top level, returning `apiResponse([], $e->getMessage(), 'error', 422)` with message `"This Enrollment Already Has This Topic, Please try with another topic"` — note this means **one bad enrollment in a multi-enrollment batch rolls back the whole transaction** (it's inside `DB::transaction()`), even if other enrollments in the same request were valid. If the topic is new (doesn't exist yet), a **different code path** runs (no duplicate-topic check at all, since a just-created topic can't already be attached to anything) — structurally, the duplicate-topic guard only exists in the "topic already exists" branch.
- Each enrollment additionally requires (in both branches) `whereRelation('course', 'course_category_id', 8) OR whereNotNull('batch_id')` to even be found by the initial `Enrollment::query()->where(...)` lookup — an enrollment failing this is **silently skipped** (no error, no mention in the response) rather than reported as ineligible, unlike `validateEnrollments()`'s explicit ineligibility reporting elsewhere in this module.
- **Success response:** `apiResponse([], 'Student Assignments created successfully', statusCode: 201)` (named-argument call — correct, not subject to the positional bug) in both branches.
- **Side effects (per successfully-processed enrollment):** creates one `Assignment` (via `createAssignment()`) and one `StudentAssignment` (via `createStudentAssignment()`); attaches tags (additive, `attach()` not `sync()`); queues `StudentAssignmentCreated` mail to the student; creates an in-app `NotificationEntity`/`NotificationUser` row (unconditionally, unlike the bulk `assign-by-filters` path's email-failure-only fallback); notifies the **acting admin user** (not the student) via `\Modules\StudentAssignment\Notifications\StudentAssignmentCreated` (a same-named-but-distinct class from the student-facing mail); writes an `activity()`-helper log entry per student assignment (`event: 'Student Assignment Created'`); conditionally writes a `FirstAssignmentSendLog` row if this is the enrollment's first-ever subjective assignment.
- ⚠️ **All `AssignmentLog`/`AssignmentLogMapping` write code inside this method is commented out** — confirmed dead, consistent with the module-wide finding documented in `AssignmentSendingLog.md`.

### `PUT /v1/student-assignments/{studentAssignment}` — `update()` (controller)
- **Request body** (`UpdateRequest`): all fields nullable — `submission_last_date`, `number_of_exercises`, `assignment_download_file`, `assignment_topic`, `assignment_type`, `plagiarism`, `word_count`, `tags`, `ai_model_id`, `is_ai_enabled`, AI link/file fields.
- **Success response:** `apiResponse(['student_assignment' => StudentAssignmentResource::make($studentAssignment->fresh())], 'Student Assignment updated successfully')` — uses the "filtered-query" `StudentAssignmentResource` (the `student_assignments_view`-column one), even though this single-record fetch via `fresh()` is a plain Eloquent model, **not** a row from the view — any resource field that assumes a view-only column (e.g. `full_name`, `email` as flat magic properties) will resolve to `null`/undefined here rather than the value a listing call would show, since the base table doesn't have those denormalized columns. This is a real shape inconsistency between this endpoint and `index()`'s filtered-mode listing for what is nominally "the same resource."
- **Side effects:** reuses or creates a `Topic` from `assignment_topic` if provided (else keeps the existing one); updates both the `StudentAssignment` row and its parent `Assignment` template (AI fields nulled if `is_ai_enabled` is falsy, per the module's standing "don't inherit course defaults" convention); `syncTags()` here is **destructive-by-omission** (`sync([])` if `tags` key absent — same asymmetric create-vs-update tag semantics documented in `Assignment.md`); queues `StudentAssignmentUpdated` mail; logs one `activity()`-helper entry (`event: 'Student Assignment AI Config Updated'` — the event name is AI-specific even though the update can touch non-AI fields too).

### `DELETE /v1/student-assignments/{studentAssignment}` — `destroy()` (controller)
- **Error response:** `apiResponse([], 'Student Assignment with status Submitted cannot be deleted', 'error', 404)` if `status == STATUS_SUBMITTED` — **HTTP 404 for what is semantically a 403/409 state-conflict**, not a "resource not found" condition; note this single-record `destroy()` only blocks `STATUS_SUBMITTED`, **not** `STATUS_EVALUATED` (contrast with `destroyMultiple()` above, which blocks both) — an evaluated student assignment CAN be deleted via this single-record endpoint even though the bulk endpoint would silently skip it.
- **Success response:** `apiResponse([], 'Student Assignment deleted successfully')`.
- **Side effects:** `deleteFirstAssignmentLog()` (re-point-or-delete the `FirstAssignmentSendLog` row, same logic as the bulk variant); writes one `activity()`-helper log entry (`event: 'Student Assignment Deleted'`); **soft-deletes** the `StudentAssignment` (`SoftDeletes` trait on the entity — `$studentAssignment->delete()`); cascades to `deleteCorespondingResults()`, which **hard-deletes** matching `Result` rows via a `foreach` loop calling `->delete()` per row (soft-delete per `Result`'s own trait — see `Result.md` — so "hard" here means "each row individually," not "bypasses soft-deletes").
- **Dead code:** `triggerDeleteAssignmentEvent()` webhook call is commented out — no webhook fires on deletion despite the method existing.

### `GET /v1/student-assignments/{studentAssignment}` — `apiResource`'s `show` — **confirmed broken, no method exists**
Neither `StudentAssignmentController` nor `StudentAssignmentTrait` implements a `show()` method — confirmed by grepping both files in full. Calling this route triggers a PHP fatal `Error: Call to undefined method`, surfacing as an uncaught **500**, not a clean 404 — the same broken-`apiResource`-action pattern already documented for `NPS`, `AssignmentTag`, and `AssignmentSendingLog`.

## Summary of endpoints documented

**20 route entries** in `Modules/StudentAssignment/Routes/api.php` (14 named routes + the 5-route `apiResource` + 1 student-guard route = 20 total; `apiResource`'s `show` is one of the 5 but is broken):
- **19 live/working, 1 confirmed broken:** `GET /v1/student-assignments/{studentAssignment}` (`apiResource`'s `show`) — fatal 500, undefined method.
- All other 19 routes documented above with confirmed source-level behavior.

**Notable findings for parity testing (highest-impact first):**
- **`updateMultiple()` shadowing:** the controller's own method silently overrides the trait's same-named method — `assignment_topic`/`tags` are validated but functionally inert on `PUT /v1/student-assignments/update-multiple`.
- **`re_submit()`'s two most severe 3-positional-arg `apiResponse()` bugs**: its "some error occurred" (should-be-500) and "cannot re-submit" (should-be-403) responses both actually return **HTTP 200** — a parity test relying on HTTP status codes alone for these two branches will misread them as success.
- **`activity()` (per-student-assignment audit trail) queries the wrong `subject_type`/id pairing** and will typically return empty results regardless of real activity history — confirm with the team whether AP-V3 should reproduce this bug or fix it.
- **`getMetaData()`'s response is double-nested under `data.data`** — a distinctive, easy-to-miss shape.
- **`validateEnrollments()`'s response omits the `eligible_enrollments` array** that `API_SPECIFICATIONS.md` claims exists — only a `eligible_count` integer is present.
- **`assign-by-filters`'s `WebhookTriggered` event and admin-CC on the bulk report mail are both dead/commented code** — contradicts `API_SPECIFICATIONS.md`'s side-effects claim for the webhook specifically.
- **`getStudentAssignmentResubmissionList()`'s resource has a trailing-whitespace key-name bug** (`'feedback_file  '` vs. real column `feedback_file`) that causes `feedback_file` to leak into the response despite apparent intent to exclude it.
- **`submit()`'s plagiarism-check branch is entirely dead** (hardcoded `$plagiarism = false`) — grading always proceeds via the no-plagiarism-check path regardless of `assignment.plagiarism`.
- **`bypass_large_csv_set()` emails a hardcoded 4-address list** (including a literal misspelling, `dipanajan@lawsikho.in`) rather than any config-driven admin list.
- **`studentAssignmentsDashboardData()` caches its response for 30 minutes with a single, unscoped cache key** shared by every caller.
- All `AssignmentLog`/`AssignmentLogMapping` write attempts inside this module's `store()` are dead/commented, consistent with `AssignmentSendingLog.md`'s module-wide finding.

**Cross-module coupling confirmed from this side:**
- `submit()` creates the `Result` row with `evaluator_id` sourced from **`enrollment.course.default_evaluator_id`** (a `Course`-module field), not from anything in the `Evaluator` module itself — evaluator *assignment* logic proper lives in `Result` (`assign-evaluator-single`/`assign-evaluator-round-robin`, documented in `Result.md`), confirming `API_SPECIFICATIONS.md`'s note that `Evaluator` itself is read-mostly master data.
- `Assignment.php`'s own `store()`/`update()` (see `Assignment.md`) write directly into this module's `student_assignments` table as a side effect (retroactive assignment on template creation, AI-field propagation on template update) — a fully independent creation path from this module's own `store()`/`assign-by-filters`, all three converging on the same table.
- `deleteCorespondingResults()`/`destroy()` cascade into `Result` (soft-delete) — see `Result.md` for that entity's own soft-delete/status semantics.

**Confidence:** High — every endpoint traced to its controller or trait method (including the shadowing discovery, confirmed by reading both same-named method bodies in full), every FormRequest/Resource read directly, and every "dead code" claim (webhook triggers, plagiarism branch, `AssignmentLog` writes, admin-CC) confirmed by finding the exact commented-out line, not inferred from absence.
